## §0 세 요구의 관계와 사실 분리

### 0.1 왜 한 문서에 셋을 담고도 3부로 나누는가

| 요구 | 성격 | 다른 요구와의 결합 |
|------|------|--------------------|
| **A** 단일 세션 강제 폐기 | **문서 작업**(코드 0줄) | 없음 |
| **B** 역할별 테스트 모드 | 클라 신규 기능(INI·세션·UI) | C와 **1지점 접촉**: 테스트 모드가 PIN 게이트를 통과해야 설정 화면(=C의 진입점)에 닿는다 → §B8 |
| **C** 라이선스 인앱 열람 | 클라 UI 이동·확장 | B와 위 1지점. A와 무관 |

세 요구는 **서로 다른 파일을 건드리고 서로의 완료를 기다리지 않는다.** 착수 순서는 A → C → B를 권한다(A는 코드 없음, C는 위험이 국소, B가 가장 넓다). 단 §B8의 PIN 게이트 결론은 C의 접근 경로 추적(§C4)과 **같은 사실**을 근거로 하므로, B를 먼저 하면 C의 §C4 표를 갱신해야 한다.

# A부 · 단일 세션 강제 스펙 폐기

## A1 요구와 판정

### A1.1 요구 원문

> "한 계정으로 다른 플랫폼이나 다른 PC로 로그인 시 기존 기기 로그아웃되도록 하는 기능 제거 (모든 플랫폼 동일). QR 생성 횟수를 과금하므로 불필요하다고 판단. 프레임은 모든 PC에 설치되지만 1회 다운로드 정책으로 과한 청구를 막을 수 있다."

### A1.2 판정 — 제거 대상은 코드가 아니라 **설계 스펙**이다

| 판정 | 근거 |
|------|------|
| 코드에서 지울 것이 **없다** | VF-1. `web/functions/src/routes/auth.ts`의 라우트는 로그인 1개뿐이고, 세션 레지스트리·하트비트·`sid` 클레임·`deviceId` 전송이 어디에도 없다 |
| 폐기 대상은 `docs/billing/06` 전체와 **그것을 전제로 삼은 다른 문서의 서술** | 06 자신의 §2 사실표가 "서버에 활성 세션·기기 레지스트리가 **없다**(신설 필요)"라고 적고 있다 — 즉 06은 처음부터 **미래 계획서**였다 |
| `docs/billing/README.md`가 "성격: 설계 문서 — 코드 구현 금지"를 선언하고 있다 | 따라서 이 폐기는 **구현 계획의 취소**이며, 배포물·DB·API에 아무 영향이 없다 |

> ✅ **이 판정이 중요한 이유**: "기능 제거"로 착수하면 개발자가 코드에서 세션 코드를 찾다가 못 찾고 시간을 쓰거나, 더 나쁘게는 **엉뚱한 것을 지운다**(예: `SessionContext`, `BackendSession`, `sessionId`(업로드 세션 식별자) — 이름이 비슷하지만 전혀 다른 것들이다). 아래 §A3에 "건드리면 안 되는 동명이의" 표를 둔다.

## A2 폐기 방식 — 삭제가 아니라 "폐기 + 근거 보존"

리포 선례를 따른다. 커밋 `b20d49f`(프레임 zip 내보내기/가져오기 폐기)가 확립한 형식이고, `docs/web-client/05 §4.6`이 그 물리적 형태다.

### A2.1 형식 규약 (선례 복제)

```markdown
### N. ~~제목~~ → ❌ **2026-08-10 폐기**

> 🚫 **이 절의 규격은 더 이상 구현 대상이 아니다.** {무엇을 하지 않기로 했는가}
>
> **폐기 사유**: {명분이 무엇이었고 왜 소멸했는가}
>
> {폐기가 남기는 구멍과 그 처리 — 링크}

<details><summary>폐기된 종전 규격(이력 보존)</summary>
{원문 그대로}
</details>
```

| 규칙 | 이유 |
|------|------|
| **파일을 삭제하지 않는다** | 06은 정책 3안(S1/S2/S3) 비교와 "다점포 운영과의 충돌"이라는 **운영 지식**을 담고 있다. 좌석제 수요가 확인되면 다시 열릴 문서다 |
| 제목에 취소선 + 날짜 | 목차·검색 결과에서 **열기 전에** 폐기 상태가 보인다 |
| `<details>`로 원문 보존 | 기본 접힘 → 읽는 사람이 폐기된 규격을 현행으로 오독하지 않는다 |
| 참조하는 쪽도 함께 고친다 | 문서 하나만 폐기 표시하고 참조를 남기면 **다른 문서가 계속 거짓을 말한다.** 이것이 §A4의 존재 이유다 |

## A3 ⚠️ 건드리면 안 되는 동명이의 (착수 전 필독)

"세션"이라는 단어가 이 리포에서 **네 가지 다른 것**을 가리킨다. 폐기 작업이 코드에 손을 대는 순간 사고가 난다.

| 이름 | 실체 | 폐기와의 관계 |
|------|------|---------------|
| `SessionContext` (`src/MCPhoto.App/`) | **한 손님의 촬영 세션** 상태(프레임·컷·결과) + 계정 단일 소스 | **무관.** 절대 손대지 않는다 |
| `IBackendSession` / `BackendSession` (`src/MCPhoto.Http/Session/`) | 메모리 JWT 홀더 | **무관.** 로그인 토큰 보관은 그대로 유지된다 |
| `BackendSessionSynchronizer` | 로그아웃 시 JWT 폐기 배선 | **무관.** 오히려 반드시 살아 있어야 한다 |
| `sessionId` / `ResultSession` / `domain/session.ts` | **업로드 전송 세션** 식별자(Storage 경로·QR URL 조립) | **무관.** 과금 단위 그 자체다 |
| ~~`sessions/{userId}`·`sid`·하트비트~~ | 06이 신설하려던 **로그인 세션 레지스트리** | **이것만** 폐기 대상. 코드에 존재하지 않으므로 지울 것이 없다 |

> ⚠️ **A부의 코드 변경 파일 수는 0이다.** PR diff에 `src/` 또는 `web/functions/`가 한 줄이라도 있으면 그 PR은 잘못됐다.

## A5 폐기가 다른 설계에 남기는 구멍 — 전수 분석

06은 5개 설계의 **전제**였다. 전제를 빼면 그 설계들이 근거 없이 떠 있게 된다. 하나씩 판정한다.

### A5.1 구멍 ① — `04 §5` 로컬 프레임 purge (**이미 메워져 있다**)

| 항목 | 내용 |
|------|------|
| 06이 제공하던 전제 | "로그아웃 시 로컬 프레임을 지우려면 **'지금 이 기기가 이 계정의 세션인가'를 서버가 판정 가능**해야 한다"(06 §1) |
| 전제가 사라지면 | 강제 로그아웃이라는 트리거(04 §5.3 두 번째 행)가 존재하지 않게 된다 |
| **판정** | **구멍이 아니다.** `04 §5`는 **2026-08-07에 이미 폐기**됐다(VF-3). 폐기 사유는 세션이 아니라 소유권 서명 도입(`.slots #owner` 서명 → 파일이 남아도 타 계정에 보이지 않는다)이었다. 즉 purge 설계는 06과 **무관한 이유로** 먼저 죽었다 |
| 조치 | `04 §5` 폐기 블록에 한 줄 추가: `※ 2026-08-10: 06(단일 세션)까지 폐기되어 §5.3의 "강제 로그아웃" 트리거 자체가 소멸했다. 이 절의 폐기 근거는 이제 둘이다.` |
| 파생 정리 | `README.md:14`의 경고 배너 ②(로그아웃 시 로컬 프레임 삭제)도 **함께 정리**해야 한다(R1) — 이미 죽은 항목이 "현행 계약과 정면으로 다르다"고 경고하고 있다 |

> ✅ **운이 좋았던 것이 아니다.** 두 폐기가 같은 방향인 이유는 명확하다 — 둘 다 "서버가 기기를 통제한다"는 전제 위에 있었고, 이 프로젝트는 **소유권을 데이터에 서명해 넣고 과금은 사용량으로 센다**는 반대 방향을 골랐다. 방향이 정해지자 두 설계가 차례로 근거를 잃었다.

### A5.2 구멍 ② — 정원 이중 소비 (**남는다. 사용자가 수용했다**)

| 항목 | 내용 |
|------|------|
| 06이 제공하던 방어 | 불변식 **B11**: 세션이 교체되면 이전 세션의 과금 유발 요청을 401로 거부 → 2대 동시 사용 시 정원이 2배로 새는 것을 차단 |
| 전제가 사라지면 | 같은 계정으로 2대(또는 N대)에서 동시에 촬영·전송하면 **일일 정원이 N배 속도로 소진**된다 |
| **사용자 판단(문서에 근거로 명시할 것)** | "**QR 생성 횟수를 과금하므로 불필요하다고 판단**" — 정원은 판매한 사용량이고, N대가 나눠 쓰든 1대가 다 쓰든 **총 청구액은 같다.** 따라서 **과금 정확성 문제는 존재하지 않는다** |
| **남는 리스크 (정직하게 기록)** | ① **체감 손실**: "내가 안 썼는데 정원이 없다"는 문의가 발생할 수 있다(다른 부스가 썼기 때문). ② **원인 추적 불가**: 기기 식별자를 수집하지 않으므로 "어느 부스가 썼는지"를 답해줄 수 없다. ③ **정원 소진 시각 예측 불가**: 운영자가 하루 계획을 세우기 어렵다 |
| 완화책(차단이 아니라 가시성) | (a) 상단바에 **잔량 상시 노출**([03 §8](../billing/03-qr-daily-quota.md)) — 이미 설계돼 있다. (b) 계정별 **전송 이력**(시각 + 성공 여부)을 조회 가능하게 두면 ②를 부분 해소한다. 기기 식별자 없이도 "언제 몇 건" 은 답할 수 있다 → **[11]에 신규 미결정 D-13으로 등재**(§A7) |
| 유일하게 남은 하드 방어 | `02:239`의 **commit 트랜잭션 직렬화**. 이것이 정원 **초과**(음수·한도 넘김)를 막는 유일한 장치가 되었다 → R11이 그 사실을 문서에 못 박는다 |

### B3.2 파생값 — 키로 만들지 **않은** 것과 그 이유

| 후보 | 판정 | 이유 |
|------|:---:|------|
| `HasPin` | ❌ 키로 두지 않는다. `Pin`의 존재로 **파생** | 두 키가 모순될 수 있다(`HasPin=1` + `Pin` 없음 → 게이트가 서버 검증 분기로 가서 §B8 블로커가 되살아난다). 단일 소스 원칙 |
| `AuthMethod` | ❌ `Google` 고정 | 영향 범위가 라벨 2종(`"Google SSO"` / `"알 수 없음"`)뿐이고 역할 게이트와 무관하다. 키 표면을 늘릴 값이 없다 |
| `CreatedAt` | ❌ `DateTime.UtcNow` 고정 | 계정 관리 화면의 표시값일 뿐이고, 서버 판정(TempUser 시간 한도)은 서버가 한다 — 테스트 모드에는 서버가 없다 |

### B3.3 ini 작성 예시(문서·주석 샘플용)

```ini
[MCPhoto]
CutCount=0
CountdownSec=6
... (앱이 관리)

[Test]
TestMode=1
Id=testadmin
Email=test@email.com
Role=admin
Pin=1234
QrBlocked=0
QrBlockReason=count
```

> ⚠️ **주석은 보존되지 않는다**(B2-4). 앱이 ini를 다시 쓸 때 `;`/`#` 줄은 사라진다. 샘플과 설명은 **문서**(`analysis/12`)에 두고 ini에는 값만 적는다. 개행도 LF로 재작성된다(메모장에서 열려도 문제없다).

> ✅ **키 이름 대소문자는 무시된다**(`IniFile`이 `OrdinalIgnoreCase`) — 사용자 요구의 `email`/`role`(소문자)도 그대로 동작한다. 표에 `Email`/`Role`로 적었지만 **둘 다 유효**하다.

> ✅ **값도 대소문자를 무시한다(설계 결정).** `Role`·`QrBlockReason`은 **trim + `ToLowerInvariant()` 후** 5개(2개) 문자열과 대조한다. `ParseRole`은 대소문자를 구분하므로(`UserRole.cs:39-47`) 그대로 넘기면 `Role=Admin`이 조용히 `user`로 떨어진다 — 손으로 쓰는 설정 파일에서 그것은 함정이다. **명시 열거 규약은 유지된다**(비교 대상 목록이 여전히 5개 리터럴이며, 서수 부등식을 쓰지 않는다).
>
> 구현 규약: `TestModeOptions`가 `ToLowerInvariant()` 정규화 후 `UserRoleExtensions.ParseRole`에 넘기고, **`ParseRole`의 미지원값 폴백(`User`)에 의존하지 않는다** — 목록 밖인지를 먼저 스스로 판정해 Warning을 남기고 문서화된 기본값(`advanced_user`)을 쓴다. 최소권한 폴백(`User`)을 쓰지 않는 이유: 그 규약은 **서버가 준 값**을 해석할 때 권한 상승을 막는 것이고, 여기에는 서버가 없다. 대신 사용자가 의도한 것과 다른 역할이 조용히 서는 것을 막아야 하며, 그 안전망은 **배너에 실제 역할을 표시**하는 것이다(§B9).

## B4 ⚠️ 최대 함정 — `Save()`가 `[Test]` 섹션을 지운다

### B4.1 결함의 정확한 형태

```
IniSettingsService.Save()                       // :57-83
    var ini = new IniFile();                    // ← 빈 딕셔너리
    WriteFrom(settings, ini);                   // ← [MCPhoto] 키만 채운다
    File.WriteAllText(path, ini.ToString());    // ← 파일 전체 교체
```

| 사실 | 결과 |
|------|------|
| `new IniFile()`은 디스크의 다른 섹션을 **모른다** | `[Test]`가 출력에 포함되지 않는다 |
| `TryWrite`는 `File.WriteAllText`(append 아님) | 파일이 `[MCPhoto]` 하나만 남는다 |
| **`MainWindow.OnClosing`이 `Save()`를 무조건 호출**(VF-6) | 설정 화면을 열지 않아도 **앱을 한 번 닫으면 테스트 모드 설정이 사라진다** |
| 사용자 관점 | "테스트 모드로 잘 됐는데 다시 켜니 게스트다. ini를 열어보니 `[Test]`가 없다" — **원인 추적이 매우 어렵다** |

> ⚠️ **이 결함을 고치지 않으면 B부의 기능은 "한 번만 동작하는 기능"이다.** 회귀 테스트로 못 박는 것이 필수다.

### B4.2 해법 — 대상 파일의 **외래 섹션을 읽어 보존**한다

| 설계 | 내용 |
|------|------|
| 소유 경계 정의 | `[MCPhoto]` 섹션은 **`IniSettingsService`가 전적으로 소유**한다(현행 동작 유지 — 매핑되지 않은 키는 계속 사라진다). 그 밖의 **모든 섹션은 외래(foreign)** 이며 저장 시 원문 그대로 실어 보낸다 |
| 병합 시점 | **`Save()`가 아니라 `TryWrite(path, …)` 직전**, 즉 **쓰려는 그 경로의 현재 파일**을 읽어 외래 섹션을 채취한다 |
| 왜 `Load()` 시점의 스냅샷을 쓰지 않는가 | ① `Save()`는 **폴백 체인**으로 다른 경로에 쓸 수 있다(`FallbackPaths()`) — 그 경로의 파일에는 다른 외래 섹션이 있을 수 있다. ② 앱 실행 중 QA가 ini를 편집하는 것이 이 기능의 정상 사용 패턴이다. 스냅샷은 그 편집을 되돌린다 |
| 실패 처리 | 대상 파일 읽기 실패(없음·잠김·손상)는 **무시하고 계속 쓴다**. 외래 섹션 보존은 부가 기능이고, 설정 저장을 막을 이유가 못 된다(크래시 금지 원칙 승계) |
| 비용 | 저장 1회당 파일 읽기 1회(수 KB). 저장 빈도는 사용자 조작·앱 종료 수준 → 무시 가능 |

**`IniFile` 신규 API**

```csharp
/// <summary>이 딕셔너리가 갖지 않은 섹션을 source에서 그대로 가져온다(외래 섹션 보존).
/// 이미 존재하는 섹션(예: [MCPhoto])은 건드리지 않는다 — 소유자가 방금 채운 값이 정본이다.</summary>
public void AdoptMissingSections(IniFile source)
```

| 규칙 | 이유 |
|------|------|
| 이름이 `Merge`가 아니라 `AdoptMissingSections` | 방향과 범위를 이름이 말해야 한다. `Merge`는 "`[MCPhoto]` 키도 섞이나?"를 묻게 만든다 |
| 기본(무명) 섹션 `""`도 대상 | 파일 선두에 섹션 없이 적힌 줄도 보존한다(현행 파서가 그것을 `""` 섹션에 담는다) |
| **키 단위 병합은 하지 않는다** | `[MCPhoto]` 안의 미매핑 키를 되살리면 오탈자 키가 영구히 남고(`Cutcount=8` 같은 것), 폐기된 키(`HostingBaseUrl` 등)가 되살아난다. 섹션 단위가 정확한 경계다 |

**`Save()` 변경 후 형태**

```
var ini = new IniFile();
WriteFrom(settings, ini);                       // [MCPhoto] 소유 구간
foreach (var candidate in FallbackPaths())
{
    var merged = new IniFile();
    WriteFrom(settings, merged);
    merged.AdoptMissingSections(TryReadExisting(candidate));   // 이 경로의 외래 섹션
    if (TryWrite(candidate, merged.ToString())) { … return true; }
}
```

> ⚠️ **경로마다 다시 조립해야 한다.** 한 번 조립한 문자열을 폴백 경로에 재사용하면, 첫 후보의 외래 섹션이 두 번째 후보 파일에 **이식**된다(엉뚱한 위치의 `[Test]` 복제). 위 의사코드처럼 루프 안에서 조립한다.

> ✅ **왜 `[Test]` 전용 처리가 아니라 일반적 외래 섹션 보존인가**: `[Test]`만 특별 취급하면 다음 섹션(`[Branding]`·`[Diagnostics]` 등)이 추가될 때 같은 버그가 반복된다. 또 테스트 코드가 "임의 섹션"으로 검증할 수 있어 `[Test]`의 스키마 변경과 독립적이다.

### B4.3 회귀 테스트 (필수)

| # | 케이스 | 기대 |
|---|--------|------|
| **B-T1** | `[Test]` 있는 ini → `Load()` → `Save()` → 다시 읽기 | `[Test]`의 모든 키·값이 **그대로 존재** |
| **B-T2** | 앱을 켜지 않고 `Save()`만 2회 연속 | 2회 후에도 `[Test]` 보존(멱등) |
| **B-T3** | `[Test]` + `[Unknown]` + 선두 무명 섹션 줄 모두 있는 ini → 저장 | 3종 전부 보존 |
| **B-T4** | `[MCPhoto]`에 미매핑 키(`Bogus=1`)가 있는 ini → 저장 | `Bogus`는 **사라진다**(소유 경계가 의도대로 동작) |
| **B-T5** | `[Test]` 안에 `[MCPhoto]`와 같은 이름의 키(`CutCount=99`) | `[MCPhoto].CutCount`는 설정값, `[Test].CutCount`는 원문 보존 — 섞이지 않는다 |
| **B-T6** | 대상 경로에 파일이 없을 때 저장 | 예외 없이 `[MCPhoto]`만 기록 |
| **B-T7** | 대상 파일이 잠겨 읽기 실패(읽기 실패 주입) | 저장은 성공하고 외래 섹션만 유실 + Warning 로그. **크래시 없음** |
| **B-T8** | 폴백 승격 경로에 저장(1순위 쓰기 불가 주입) | 2순위 파일의 외래 섹션이 보존되고, **1순위 파일의 외래 섹션이 2순위로 복제되지 않는다** |

> B-T9는 `MainWindow`를 인스턴스화할 수 없으므로(headless Window 함정) **`OnClosing`이 호출하는 것과 같은 시퀀스**(`CaptureWindowBounds` 상당 + `Save()`)를 직접 호출해 검증한다. 창을 띄우는 테스트는 만들지 않는다.

### B5.2 `ITestModeService` 계약

```csharp
public interface ITestModeService
{
    /// <summary>[Test] TestMode가 참인가. 앱 수명 동안 불변(시작 시 1회 판정).</summary>
    bool IsEnabled { get; }

    /// <summary>검증·폴백이 끝난 옵션. IsEnabled=false여도 기본값 객체를 돌려준다(null 금지).</summary>
    TestModeOptions Options { get; }

    /// <summary>실제로 읽은 INI 절대 경로(진단·로그용). 파일이 없어도 경로는 돌려준다.</summary>
    string SourcePath { get; }

    /// <summary>테스트 계정 User를 1회 생성해 보관하고 같은 인스턴스를 돌려준다.
    /// IsEnabled=false면 null. 인스턴스 동일성이 IsTestUser의 판정 근거다.</summary>
    User? TestUser { get; }

    /// <summary>이 User가 테스트 계정 인스턴스인가(참조 동일성).</summary>
    bool IsTestUser(User? user);
}
```

| 설계 결정 | 근거 |
|-----------|------|
| **`IsTestUser`는 참조 동일성**(`ReferenceEquals`)으로 판정한다 | `User` 모델에 `IsTest` 같은 필드를 **추가하지 않기 위해서**다. 도메인 모델에 테스트 전용 플래그를 넣으면 그 값이 서버 DTO 매핑·직렬화·표시 코드로 번져 나간다. 또 참조 동일성은 **위조가 불가능**하다 — 테스트 모드가 켜진 상태에서 실제 Google SSO 로그인이 일어나도 그 `User`는 다른 인스턴스이므로 PIN 우회·QR 주입이 **적용되지 않는다**(§B8·§B10의 핵심 안전장치) |
| `IsEnabled`는 시작 시 1회 판정하고 불변 | 런타임에 ini를 편집해 권한이 바뀌는 앱은 만들지 않는다. 재시작이 정직하다 |
| `Options`가 `IsEnabled=false`에서도 non-null | 호출부에 null 분기를 늘리지 않는다(`AppSettings` 관례와 동형) |
| `SourcePath` 노출 | B2-14. QA가 "내가 편집한 ini가 그 ini인가"를 확인할 수 있어야 한다 |

### B5.3 부팅 배선 — 어디서 `Login()`하는가

**결정: `AppShellViewModel.Startup()`에서, `NavigateAsync(AppState.Home)` 직전.**

```
MainWindow ctor → DataContext = shell → Loaded → shell.Startup()
                                                    ├─ (신규) 테스트 모드면 _session.Login(testUser)
                                                    └─ NavigateAsync(Home)
```

| 후보 지점 | 판정 | 이유 |
|-----------|:---:|------|
| `App.OnStartup`(호스트 조립 직후, `MainWindow` 해결 **전**) | ❌ | `AppShellViewModel`이 아직 생성되지 않아 `CurrentUserChanged`를 **구독하지 않은 상태**다. `Login()`이 발행하는 통지가 유실되고, 그 통지가 하는 일 중 하나가 **TempUser QR 상태 조회 시작**(`AppShellViewModel.cs:183-184`)이다 → `QrBlocked=1`이 절대 반영되지 않는다 |
| `App.OnStartup`(`MainWindow` 해결 **후**, `Show()` 전) | △ 가능 | 셸이 구독을 마친 뒤이므로 동작한다. 그러나 `App.xaml.cs`에 순서 의존(“이 두 줄의 순서를 바꾸면 조용히 깨진다”)을 새로 심는다 |
| **`AppShellViewModel.Startup()`** | ✅ **채택** | ① 셸 자신이 이미 구독을 마친 상태다(ctor에서 구독). ② `Startup()`은 이미 "앱이 시작된다"의 단일 이음새다. ③ `App.xaml.cs` 무변경. ④ 홈 화면 진입 **전**이므로 `HomeViewModel.OnEnterAsync`가 처음부터 로그인 상태를 본다(`HomeViewModel.cs:31`의 안내 문구가 역할에 맞게 나온다) |
| `MainWindow.Loaded` 핸들러 | ❌ | 코드비하인드에 상태 로직을 넣는다. MVVM 규약 위반 |

**주입 방식**: `AppShellViewModel` 생성자의 **마지막 선택 파라미터**로 `ITestModeService? testMode = null`을 추가한다(`UserMgmtViewModel`의 `IFrameRepository? frames = null` 선례). 기존 위치 인수 호출부(테스트 다수)가 그대로 컴파일된다.

```csharp
public void Startup()
{
    if (_testMode?.TestUser is { } u)
    {
        _logger?.LogWarning("테스트 모드 로그인: id={Id} role={Role} ini={Path}",
            u.Id, u.Role.ToFirestoreValue(), _testMode.SourcePath);
        _session.Login(u);
    }
    _ = NavigateAsync(AppState.Home);
}
```

| 규칙 | 이유 |
|------|------|
| 로그 레벨은 **Warning** | Information으로 두면 평시 로그에 묻힌다. "이 실행은 인증을 우회했다"는 사실은 사후 조사에서 **눈에 띄어야** 한다 |
| `Login()`을 `NavigateAsync` **앞**에 | 홈 화면 VM이 처음부터 올바른 역할을 본다. 뒤에 두면 홈 진입 후 통지로 갱신되며, 그 사이 한 프레임 동안 게스트 UI가 보인다 |
| `BackendSession`은 건드리지 않는다 | 토큰을 만들지 않는다는 방침의 구현. `BackendSessionSynchronizer`는 로그인 전이에서 아무 것도 하지 않으므로(`:44-48`) 배선 변경 불요 |

### B5.4 INI 경로 가시화 (B2-14 대응)

| 문제 | QA가 편집한 ini가 앱이 읽는 ini가 아닐 수 있다. 활성 경로를 **앱이 어디에도 표시하지 않는다** |
|------|------|
| 조치 1 | `ISettingsService`에 `string IniPath { get; }` **추가**. `IniSettingsService`는 이미 같은 이름의 프로퍼티를 갖고 있어(`:29`) 구현은 0줄 |
| 비용 | 테스트의 `ISettingsService` 스텁 **5곳**(`AccountViewModelTempUserTests`·`AccountViewModelPinTests`·`DiagnosticsViewModelTests`·`Http/BackendSessionLogoutTests`·`SettingsViewModelTests`)에 1줄씩 추가 |
| 왜 별 경로 해석을 만들지 않는가 | `TestModeService`가 자체적으로 `SettingsPathResolver`를 다시 돌리면 **두 개의 독립적인 경로 판정**이 생긴다. `ResolveWritable`은 "쓰기 가능한 첫 후보"이므로 환경에 따라 두 판정이 갈릴 수 있고, 그 순간 "테스트 모드가 안 켜진다"의 원인이 미궁이 된다 |
| 조치 2 | 진단·상태 모달에 `설정 파일` 행 1개 추가(읽기 전용 TextBox — 로그 폴더 경로와 동일 관례). ⚠️ 이 행은 테스트 모드와 무관하게 **평시에도 유용**하다(설정이 안 먹는 문의의 1번 원인) |
| 조치 3 | `TestModeService`가 시작 시 1회 로그: 켜짐이면 Warning(위 §B5.3), **꺼짐인데 `[Test]` 섹션이 있으면** Information(`"테스트 모드 OFF([Test] 발견, TestMode={값}) ini={path}"`) → "분명히 썼는데 안 된다"에 즉답 가능 |

## B7 토큰 없는 서버 의존 지점 — 전수 조사와 판정

### B7.2 지목 컴포넌트 심화 판정 — 크래시 / 조용한 실패 / 사람 말 안내

분류 기준을 먼저 고정한다. 커밋 `d31c12c`("서버 실패 안내를 사람 말로 — 오프라인·미설정·토큰만료 구분")가 확립한 관례를 그대로 쓴다: **원인 판정은 예외 타입으로**(문자열 분기 금지), 문구는 **①무엇이 안 됐는지 ②왜 ③무엇을 하면 되는지** + 오해 방지 사실.

## B8 PIN 게이트 — 이 요구의 유일한 블로커

### B8.1 왜 블로커인가


| 결과 | 파급 |
|------|------|
| 설정 화면 진입 **불가** | 테스트 모드의 핵심 검증 대상(역할별 설정 편집 권한)에 도달할 수 없다 |

| 어느 `HasPin` 값도 탈출로가 아니다 | `false`로 두면 Setup 분기가 서버를 호출한다 — 양쪽 다 막힌다 |

> ⚠️ **이것을 설계하지 않으면 B부는 "역할 배지만 바뀌는 기능"이 된다.** 게이트를 공유하는 계정 관리 화면(`AccountViewModel.cs:112`)까지 막히므로, **admin/manager 역할 테스트의 핵심 화면인 사용자 관리에 도달할 방법이 없다**(사용자 관리는 계정 관리 → 관리자 도구를 거친다).

### B8.2 세 가지 안 비교

| **②로컬 검증으로 대체(고정 PIN)** | 테스트 계정이면 `0000` 같은 하드코딩 값과 로컬 대조 | 게이트 UI를 테스트할 수 있다 | ⚠️ 하드코딩 값이 **문서·코드 두 곳**에 살고 어긋난다. QA가 값을 모르면 **자기 발로 잠긴다**(우회보다 나쁜 상태) | ❌ |

|---|---|
| **`PromptSetup` 분기를 영구히 봉인한다** | 브리프 지적대로 `HasPin=false`가 더 나쁘다(존재하지 않는 계정에 **쓰기** 시도). ③은 `Pin` 존재 = `HasPin`이므로 **Setup 분기에 도달하는 경로가 없다**. 상태 조합으로 막는 것이 아니라 **파생 관계로 표현 불가능하게** 만드는 것이 요점이다 |

| 실패 상한을 그대로 쓴다 | 로컬 대조도 `PinPromptWindow`를 통과하므로 5회 실패 시 창이 닫히고 게이트는 열리지 않는다. **테스트 모드가 fail-closed 규약의 예외를 만들지 않는다** |

### B8.3 판정 단일 지점 — 우회가 실계정 경로로 새지 않는 보장

우회 코드가 실제 계정에 적용되면 그것은 **인증 우회 취약점**이다. 아래 4중으로 봉인한다.

| # | 봉인 | 내용 |
|---|------|------|
| **S1** | **판정 함수 단 하나** | 테스트 분기 조건은 `ITestModeService.IsTestUser(User? user)` **한 개**뿐이다. `IsEnabled`만 보고 분기하는 코드를 **금지**한다(불변식 TM3, §B10.3) — `IsEnabled`는 "ini가 켜져 있다"이고 `IsTestUser`는 "이 객체가 그 가짜 계정이다"라는 다른 명제다 |
| **S2** | **참조 동일성**(`ReferenceEquals`) | `IsTestUser`는 값 비교가 **아니다.** `TestModeService`가 1회 생성해 보관한 그 인스턴스와 같은지만 본다. 따라서 실제 Google SSO 로그인이 만든 `User`는 — **이메일·Id·역할이 우연히 전부 같아도** — 판정이 false다. 위조 불가 |
| **S3** | **분기의 입력이 게이트 대상 자신** | `EnsurePinGateAsync(User user)`가 받는 `user`는 `_session.CurrentUser`(설정 진입) 또는 계정 화면이 읽은 같은 객체다. 즉 **판정 대상과 검사 대상이 같은 객체**이므로 "다른 계정을 검사해 통과시키는" 혼동이 성립하지 않는다 |
| **S4** | **테스트로 고정** | B-T19: 테스트 모드 ON + **다른 `User` 인스턴스**로 로그인 → `EnsurePinGateAsync`가 `IAccountService.VerifyPinAsync`를 호출한다(=서버 경로를 탄다). 이 테스트가 깨지면 우회가 샜다는 뜻이다 |

```csharp
// 봉인된 형태 — 조건이 이 한 줄 외에 존재하지 않는다.
if (_testMode?.IsTestUser(user) == true) { … 테스트 경로 … }
// ⚠️ 금지: if (_testMode?.IsEnabled == true) { … }   ← 실계정에도 적용된다
```

| 잔여 위험 | 판정 |
|-----------|------|
| ini를 쓸 수 있는 사람이 `TestMode=1 Role=admin`으로 **설정 화면에 무인증 진입** | ⚠️ 존재한다. 단 **PIN 게이트는 원래 게스트에게 없다**(VF-12: 게스트는 무가드로 설정 진입) → 테스트 모드가 새로 뚫는 것은 "로그인 상태에서의 PIN"이며, 그 상태 자체가 ini로 만들어진 가짜다. **서버 권한은 0**(§B10.2) |
| 우회가 다른 게이트로 전파 | ❌ 불가. `EnsurePinGateAsync`가 **PIN 게이트의 유일한 구현**이고(호출부 2곳 모두 이 메서드를 지난다), 역할 게이트는 PIN과 무관하게 `Role`만 본다 |

### B8.4 해법

`EnsurePinGateAsync` 선두에 **테스트 계정 분기**를 둔다.

```csharp
public Task<bool> EnsurePinGateAsync(User user)
{
    // 테스트 계정 전용 경로: 서버를 호출하지 않는다.
    if (_testMode?.IsTestUser(user) == true)
    {
        var pin = _testMode.Options.Pin;
        if (pin is null) return Task.FromResult(true);              // 게이트 생략
        var dlg = _services.GetService<IPinPromptDialogService>();
        if (dlg is null) return Task.FromResult(false);             // fail-closed 규약 승계
        return Task.FromResult(dlg.PromptVerify(p =>
            Task.FromResult(string.Equals(p, pin, StringComparison.Ordinal))));  // 로컬 대조
    }
    … 기존 경로 …
}
```

| 결정 | 근거 |
|------|------|
| `Pin` 미설정 → **게이트 생략**(true) | 기본 사용 흐름을 막지 않는다. 테스트 모드의 목적은 "빠르게 역할 UI를 본다"이다 |
| `Pin` 설정 → **게이트를 띄우고 로컬 대조** | PIN 게이트 **UI 자체**(입력 형식 검증·5회 실패 자동 닫힘·1.5초 쿨다운)를 서버 없이 검증할 수 있다. it14/it15가 설계한 rate-limit 동작이 테스트 가능해진다 |
| **Setup 분기를 쓰지 않는다** | 테스트 모드에는 저장할 서버가 없다. `Pin`이 있으면 항상 Verify, 없으면 게이트 없음 — `HasPin` 파생값(§B3.2)과 정확히 일치한다 |
| `IsTestUser`(참조 동일성) 가드 | 테스트 모드가 켜진 상태에서 **실제 SSO 로그인**이 일어나면 그 계정은 **정상 PIN 게이트**를 통과해야 한다. 참조 비교가 그것을 보장한다 |
| 다이얼로그 서비스 미등록 시 `false` | 기존 fail-closed 규약(`:456`)을 그대로 승계 — 테스트 모드가 규약의 예외를 만들지 않는다 |
| 5회 실패 시 | `PinPromptWindow`가 창을 닫고 `false` → 설정 진입 거부. 정상 동작이며 ini의 `Pin`을 확인하면 된다 |

| 조작 | 동작 | 근거·판정 |
|------|------|-----------|
| 계정 팝오버 [로그아웃] | **정상 동작한다.** `SessionContext.Logout()` → `CurrentUser=null` → 게스트 UI + 홈 복귀 | 로그아웃을 막거나 즉시 재로그인시키면 "로그아웃 버튼이 고장난 앱"이 된다. 게스트 상태도 테스트 대상이다 |
| 로그아웃 후 배너 | **유지된다**(문구만 바뀜, §B9) | 테스트 모드는 **설정 상태**이지 세션 상태가 아니다. ini가 그대로 있는 한 위험도 그대로다 |
| 다시 테스트 계정으로 | 로그인 화면(상단바 계정 버튼)에 **[테스트 계정으로 로그인]** 버튼을 테스트 모드에서만 노출 | 유일한 대안은 앱 재시작인데, 역할별 UI를 비교하는 QA 작업에서 매번 재시작은 실용성을 해친다 |
| 그 버튼의 규격 | 라벨 `테스트 계정으로 로그인 ({역할 라벨})`, `Button.Secondary`, `Visibility={Binding IsTestMode…}`. 커맨드는 `_session.Login(_testMode.TestUser)` + `ReturnFromOverlay()` — **`LoginWithGoogle`과 같은 후처리** | 같은 `User` 인스턴스를 다시 태우므로 `IsTestUser`가 계속 참이다(PIN·QR 주입 유지) |
| 실제 Google SSO 로그인 | 테스트 모드에서도 **정상 시도된다**(막지 않는다) | 성공하면 실제 계정이 세션에 들어가고 토큰이 발급되어 **모든 서버 기능이 정상 동작**한다. 이때 `IsTestUser=false`이므로 PIN·QR 주입이 자동으로 비활성된다 → **"테스트 모드 ini를 켜 둔 채 실계정으로 일할 수 있다"**(단 배너는 계속 뜬다) |
| 유휴 타임아웃 | 로그아웃하지 않는다(it8 A1 불변) | 테스트 모드가 이 규약을 바꾸지 않는다 |

> ✅ **`IsTestUser`의 참조 동일성 한 줄이 3개 질문(로그아웃·실계정 병행·PIN 우회 범위)을 동시에 닫는다.** 모델에 플래그를 넣는 대안으로는 얻을 수 없는 성질이다(플래그는 실계정 `User`에도 실릴 수 있다).

## B9 경고 배너 UI 명세

### B9.1 배치 — `MainWindow` 루트에 행을 추가한다

| 후보 | 판정 | 이유 |
|------|:---:|------|
| 상단바(`TopBar`) 안 | ❌ | **촬영·QR 화면에서 숨겨진다**(B2-13). 배너가 사라지는 순간이 있으면 "지울 수 없는 배너"가 아니다 |
| 루트 Grid에 겹쳐 배치(`VerticalAlignment=Top`) | ❌ | 상단 72px는 브랜드 칩·설정 기어가 차지한다. 겹치면 버튼을 가리거나 배너가 가려진다 |
| **루트 Grid에 행 추가**(row 0 = 배너, row 1 = 나머지 전부) | ✅ **채택** | 겹침이 원리적으로 불가능하고, 배너가 항상 보인다. 화면들은 32px 짧아질 뿐이며 각 View는 자기 높이를 `*`로 채우므로 코드 변경이 없다 |
| 별 `Window`(항상 위) | ❌ | 전체화면 키오스크에서 포커스·z-order 문제를 만든다 |

**구현 형태**

```xml
<Grid x:Name="RootGrid">
    <Grid.RowDefinitions>
        <RowDefinition Height="Auto" />   <!-- 테스트 모드 배너(꺼짐이면 Collapsed → 0px) -->
        <RowDefinition Height="*" />
    </Grid.RowDefinitions>

    <Border Grid.Row="0" … Visibility="{Binding IsTestMode, Converter={StaticResource BoolToVis}}">…</Border>

    <!-- 기존 자식 전부에 Grid.Row="1" 부여: ContentControl · TopBar · 버전 표기 · 토스트 · 유휴 오버레이 -->
</Grid>
```

| 규칙 | 이유 |
|------|------|
| 배너가 꺼지면 `Collapsed` + `Height="Auto"` | 테스트 모드 OFF에서 레이아웃이 **현행과 픽셀 단위로 동일**하다 |
| 유휴 경고 오버레이는 row 1에 둔다 | 스크림이 배너를 덮지 않는다 → 유휴 경고 중에도 배너가 보인다 |
| 기존 자식 5개에 `Grid.Row="1"` 누락 금지 | 누락하면 그 요소가 row 0에서 배너와 겹친다. **UV-4 검증 항목** |

## B10 보안 — 무엇이 뚫리고 무엇이 뚫리지 않는가

### B10.1 사실 진술 (완화하지 않는다)

> **배포된 exe에, 텍스트 파일 한 줄로 인증 없이 `admin` 역할 UI에 도달하는 경로가 존재한다.** 이것은 부작용이 아니라 §B1.2에서 **의도적으로 선택한** 트레이드오프다.

**공격 표면**

| 항목 | 내용 |
|------|------|
| 필요 권한 | 활성 INI 파일에 대한 **쓰기 권한** |
| 활성 INI 위치 | 실행경로 → `%ProgramData%\MCPhoto\` → `%LocalAppData%\MCPhoto\` 중 **쓰기 가능한 첫 곳**(B2-14) |
| ⚠️ 현실적 난이도 | **낮다.** Program Files 설치본이라도 폴백으로 `%ProgramData%\MCPhoto\MCPhoto.ini`가 쓰이며, 그 파일은 앱(=대화형 사용자)이 만들었으므로 **그 사용자가 자유롭게 수정할 수 있다.** 즉 **키오스크 PC를 만질 수 있는 사람은 누구나** 테스트 모드를 켤 수 있다 |
| 필요 조건 추가 | 없다. 재부팅·관리자 권한·네트워크 불요. 앱 재시작만 필요 |

### B10.2 위험 범위 — 정확히 규정한다

| 영역 | 뚫리는가 | 근거 |
|------|:---:|------|
| 역할별 **UI 노출**(관리자 도구 메뉴·프레임 생성·삭제 버튼) | ✅ 뚫린다 | 게이트가 `CurrentUser.Role`만 본다 |
| **로컬 설정 편집·저장**(거울모드·필터·QR 토글·URL·버킷·로컬 저장 경로) | ✅ 뚫린다 | 게스트 편집 제한이 해제된다. **이 PC의 동작이 바뀐다** |
| 설정 진입 PIN 게이트 | ✅ 뚫린다(§B8: `Pin` 미설정이면 생략) | ⚠️ 단 **PIN 게이트는 원래 게스트에게 없다**(VF-12) — 게스트도 무가드로 설정에 들어간다. 즉 **이 항목은 테스트 모드가 새로 뚫는 것이 아니다** |
| 로컬 개인 프레임 **열람** | ⚠️ 부분 | `[Test] Email`을 남의 이메일로 적으면 그 이메일 폴더를 열려 시도한다. **그러나 `.slots` 서명 검증 + `#owner` 일치**를 통과해야 하고(`LocalFrameStore.LoadUser`), 서명 키는 앱에 내장돼 있어 **같은 PC의 같은 앱이면 통과한다** → **같은 PC에 남은 타 계정 로컬 프레임은 열람될 수 있다**. 원격·타 PC 데이터는 불가 |
| **서버 데이터 조회**(계정 목록·이메일·역할) | ❌ 불가 | 토큰이 없다. `bearer:true`가 HTTP 전에 차단(VF-9) |
| **서버 데이터 변경**(역할 변경·계정 삭제·PIN 재설정·전역 한도) | ❌ 불가 | 동상 |
| **프레임 서버 등록·삭제** | ❌ 불가 | 동상 |
| **과금·정원 소비** | ⚠️ 게스트 수준만 | 업로드는 선택적 Bearer라 **게스트로 성공**한다(VF-10). 즉 테스트 모드는 계정 정원을 소비하지 못하고, **게스트가 원래 할 수 있는 것만** 한다 |
| 다른 사용자의 계정·데이터 | ❌ 불가 | 서버 권위가 전부 토큰에 걸려 있다 |

> ✅ **핵심 규정**: 테스트 모드는 **로컬 UI와 로컬 설정의 권한 경계만** 무너뜨린다. 서버는 조금도 뚫리지 않으며, 그 이유는 단 하나 — **JWT를 만들지 않기 때문**이다(§B3.2가 가짜 토큰 키를 거부한 이유). 이 성질은 우연이 아니라 설계상 유지해야 하는 **불변식**이다.

### B10.3 불변식 (위반하면 이 절의 결론이 무효)

| # | 불변식 | 위반 예시 |
|---|--------|-----------|
| **TM1** | 테스트 모드는 `IBackendSession`에 **토큰을 넣지 않는다** | 가짜 JWT 생성, 서버 개발용 토큰 하드코딩 |

## C1 요구와 법적 제약

### C1.1 요구 원문

> "오픈소스 라이선스 전문을 파일로 관리하되, 진단 상태에 들어가서 열지 않고, 설정 내 고급 탭 내부에 오픈소스 라이선스 탭을 만들고 모든 계정이 접근 가능하도록 할 것. 그리고 라이선스 내용을 폴더를 열거나 경로를 적어주지 말고, 직접 해당 파일을 열어서 안에 있는 내용을 그대로 노출해줄것. 로그인 여부와 관계없이 무조건 보여줘야 하는 내용임."

### C1.2 법적 제약 — 이 변경은 의무를 **강화**한다(약화 금지 확인)

`docs/design/wpf-ffmpeg-licensing-and-distribution-design.md §2.4`의 의무 대조:

### C3.1 채택안 ③의 구체 형태

```
SettingsView.xaml (루트 Grid: row0=ScrollViewer, row1=sticky bar)
├─ row 0: 설정 본문 … 고급 그룹에 [오픈소스 라이선스] 버튼 추가
├─ row 1: sticky 저장/닫기 바
├─ (기존) 저장 토스트  Grid.RowSpan=2
└─ (신규) 라이선스 오버레이  Grid.RowSpan=2   ← 저장 바까지 덮는다
     Background = Brush.Scrim
     └─ Border Style=Card, Background=Brush.Bg, MaxWidth=1000, Margin=40
          ├─ 헤더: "오픈소스 라이선스" + [닫기]
          ├─ 안내 1줄(FFmpeg=GPLv3 / 본체=MIT)
          ├─ 파일 선택 ListBox(좌, 폭 260 고정) │ 본문 TextBox(우, *)
          └─ (실패 시) 경고 Border
```

| 규칙 | 이유 |
|------|------|
| `Grid.RowSpan="2"` | 저장/닫기 sticky 바를 덮어야 모달이 된다. 기존 토스트가 같은 기법을 쓴다(`:460`) |
| `Brush.Scrim` + **불투명 `Card`(`Brush.Bg`) + 기본 글자색** | C2-9 관례. 흰 배경 화면에서 `Brush.OnAccent`(흰 글자)를 쓰면 읽히지 않는다 |
| 좌측 목록 폭 **260 고정** | ⚠️ 리포에 "고정폭 컬럼 잘림" 이력이 있다 → 파일명이 길면 `TextTrimming="CharacterEllipsis"` + `ToolTip`에 전체 이름. 폭을 `Auto`로 두면 `MCPhoto-LICENSE-MIT.txt`가 본문 영역을 잡아먹는다 |
| 오버레이 열림 중 설정 편집 차단 | scrim이 히트테스트를 흡수하므로 자동. 별도 `IsEnabled` 배선 불요 |
| **신규 리소스 키 0개** | `Brush.Scrim`·`Card`·`Brush.Bg`·`Text.*`·`Button.Ghost`·`Radius.*`·`Brush.Warning*` 전부 기존 → 병합 딕셔너리 교차 참조 함정 회피 |
| 버튼 위치 | 고급 그룹 안, **[진단·상태] 버튼 위**. 이유: 진단은 로그인 전용이고 라이선스는 전원 접근이므로, 접근 범위가 넓은 항목을 먼저 둔다 |
| 버튼 라벨 | `오픈소스 라이선스` · `Button.Secondary` · `IsEnabled` **바인딩 없음**(항상 활성 — §C4) |

### C4.2 ⚠️ TestMode 하에서의 도달성 — **수락 기준에 포함한다**

TestMode(B부)가 켜지면 `SessionContext.CurrentUser`가 non-null이 되므로 설정 진입이 **게스트 무가드 경로에서 PIN 게이트 경로로 바뀐다.** 즉 C의 접근 경로가 B의 상태에 따라 달라진다 — 이것을 우연에 맡기지 않고 **수락 기준으로 못 박는다.**

| 상태 | 설정 진입 | 라이선스 뷰어 도달 | 근거 |
|------|-----------|:---:|------|
| 게스트(TestMode OFF) | 무가드 | ✅ | VF-12 |
| 실제 계정 로그인 | PIN 통과 필요 | ✅ | 정상 자격 |
| **TestMode ON · `[Test] Pin` 없음** | **게이트 생략** | ✅ | §B8.4 — 테스트 계정 분기가 `true` |
| **TestMode ON · `[Test] Pin=1234`** | 게이트 표시 → **로컬 대조** | ✅ | §B8.4 — 서버를 호출하지 않는다 |
| TestMode ON · 그 상태에서 로그아웃 | 무가드(게스트가 된다) | ✅ | §B8.5 |
| TestMode ON · 실제 SSO 로그인 병행 | 정상 PIN 게이트 | ✅ | `IsTestUser=false` → 실경로 |

| 수락 기준(C부) | 내용 |
|----------------|------|
| **AC-C1** | 위 6개 상태 **전부**에서 [오픈소스 라이선스] 버튼이 활성이고 오버레이가 열리며 본문이 표시된다 |
| **AC-C2** | 라이선스 뷰어 코드에 **계정·역할·테스트 모드 참조가 0개**다 — 도달성은 전부 **상위 진입 게이트**가 결정하고, 뷰어 자신은 어떤 상태에서도 같게 동작한다(§C7.2 규칙) |

## C5 파일 목록 · 본문 렌더링 설계

### C5.1 파일 목록 — 하드코딩하지 않고 열거한다

| 항목 | 설계 | 근거 |
|------|------|------|
| 방식 | **폴더 열거**(하드코딩 금지) | ① 파일 구성이 이미 4개로 늘었고(MIT는 빌드 시 생성) 앞으로도 변한다(LGPL 전환 시 `FFmpeg-COPYING.LGPLv2.1.txt` 추가 등). ② csproj가 `**\*.*`를 복사하므로 **소스 폴더에 파일을 넣으면 배포된다** — UI가 하드코딩이면 새 고지가 조용히 안 보인다(= 법적 고지 누락) |
| 검색 패턴 | `*.txt` **재귀**(`SearchOption.AllDirectories`) | csproj가 `%(RecursiveDir)`을 보존하므로 하위 폴더가 성립한다(C2-3) |
| 확장자 제한 | `.txt`만 | 폴더에 실수로 들어간 바이너리(PNG·zip)를 텍스트로 읽어 깨진 문자를 보여주는 것을 막는다. ⚠️ **비-txt 고지 파일이 생기면 이 목록을 넓혀야 한다** → 배포 체크리스트 항목(§C9) |
| 표시 이름 | **파일명 그대로**(하위 폴더는 `하위폴더/파일명.txt`) | `README.txt`가 다른 파일을 **파일명으로 상호 참조**한다("전문은 FFmpeg-COPYING.GPLv3.txt에 있습니다"). 친절한 별칭을 붙이면 그 상호 참조가 목록과 어긋난다 |
| 정렬 | ① `README.txt`(색인, **→ it24에서 `NOTICE.txt`로 개명**) **최상단 고정** ② 나머지는 파일명 `OrdinalIgnoreCase` 오름차순 | 색인을 먼저 읽게 하는 것이 그 파일을 만든 의도다. 나머지를 이름순으로 두면 `FFmpeg-*` 2개가 인접한다. ※ it24에서 색인의 UI 역할은 요약 카드가 가져갔고, 이 목록은 강등·미참조 문서 전용이 됐다 |
| 초기 선택 | 목록 첫 항목(=`README.txt`) 자동 선택 + 본문 즉시 표시 | 열자마자 빈 화면을 보여주지 않는다 |
| 크기 상한 | 파일당 **2 MB** | 현행 최대 35 KB. 2 MB는 오작동·오배치 방어선이며 정상 파일을 절대 막지 않는다 |
| 개수 상한 | **없다** | 고지 파일을 임의로 잘라내지 않는다. 목록이 길어지면 스크롤될 뿐이다 |

### C5.2 읽기 — 인코딩·개행

| 항목 | 설계 | 근거 |
|------|------|------|
| 인코딩 | `new StreamReader(path, Encoding.UTF8, detectEncodingFromByteOrderMarks: true)` | 현행 파일은 BOM 없는 UTF-8(VF-14). BOM 감지를 켜면 향후 BOM 있는 파일도 정상 처리된다 |
| BOM 문자 제거 | 읽은 문자열 선두의 `﻿`를 **1회 제거** | BOM 감지가 실패하는 경계(예: UTF-8 BOM을 ANSI로 오판)에서 화면 첫 글자로 보이는 것을 막는다 |
| CP949(ANSI) 파일 | ⚠️ **깨진다.** 방어하지 않는다 | 인코딩 자동 추측은 오판을 만들고, 동봉 파일은 우리가 관리한다. 대신 **테스트로 고정**: 배포되는 4파일이 모두 UTF-8로 읽혀 한글이 온전한지 검증(`README.txt`의 `"오픈소스 라이선스"` 문자열 포함 확인) |
| 개행 | **변환하지 않는다.** CRLF 원문 그대로 `TextBox`에 넣는다 | "안에 있는 내용을 그대로 노출"이라는 요구. WPF `TextBox`는 CRLF/LF 모두 정상 렌더한다 |
| 탭·정렬 문자 | 그대로. `TextBox`는 탭을 렌더한다 | GPLv3 전문은 공백 정렬이라 문제없다 |
| 읽기 시점 | **선택할 때마다 읽는다**(캐시하지 않는다) | 최대 35 KB·674줄 = 수 ms. 캐시하면 파일 교체를 반영하지 못하고 메모리에 상주한다. ⚠️ 단 **UI 스레드에서 동기 읽기**는 하지 않는다 → 아래 |
| 스레드 | `await Task.Run(() => 읽기)` 후 UI 스레드에서 대입 | 파일이 네트워크 드라이브·느린 디스크에 있을 수 있다. 리포 규약(로컬 I/O는 `Task.Run`)과 정합. 읽는 동안 본문에 `불러오는 중…` |

### C5.3 본문 표시 컨트롤

| 항목 | 값 | 근거 |
|------|-----|------|
| 컨트롤 | `TextBox` (`IsReadOnly="True"`, `IsReadOnlyCaretVisible="True"`, `AcceptsReturn="True"`) | **선택·복사가 가능해야** 한다(GPLv3 전문을 인용할 상황). `TextBlock`은 선택이 안 된다. `AcceptsReturn`이 없으면 여러 줄이 표시되지 않는다 |
| 스크롤 | `VerticalScrollBarVisibility="Auto"` · `HorizontalScrollBarVisibility="Auto"` | **`ScrollViewer`로 감싸지 않는다** — 감싸면 `TextBox`가 무한 높이를 요구해 자체 스크롤이 죽는다 |
| 줄바꿈 | `TextWrapping="NoWrap"` | 원문이 이미 ~70열로 정렬돼 있다. `Wrap`을 걸면 창 폭에 따라 문단이 재배치되어 **"그대로"가 깨진다**. 대신 수평 스크롤을 제공 |
| 폰트 | `FontFamily="Consolas, D2Coding, Malgun Gothic"` · `FontSize="13"` | 등폭이 원문 정렬(`====` 구분선·들여쓰기)을 보존한다. Consolas에 한글 글리프가 없어 한글은 `Malgun Gothic`으로 폴백된다(폭이 달라지지만 ASCII 정렬은 유지된다) |
| 테두리·배경 | `Brush.Surface.Alt` 배경 + `Brush.Divider` 1px | 본문 영역임을 시각적으로 구분 |
| 성능 | 35 KB / 674줄은 WPF `TextBox`에 부담이 아니다(UV-2로 실측 확인) | ⚠️ 만약 체감 지연이 있으면 대안은 `TextBlock`+가상화가 아니라 **`TextBox`에 `MaxLines` 없는 그대로 두고 `Padding` 축소** — 지연 원인은 대개 `TextWrapping="Wrap"`의 재측정이며 여기서는 `NoWrap`이다 |
| 하단 | 선택 파일명 + 크기(예: `FFmpeg-COPYING.GPLv3.txt · 34.3 KB`) | 전문 여부를 사용자가 가늠할 수 있다 |

## C7 서비스 재설계 — `LicenseFolderService`의 운명

### C7.1 판정

사용자 요구가 두 가지를 동시에 없앤다: "**폴더를 열거나 경로를 적어주지 말고**". 즉 현행 서비스의 두 기능(경로 표시·탐색기 열기)이 **모두 UI에서 사라진다.**

| 안 | 내용 | 판정 |
|----|------|:---:|
| ① `ILicenseFolderService`를 그대로 두고 별도 `ILicenseTextReader` 추가 | 이름이 남지만 `OpenLicenseFolder`는 호출자 0 | ❌ 서비스 2개 + 죽은 메서드 |
| ② `ILicenseFolderService`에 열거·읽기 API를 덧붙임 | 이름("Folder")이 실체와 어긋난다 | ❌ |
| **③ `ILicenseNoticeService`로 대체**(경로·존재·열거·읽기). `OpenLicenseFolder` **삭제** | 이름·책임 일치. 서비스 1개 | ✅ **채택** |

**계약**

```csharp
public sealed record LicenseDocument(string DisplayName, string FullPath, long SizeBytes);

/// 읽기 결과 — 예외를 UI로 전파하지 않는 판별 결과값.
public sealed record LicenseTextResult(string? Text, string? ErrorMessage)
{
    public bool IsSuccess => Text is not null;
}

public interface ILicenseNoticeService
{
    /// 고지 폴더 절대 경로(로그·진단용. UI에 표시하지 않는다).
    string FolderPath { get; }

    /// 폴더 실재 여부(배포 누락 진단).
    bool Exists { get; }

    /// 고지 문서 열거(정렬 규약 적용). 폴더 없음·열거 실패는 빈 목록.
    IReadOnlyList<LicenseDocument> ListDocuments();

    /// 문서 본문 읽기. 실패는 예외가 아니라 ErrorMessage로 돌려준다(§C6).
    LicenseTextResult ReadText(LicenseDocument document);
}
```

| 결정 | 근거 |
|------|------|
| `ReadText`가 **예외를 던지지 않는다** | 웹 클라이언트 규약("어댑터는 예외를 전파하지 않는다")과 동형. VM이 6종 catch를 갖는 대신 문구를 그대로 바인딩한다 |
| `FolderPath`를 **남긴다**(삭제하지 않음) | UI에는 안 쓰지만 **로그**에 필요하다("어디를 찾았는데 없었다"를 로그가 말해야 한다). 진단 화면에도 노출하지 않는다(요구) |
| `OpenLicenseFolder` **삭제** | 호출자가 0이 된다. 남겨 두면 "폴더로 안내한다"는 폐기된 UX가 코드에 살아 있어 다음 사람이 되살린다. ⚠️ 이 삭제는 `LicenseComplianceTests`의 `Service_Opens_When_Folder_Exists` 1건 제거를 수반한다 → §C8.2 |
| 동기 API(비-async) | 파일 I/O는 수 ms이고, **호출자(VM)가 `Task.Run`으로 감싼다**(§C5.2). 서비스에 async를 넣으면 순수 파일 조작 테스트가 async로 오염된다. `LogFolderService`·`LicenseFolderService` 선례와 동형 |
| `baseDirectory` 주입 유지 | 현행 테스트 3건이 임시 폴더로 검증하는 이음새다. **반드시 보존** |

## C8 진단 모달의 처리

### C8.1 "이동"의 범위

사용자: "**진단 상태에 들어가서 열지 않고**" → 진단 카드의 **진입 기능은 제거**한다. 그러나 진단 화면은 "배포 사고를 현장에서 잡는 마지막 그물"(설계 §10.3)이기도 하다.

| 안 | 내용 | 판정 |
|----|------|:---:|
| ① 카드 전체 삭제 | 가장 단순 | ❌ **누락 감지 그물이 사라진다.** 진단 화면은 운영자가 "무엇이 잘못됐나"를 보는 유일한 화면이다 |
| **② 카드를 1줄 상태 행으로 축소** | `오픈소스 라이선스 고지 │ 정상(4개)` 또는 `누락 — 개발자에게 알려주세요`. **경로·열기 버튼·안내 문구 제거** | ✅ **채택** |
| ③ 카드 유지 + 설정에도 추가 | 두 곳 관리 | ❌ 문구·상태가 갈린다 |

| 채택 근거 | 내용 |
|-----------|------|
| 요구 충족 | 진단에서 **열지 않는다**(버튼·경로 없음). 전문 열람은 설정에서만 |
| 안전망 유지 | 헬스체크 형식(카메라·ffmpeg·백엔드와 같은 행 형태)으로 남아 배포 누락이 진단 화면에서 보인다 |
| 부수 이득 | 진단 모달이 짧아진다(현행 카드 29줄 → 행 8줄) |
| 문구(동결) | 정상: `정상({N}개)` / 누락: `누락 — 배포 산출물에 고지가 없습니다` · 색은 기존 `Brush.Success`/`Brush.Danger`(카메라 행과 동일 패턴) |

## D2 통합 WBS

### D2.1 착수 순서와 병렬성

```
A(문서)  ──────────────────────────────  독립. 언제든
C(라이선스) ─── C1 → C2 → C3 → C4 ────  독립
B(테스트모드) ── B1 → B2 → B3 → B4 → B5 → B6 → B7
                          ↑
                     B3(PIN) 이후 C의 게스트 경로와 무관하게 진행
```

- **A는 완전 독립**(코드 0줄) → 다른 작업과 동시 진행 가능
- **B와 C는 파일이 겹치지 않는다**(B: `MainWindow`·`AppShell`·`Core/Settings` / C: `SettingsView`·`SettingsViewModel`·`Diagnostics*`) — 단 **`DiagnosticsWindow.xaml`·`DiagnosticsViewModel`을 둘 다 건드린다**(B는 경로 행 추가, C는 라이선스 카드 축소) → 같은 파일 충돌을 피하려면 **C를 먼저** 끝내고 B의 진단 행을 얹는다
- 권장: **A → C → B**
