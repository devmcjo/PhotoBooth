## 1. 설계 목표와 비목표

### 1.1 목표

| # | 목표 |
|---|------|
| G1 | **동작 동일성** — 같은 프로파일의 클라이언트는 같은 입력에 같은 결과를 낸다(픽셀 규격까지) |
| G2 | **불변식 보존** — [05 §6](../analysis/05-cross-platform-client-guide.md)의 M1~M16이 모든 플랫폼에서 지켜진다 |
| G3 | **서버 계약 단일화** — 플랫폼이 늘어도 서버 분기는 최소(인증 리디렉트 방식만) |
| G4 | **테스트 가능한 순수 로직 비중 최대화** — 상태 전이·기하·정책 판정은 UI·OS API 없이 단위 테스트 가능해야 한다 |
| G5 | **점진 출시** — 프로파일 단위로 독립 출시 가능(P1만, P1+P4만 등) |

### 1.2 비목표

| # | 비목표 | 이유 |
|---|--------|------|
| N1 | **단일 크로스플랫폼 코드베이스 강제** | 카메라·인코딩·파일 시스템이 파이프라인의 절반이다. 그 계층은 어차피 플랫폼별이며, 억지로 추상화하면 성능·품질 제어를 잃는다 |
| N2 | 기존 Windows 앱을 크로스플랫폼 프레임워크로 재작성 | 검증된 자산을 버리는 비용이 이득보다 크다. Windows는 그대로 유지하고 새 플랫폼을 추가한다 |
| N3 | 프레임·설정의 기기 간 동기화 | 현재 개인 프레임은 로컬 전용이 정책이다([41 §3.1](../analysis/41-local-data-and-file-formats.md)). 동기화는 별 과제 |
| N4 | 오프라인 로그인 | 보안 회귀다([61 §9](../analysis/61-auth-platform-integration.md)) |
| N5 | 서버측 이미지 합성·타임랩스 변환 | 현재 전부 클라이언트 책임. 도입은 별 결정(B6) |

## 2. 계층 구조 (모든 플랫폼 공통 골격)

Windows 구현이 4계층으로 검증했고, 그 경계를 그대로 쓴다. **언어·프레임워크는 달라도 경계는 같다.**

```
┌──────────────────────────────────────────────────────────────┐
│  UI 계층                                                      │
│  화면 렌더 · 입력 · 내비게이션 · 네이티브 관례(권한 대화상자 등)      │
└───────────────────────┬──────────────────────────────────────┘
                        │  (화면 로직이 노출하는 상태·명령만 소비)
┌───────────────────────▼──────────────────────────────────────┐
│  화면 로직 계층 (Presenter / ViewModel / Store)                │
│  화면별 상태·명령·진입/이탈 훅 · 셸(상태머신·유휴·세션)             │
└───────────────────────┬──────────────────────────────────────┘
                        │  (인터페이스에만 의존)
┌───────────────────────▼──────────────────────────────────────┐
│  도메인 계층  ★ 플랫폼 무의존 · 100% 단위 테스트 가능             │
│  • 화면 상태 전이 규칙          • 슬롯 기하(자동배치·스케일·클램프)   │
│  • 중앙 크롭 계산               • 좌표 변환(화면↔프레임)            │
│  • 프리뷰 Ready 판정            • 유휴 카운트다운                  │
│  • 역할·권한 정책               • 프레임 출처 분류·편집/삭제 판정     │
│  • 사본 이름 생성               • QR 토글 정규화                   │
│  • 세션 ID·경로·URL 조립        • 만료 시각 계산                   │
│  • 업로드 오케스트레이션         • 설정 범위 보정(clamp)             │
│  • 서비스 인터페이스(계약) 정의                                    │
└───────────────────────┬──────────────────────────────────────┘
                        │  (도메인 인터페이스를 구현)
┌───────────────────────▼──────────────────────────────────────┐
│  플랫폼 어댑터 계층 (플랫폼마다 새로 씀)                          │
│  카메라 · 인코더 · 합성/필터 · 파일 저장 · 백엔드 HTTP · OAuth ·    │
│  QR 생성 · 로그 · 브라우저 열기 · 사진 라이브러리 · 창/표시 모드      │
└──────────────────────────────────────────────────────────────┘
```

### 2.1 계층 규칙

| 규칙 | 내용 |
|------|------|
| **의존 방향 단방향** | UI → 화면 로직 → 도메인 ← 플랫폼 어댑터. **도메인은 아무것도 참조하지 않는다** |
| **도메인에 OS API 금지** | 파일 I/O·네트워크·시각(now)·난수를 도메인 로직 안에서 직접 호출하지 않는다. 필요하면 인자로 주입(테스트 가능성) |
| **어댑터는 예외를 전파하지 않는다** | 장치 열기 실패·인코더 부재는 **false/null 반환**. 상위가 상태로 표현한다([14 §2.1](../analysis/14-media-pipeline-spec.md)) |
| **하드웨어 리소스 단일 소유** | 카메라 어댑터는 앱 전체에서 하나만 존재한다(싱글턴). 화면은 소유하지 않고 빌린다 |
| **화면 로직은 화면을 모른다** | 창 닫기·다이얼로그 표시는 이벤트/콜백으로 요청한다. UI 타입을 직접 참조하지 않는다 |

### 2.2 도메인 계층에 반드시 들어가야 하는 것 (이식 우선순위 1)

아래는 **플랫폼과 무관한 순수 로직**이며, 새 클라이언트에서 **가장 먼저 이식하고 단위 테스트로 고정**해야 하는 항목이다. Windows 구현에 대응 코드가 있어 그대로 옮길 수 있다.

| 도메인 로직 | 규격 | 왜 순수여야 하나 |
|-------------|------|------------------|
| 화면 상태 전이 | [13 §2](../analysis/13-client-behavior-spec.md) | 전이 누락·불법 전이가 UI 테스트로는 잡히지 않는다 |
| 중앙 크롭 | [14 §3](../analysis/14-media-pipeline-spec.md) | 정수 나눗셈 한 곳만 달라도 결과 픽셀이 어긋난다 |
| 슬롯 자동배치·스케일·클램프·검증 | [14 §4](../analysis/14-media-pipeline-spec.md) | 동상 |
| 화면↔프레임 좌표 변환 | [14 §4.5](../analysis/14-media-pipeline-spec.md) | 표시·드래그·클램프가 같은 변환을 쓰는지 검증해야 WYSIWYG가 보장된다 |
| 프리뷰 Ready 판정 | [14 §2.3](../analysis/14-media-pipeline-spec.md) | 타이밍 의존 버그를 테스트로 고정 |
| 역할·권한 정책(`isPower`·`canWriteFrames`·`canManage`·**`canResetPin`**·`assignableRoles`) | [60 §1](../analysis/60-auth-accounts-and-roles.md) | 서버 매트릭스와 1:1 대칭임을 테스트로 고정. `canResetPin`은 `canManage`보다 한 칸 좁다(동급 차단 — 매니저 PIN은 admin 전용) |
| 프레임 출처 분류 + 편집/삭제 판정 | [13 §6.1](../analysis/13-client-behavior-spec.md) | 권한 오판이 조용히 생긴다 |
| 사본 이름 생성 | [13 §6.4](../analysis/13-client-behavior-spec.md) | 무한 누적·충돌 처리가 미묘하다 |
| QR 토글 정규화·재활성 | [41 §2.4](../analysis/41-local-data-and-file-formats.md) | 최소 1개 불변식(M7)의 클라 측 방어선 |
| 설정 범위 보정 | [41 §2.1](../analysis/41-local-data-and-file-formats.md) | 손상된 설정으로 촬영이 깨지지 않게 |
| 세션 ID·Storage 경로·토큰 URL·다운로드 페이지 URL·만료 계산 | [31 §7](../analysis/31-backend-api-reference.md) | 서버 정규식과 정확히 맞아야 한다(M13) |
| 업로드 오케스트레이션(3단계 순서·최소 1개 불변식·진행률 합산) | [31 §5](../analysis/31-backend-api-reference.md) | 순서 실수가 과금·데이터 오귀속으로 이어진다 |
| 유휴 카운트다운 | [13 §7](../analysis/13-client-behavior-spec.md) | — |
| 타임랩스 배속 산출 | [14 §7.2](../analysis/14-media-pipeline-spec.md) | — |
| 표시 모드 적용 판정(데스크톱) | [11 §16](../analysis/11-exe-app-features.md) | 실제 결함 수정의 본체다 |

> **설계 판단**: 이 목록은 새 클라이언트 작업량의 상당 부분이면서 **UI 없이 전부 테스트 가능**하다. 따라서 어느 플랫폼이든 **"도메인 이식 + 테스트 통과"를 첫 마일스톤**으로 잡는 것이 가장 위험을 줄인다. 카메라·인코더는 그다음이다.

### 2.3 플랫폼 어댑터 인터페이스 목록

도메인이 정의하고 플랫폼이 구현하는 계약. Windows 구현의 인터페이스 이름을 괄호에 남겼다(대응 찾기용).

| 어댑터 | 책임 | 실패 정책 |
|--------|------|-----------|
| 카메라 소스 (`ICameraService`) | 장치 열거·시작/정지·프리뷰 프레임 발행·스틸 캡처·녹화 시작/정지·거울/종횡비 설정 | 열기 실패 = false 반환 |
| 합성기 (`ICompositionService`) | 프레임 + 컷 + 필터 → 파일 | 프레임 이미지 부재 = 명확한 오류 |
| 타임랩스 (`ITimelapseService`) | 세션 녹화본 + 배속 → 파일 | 인코더 부재·실패 = null |
| 결과물 로컬 저장 (`ILocalSaveService`) | 결과물을 영구 위치로 복사/등록 | 쓰기 불가 = null + 로그 |
| 로컬 프레임 저장소 (`ILocalFrameStore`) | 공용/개인 프레임 읽기·쓰기·삭제 | 삭제 성공은 **실제 부재로 판정** |
| 프레임 저장소(원격) (`IFrameRepository`) | `/frames` 조회·생성·삭제 | 상태코드 → 도메인 예외 매핑 |
| 업로드 게이트웨이 (`IFirebaseClient`) | prepare / 서명 PUT / commit | 한도 초과는 전용 예외로 구분 |
| 계정 서비스 (`IAccountService`) | 로그인·목록·삭제·역할·PIN | 401 처리는 **호출부가 결정** |
| 무료 한도 조회 (`IQrUsageService`) | 본인 게이트 상태 | **fail-open**(null) |
| 전역 한도 (`ITempUserLimitsService`) | 조회·수정 | 예외 전파 |
| 세션 토큰 홀더 (`IBackendSession`) | JWT 보관·부착·폐기 | 메모리 전용 |
| 인가 코드 획득 (`IGoogleSignInService`) | 플랫폼별 OAuth UI → code 반환 | 취소·타임아웃 = null |
| QR 생성 (`IQrService`) | URL → 이미지 | — |
| 설정 저장소 (`ISettingsService`) | 로드·저장(**성공 여부 반환**) | 실패 = false |
| 브랜딩 (`IBrandingService`) · 빌드 정보 (`IBuildInfoService`) | 표시명·버전 | 부재 = 기본값. 빌드 정보는 외부 파일이 아니라 **빌드 산출물 자신**(버전 리소스·타임스탬프)에서 읽는다(it18) |
| 로그 (`ILogFolderService`) | 로그 위치 노출·열기/공유 | 실패해도 크래시 금지 |
| 세션 작업 공간 | 세션 폴더 생성·정리·시작 시 잔재 정리 | 개별 실패 무시 |
| 표시 모드/창(데스크톱) | 전체화면·창 기하 적용 | — |

> ⚠️ `IFirebaseClient`라는 이름은 실체(백엔드 게이트웨이)와 어긋나 있다. 새 클라이언트는 **`IUploadGateway` 같은 정직한 이름**을 쓰는 것을 권한다(Windows에서는 리네임을 백로그로 남긴 상태다).

## 3. 플랫폼별 권장 스택

| 플랫폼 | 언어·UI | 카메라 | 인코딩 | 이미지 처리 | 저장 | OAuth UI |
|--------|---------|--------|--------|-------------|------|----------|
| **macOS** | Swift + SwiftUI | AVFoundation | AVAssetWriter / AVAssetExportSession | Core Image / Accelerate | Application Support | `ASWebAuthenticationSession`(권장) 또는 loopback |
| **iOS / iPadOS** | Swift + SwiftUI | AVFoundation | 동상 | Core Image | 앱 컨테이너 + Photos | `ASWebAuthenticationSession` |
| **Android** | Kotlin + Compose | CameraX | MediaCodec / MediaMuxer | Canvas·RenderEffect·GL | `filesDir` + MediaStore | Custom Tabs (AppAuth) |
| **웹** | TypeScript (프레임워크 자유) | `getUserMedia` | MediaRecorder(제약) | Canvas 2D / WebGL | localStorage + IndexedDB | 브라우저 리디렉트 |
| Windows(현행) | C# + WPF | OpenCV(DirectShow) | ffmpeg | OpenCV | INI + 파일 시스템 | loopback + 시스템 브라우저 |

### 3.1 코드 공유 전략 — 3가지 선택지

| 안 | 내용 | 장점 | 단점 | 권장 |
|----|------|------|------|------|
| **A. 플랫폼별 네이티브 + 규격 문서 공유** | Swift·Kotlin·TS로 각각 구현하고 [analysis](../analysis/README.md) 규격과 테스트 케이스를 공유 | 플랫폼 최적 품질, 스토어 심사 마찰 최소, 팀별 독립 진행 | 도메인 로직 **3중 구현**(드리프트 위험) | **기본안** |
| B. Kotlin Multiplatform으로 도메인 공유 | 도메인 계층을 KMP로 작성해 Android·iOS 공유 | 도메인 드리프트 제거 | iOS 팀에 Kotlin 도입 비용, 빌드 복잡도 | Android·iOS를 같은 팀이 만들면 검토 |
| C. 단일 크로스플랫폼 프레임워크(Flutter 등) | 한 코드베이스로 전부 | 개발 비용 최소 | 카메라·인코딩 제어가 파이프라인 절반이라 결국 네이티브 플러그인. Windows 앱은 유지되어 이원화 | 비권장(N1) |

**A안을 기본으로 하되 드리프트를 막는 장치를 함께 둔다:**

| 장치 | 내용 |
|------|------|
| **공유 테스트 벡터** | 도메인 로직의 입력→기대출력을 **JSON 파일로 리포지토리에 저장**하고, 각 플랫폼이 자기 테스트에서 같은 파일을 읽어 검증한다. 대상: 중앙 크롭 · 슬롯 자동배치 · 스케일 · 클램프 · 겹침 검증 · 좌표 변환 · 역할 매트릭스 · 사본 이름 · 세션 ID·URL 조립 · 타임랩스 배속 · 설정 clamp |
| **기준 이미지(골든) 비교** | 고정 입력(컷 N장 + 프레임 + 필터)에 대한 합성 결과를 기준 이미지와 비교(허용 오차 내). 필터 파라미터·크롭 오차를 잡는다 |
| **계약 스모크** | 각 클라이언트가 API 3단계 업로드를 실제 실행하고 웹에서 다운로드까지 확인하는 스모크를 CI에 둔다 |
| **규격 갱신 규칙** | 규격 변경 시 [analysis](../analysis/README.md) 문서 → 테스트 벡터 → 각 클라이언트 순으로 반영. **문서를 먼저 고친다** |

> 테스트 벡터 파일 위치 제안: `docs/spec-vectors/*.json`(플랫폼 중립, 리포지토리 루트 기준). 착수 시 Windows 구현의 기존 단위 테스트에서 추출하면 초기 벡터를 거의 공짜로 얻는다.

## 4. 프로파일별 범위 결정

프로파일 정의는 [05 §4](../analysis/05-cross-platform-client-guide.md). 여기서는 **각 플랫폼이 무엇까지 만들 것인가**를 제안한다.

| 플랫폼 | P1 소비자 | P2 촬영 | P3 저작 | P4 운영 | 근거 |
|--------|:---------:|:-------:|:-------:|:-------:|------|
| **macOS** | ○ | ○ | ○ | ○ | Windows와 동등 능력. 현행 앱의 1:1 대응 |
| **iPadOS** | ○ | ○ | ○ | △ | 거치형 키오스크로 실용적. P4는 웹 콘솔로 빼는 편이 안전 |
| **Android(태블릿)** | ○ | ○ | △ | △ | iPadOS와 동급. P3는 화면 크기에 따라 |
| **iOS(폰)** | ○ | ✕ | ✕ | △ | 손님이 QR로 여는 흐름이 주. 6~10컷 키오스크 촬영은 폼팩터 부적합 |
| **Android(폰)** | ○ | ✕ | ✕ | △ | 동상 |
| **웹** | ○(현행) | **✕** | **△**(공용만) | **○** | P4를 웹으로 빼면 **현장 기기에서 운영 기능을 제거**할 수 있다(보안·오조작 이득). P2는 **계약·불변식을 만족할 수 없어 제외**하고, P3는 **공용 프레임 저작만** 지원한다 — 근거 §4.3 |

### 4.1 설계 판단 — P4를 웹으로 분리하는 것을 권한다

| 이득 | 내용 |
|------|------|
| 공격면 축소 | 현장 키오스크에 계정 삭제·역할 변경 UI가 없어진다 |
| 오조작 방지 | 손님·현장 직원이 관리 화면에 도달할 경로가 사라진다 |
| 개발 효율 | 관리 UI는 표·폼 중심이라 웹이 압도적으로 빠르다 |
| 배포 속도 | 스토어 심사 없이 즉시 배포 |

| 비용 | 대응 |
|------|------|
| 게이트 키가 브라우저에 노출(B4) | 웹용 별도 키 발급 + 사용처 제한, 또는 **로그인 후 Bearer만 쓰는 경로로 한정**(관리 API는 전부 Bearer 필수이므로 게이트 키 불요 — 이 경로가 가장 깔끔하다) |
| 오프라인 현장에서 관리 불가 | 현장 필수 기능(카메라 테스트·진단·설정)은 클라이언트에 남긴다. 계정·역할만 웹으로 |
| 인증 흐름 추가 구현 | B1·B2·B3 확장이 어차피 필요하다 |

> ℹ️ **주목할 점**: `/accounts`·`/config` 라우터는 라우터 레벨에서 `requireBearer`만 걸고 `requireApiKey`는 걸지 않는다([31 §4.0](../analysis/31-backend-api-reference.md)). 즉 **P4 웹 콘솔은 배포 게이트 키 없이 JWT만으로 동작할 수 있다.** B4가 P4 웹 콘솔의 블로커가 아니라는 뜻이며, 이것이 "P4를 웹으로 먼저 빼자"는 제안의 실질적 근거다. (로그인 자체인 `POST /auth/google`은 게이트 키가 필요하므로 그 한 지점만 결정하면 된다.)

### 4.2 P2 축소 프로파일 (모바일 폰·웹)

촬영을 완전히 포기하는 대신 **축소 프로파일**을 두는 선택지도 있다.

| 축소안 | 내용 | 영향 |
|--------|------|------|
| **컷 수 축소** | 6컷 대신 1~4컷 | 설정 허용 집합 변경 → **계약 변경**이므로 신중해야 한다 |
| **타임랩스 미제공** | `timelapseUrl = null`로 commit | 계약 위반 없음. 서버·웹이 "옵션 꺼짐"으로 정상 처리 |
| **세션 녹화 미제공** | 타임랩스도 자동으로 없어짐 | 동상 |
| **프레임 저작 미제공** | 공용 프레임만 사용 | 영향 없음 |

> **권장**: "타임랩스 미제공 + 프레임 저작 미제공"까지는 계약 변경 없이 안전하다. **컷 수 허용 집합 변경은 하지 말 것** — 프레임 슬롯 수와 얽혀 있고 여러 클라이언트가 같은 프레임을 공유한다.

### 4.3 설계 판단 — 웹 범위 확정 제안

웹은 §4.2의 "축소 프로파일"로도 구제되지 않는 항목이 있다. 기능별 사실 판정은 [05 §7.4](../analysis/05-cross-platform-client-guide.md)에 있고, 여기서는 **그래서 무엇을 만들고 무엇을 만들지 않을 것인가**를 제안한다.

#### 4.3.1 결론

| 프로파일 | 제안 | 근거 |
|----------|------|------|
| **P1 소비자** | **지원**(현행 유지) | 제약 없음 |
| **P4 운영** | **지원 — 웹의 주력으로 삼는다** | 표·폼 UI에 최적, 즉시 배포, 현장 기기에서 관리 기능 제거(§4.1). **게이트 키도 불필요**(§4.1 각주) |
| **P3 공용 프레임 저작**(power) | **지원** | 진실원이 서버라 브라우저 저장소를 쓰지 않는다. 공용 프레임을 바꾸려고 현장에 가지 않아도 되는 **웹 고유의 이점** |
| **P3 개인 프레임 저작** | **제외** | §4.3.2 |
| **P2 촬영** | **제외** | §4.3.3 |

#### 4.3.2 개인(로컬) 프레임을 웹에서 만들지 않는 이유

두 가지 이유가 있고, **두 번째가 더 결정적**이다.

**① 브라우저 저장소는 영속을 보장하지 않는다**

IndexedDB에 PNG Blob과 슬롯 메타를 넣으면 용량은 충분하다(localStorage는 문자열 5~10MB라 애초에 불가). 문제는 수명이다.

- `navigator.storage.persist()`로 영속을 요청할 수 있지만 **Chromium은 휴리스틱으로 판단**하고 **WebKit은 사실상 지원하지 않는다.**
- WebKit은 설치되지 않은 사이트의 script-writable 저장소를 **약 7일 무상호작용 시 삭제**한다. iOS는 모든 브라우저가 WebKit이라 예외가 없다.
- 여기에 "인터넷 사용 기록 삭제"·시크릿 모드·다른 브라우저·다른 기기·회사 PC 정책이 겹친다.

행사 단위(주·월 간격)로 운영되는 포토부스에서 **7일 규칙은 "예외적 손실"이 아니라 "정상 동작"** 이 된다.

**② 웹에는 그 프레임의 소비자가 없다 — 이게 더 중요하다**

키오스크에서 로컬 프레임이 의미 있는 이유는 **프레임을 만든 곳이 곧 촬영하는 곳**이라는 것이다. 웹은 그 전제가 성립하지 않는다.

```
웹에서 개인 프레임 생성 → 브라우저 IndexedDB
촬영은 키오스크(Windows/iPadOS)에서 일어남
그 사이에 동기화 없음  ([41 §3.1](../analysis/41-local-data-and-file-formats.md) 정책)
        ↓
지워지기 전에도 쓸 곳이 없다
```

즉 ①을 완벽히 해결해도(설치형 PWA + OPFS 등) **여전히 무용하다.** 로컬 프레임의 가치는 "저장됨"이 아니라 "여기서 촬영할 때 쓸 수 있음"인데, 웹은 후자를 못 한다(P2 제외 — §4.3.3).

**따라서**: 웹에서 "내 프레임을 만들고 싶다"는 요구가 실제로 생기면, IndexedDB로 우회할 문제가 아니라 **개인 프레임을 서버에 저장하는 정책 결정**(D7)으로 다뤄야 한다.

#### 4.3.3 P2 촬영을 웹에서 만들지 않는 이유

축소로 회피할 수 없는 것이 둘 있다.

| 막히는 것 | 왜 우회 불가인가 |
|-----------|------------------|
| **타임랩스(WB1)** | 서버 계약이 타임랩스에 대해 `ext: "mp4"` + `contentType: "video/mp4"` **만** 허용한다. 브라우저 `MediaRecorder`의 산출 컨테이너·코덱은 브라우저가 정하며 mp4/H.264를 보장할 수 없다. webm을 올릴 경로가 계약에 없어 **400**이다. §4.2의 "타임랩스 미제공"으로 회피할 수는 있다 |
| **결과물 로컬 보관(WB2)** | 불변식 **M6**("로컬 저장은 업로드 이전")을 만족할 수 없다. 브라우저에서 파일을 사용자 저장소로 내보내는 유일한 수단은 사용자 제스처가 필요한 다운로드이며, 사진+영상 다중 파일은 차단에 걸린다. **회피 수단이 없다** |

WB2가 결정적이다. 이걸 포기하면 **업로드가 실패한 손님의 사진이 그대로 사라진다.** 현재 아키텍처는 "업로드는 실패할 수 있다"를 전제로 M6·M5·M6를 설계했는데(그래서 QR 실패도 우아하게 처리된다), 웹은 그 안전망을 만들 수 없다.

여기에 **WR4(Fullscreen API는 ESC로 항상 탈출 가능 — 스크립트로 막을 수 없다)** 가 더해져 **웹 단독으로는 무인 키오스크가 성립하지 않는다.** 진짜 락다운은 브라우저 kiosk mode(OS·정책 설정)를 전제해야 하는데, 그렇게까지 환경을 통제할 수 있다면 네이티브 앱을 쓰는 게 낫다.

> **예외 검토**: "직원이 지켜보는 이벤트 부스에서 태블릿 브라우저로 촬영"처럼 **무인이 아니고 타임랩스도 불필요하며 업로드 실패 시 재촬영이 허용되는** 시나리오라면 웹 P2가 성립할 여지는 있다. 그 경우 WB2를 **명시적으로 포기한 축소 프로파일**로 선언하고(업로드 실패 = 재촬영), 사용자에게 "이 기기에서는 사진이 저장되지 않습니다"를 고지해야 한다. 기본 제품 범위로 삼기에는 부적합하다.

#### 4.3.4 웹 P4로 옮길 때 함께 결정해야 할 것

| 항목 | 내용 |
|------|------|
| 설정 편집(WR1) | `localStorage`가 회수 대상이라 운영자 설정이 사라질 수 있다. **웹 콘솔은 설정 편집을 제공하지 않고** 클라이언트 설정은 각 기기에 남기는 편이 안전하다(설정은 본래 기기별 값이다) |
| 진단·로그(WB5) | 웹에는 파일 로그가 없다. 진단 화면은 **서버 상태 조회 위주**로 만들고, 기기 로그(카메라·인코더)는 클라이언트에 남긴다 |
| 로그인 게이트 키(WR6) | 관리 API는 전부 Bearer 게이트라 게이트 키가 불필요하다. **`POST /auth/google` 한 지점만** 웹용 별도 키를 쓸지 결정하면 된다 |
| P1과 같은 호스팅에 둘 것인가 | 다운로드 페이지는 엄격한 CSP를 쓴다. 같은 호스팅에 올리면 `connect-src`에 백엔드 함수 도메인 추가가 필요하다. **별 경로(`/admin`)로 분리 + 별 CSP**를 권한다 |

## 5. 서버 확장 의존성

착수 순서를 정하는 핵심 제약이다. 상세는 [61 §4](../analysis/61-auth-platform-integration.md), 목록은 [90 §7.2](../analysis/90-roadmap-and-future-work.md).

| 플랫폼 | 서버 확장 없이 가능한 것 | 확장이 필요한 것 |
|--------|--------------------------|------------------|
| **macOS(loopback 방식)** | **전부** | 없음 |
| **웹 P1** | **전부**(백엔드 API를 쓰지 않는다) | 없음 |
| 웹 P4 + P3(공용 프레임) | — | B1·B2·B3(로그인)만 |
| ~~웹 P2~~ | — | **범위 제외**(§4.3.3). 만약 진행하면 B1·B2·B3 + B5(버킷 CORS) + B6(타임랩스) + **M6 포기 결정** |
| iOS·iPadOS | — | B1·B2·**B3** (+B8 Apple 로그인 가능성) |
| Android | — | B1·B2·**B3** |

### 5.1 그래서 착수 순서는

```
Phase 0  서버 확장 (B1·B2·B3)          ← 사실상 모든 모바일·웹 작업의 선행 조건
           리디렉트 허용 목록화 + audience 목록화 + client_secret 조건부
           회귀 테스트: 데스크톱 흐름 불변 / 허용 목록 밖 거부

Phase 1  P1 소비자 (원하는 플랫폼)      ← 서버 확장 불요. 규격 이해에 가장 저렴한 진입
Phase 2  웹 P4 관리 콘솔 + P3 공용 프레임 ← Phase 0 완료 후. 현장 기기에서 관리 기능 제거
           (공용 프레임 이미지 PUT을 하려면 버킷 CORS 선행 — §6)
Phase 3  macOS P2+P3                    ← 도메인 이식의 첫 완주. 서버 확장 없이도 가능
Phase 4  iPadOS P2+P3                   ← macOS 도메인·규격 재사용(Swift 공유 가능)
Phase 5  Android P2                      ← 필요 시

(웹 P2 촬영은 범위 제외 — §4.3.3)
```

> **Phase 3을 macOS로 두는 이유**: 서버 확장 없이(loopback으로) 전 기능을 완주할 수 있는 유일한 새 플랫폼이다. 여기서 도메인 이식·테스트 벡터·골든 이미지 체계를 완성해 두면, iPadOS는 Swift 자산을 상당 부분 재사용하면서 인증만 교체하면 된다. **Android나 iOS부터 시작하면 Phase 0에 막혀 진행이 멈춘다.**

## 6. 위험과 완화

| 위험 | 영향 | 완화 |
|------|------|------|
| **도메인 로직 드리프트** | 플랫폼마다 다른 결과물 | 공유 테스트 벡터 + 골든 이미지(§3.1). 규격 문서를 먼저 고치는 규칙 |
| **불변식 위반(특히 M1 토큰 폐기)** | 데이터 오귀속·과금 사고 | 각 플랫폼에서 **"로그아웃 직후 익명 업로드에 Bearer 미부착"** 을 통합 테스트로 고정 |
| **리디렉트 허용 목록 완화 실수** | 서버가 임의 호스트로 요청하는 통로(SSRF) | 정규식 완화 금지, **완전 일치 허용 목록**만. 코드 리뷰 필수 항목으로 지정 |
| **게이트 키 웹 노출** | 무단 API 사용 | P4는 Bearer 전용 경로로 설계(§4.1). 웹용 별도 키 + 폐기 가능성 확보 |
| 브라우저 업로드 CORS 미구성 | 웹에서 서명 URL PUT 전면 실패 | 웹 P2는 범위 제외(§4.3.3)라 현재는 무영향. **웹 P3(공용 프레임 저장)에도 이미지 PUT이 필요하므로** 그 착수 전에 버킷 CORS를 구성·검증해야 한다 |
| **웹 P2를 나중에 "그냥 되게" 만들려는 압력** | M6를 조용히 포기해 업로드 실패 시 손님 사진이 유실된다 | §4.3.3의 판정을 근거로 남겨 둔다. 진행하려면 **M6 포기를 명시적 결정(D4)으로** 기록하고 사용자에게 고지해야 한다 |
| **브라우저 저장소를 신뢰하는 구현** | 설정·개인 프레임이 조용히 사라진다(WebKit 7일 규칙 등) | 웹에서는 **서버가 진실원인 데이터만** 다룬다(§4.3.2·§4.3.4) |
| 모바일 인코딩 품질·성능 편차 | 결과물 품질 불균일 | 골든 이미지 비교 + 실기기 성능 예산 설정(합성 N초 이내) |
| 스토어 심사(Apple 로그인 요구) | 출시 지연 | B8을 iOS 착수와 **동시에** 설계. 계정 통합 정책을 먼저 정한다 |
| 저장공간 무한 누적(모바일 로컬 결과물) | 사용자 이탈 | 새 클라이언트는 **정리 정책을 처음부터** 설계([41 §5](../analysis/41-local-data-and-file-formats.md)) |
| PIN 브루트포스 | 물리 접근자의 설정 침입 | **기기 단위** 잠금 구현(계정 단위 금지 — DoS). [61 §7.3](../analysis/61-auth-platform-integration.md) |
| 규격 문서와 소스 불일치 | 잘못된 구현 | 진실원 우선순위(소스 > analysis > design)를 지키고, 규격 변경 시 문서를 먼저 고친다 |

### 7.1 D7 참고 — 개인 프레임 서버 저장은 생각보다 작은 변경이다

D7을 도입하기로 하면, 서버에 **인프라가 이미 대부분 존재**한다. 결정 비용을 오해하지 않도록 사실만 정리한다.

**이미 있는 것**

| 요소 | 현재 상태 |
|------|-----------|
| `saveFrame`의 `userId` 파라미터 | **이미 존재**하며 `userId`가 있으면 **계정당 10개 제한을 이미 검사**한다 |
| Storage 경로 분기 | `frames/{userId ?? "default"}/{frameId}.png` — **이미 분기**된다 |
| 본인 프레임 조회 | `GET /frames?userId=`가 **이미 있다**(본인만, power는 임의 계정) |
| 계정 삭제 시 cascade | `deleteAllFramesByUser`가 Firestore 문서 + `frames/{userId}/` 프리픽스를 **이미 정리**한다 |
| 클라 도메인 모델 | `FrameTemplate.UserId`가 **이미 있다** |

**막고 있는 것은 두 줄이다**

`routes/frames.ts`의 `POST /frames`가 ① `userId: null, isDefault: true`를 **하드코딩**하고 ② 게이트가 `requirePower()`다.

**필요한 변경**

| # | 변경 | 주의 |
|---|------|------|
| 1 | `userId`를 **JWT의 `sub`에서 서버가 결정**, `isDefault=false` | **클라 전달값을 신뢰하면 안 된다** — 남의 계정으로 프레임을 심을 수 있다 |
| 2 | 게이트를 "프레임 쓰기 권한(`advanced_user` 이상)"으로 | 서버에는 현재 **이 축이 없다.** [60 §1.2](../analysis/60-auth-accounts-and-roles.md)가 "서버 측 대응 축은 없다(의도)"라고 못 박은 부분을 뒤집는 것이므로, 회귀 테스트(`authGates.test.ts`)와 함께 설계해야 한다 |
| 3 | 조회·삭제에도 소유자 검증 | `DELETE /frames/{id}`는 현재 `requirePower()`뿐이다 — 개인 프레임이 생기면 **소유자 본인도 삭제할 수 있어야** 하고, 동시에 **남의 프레임을 지울 수 없어야** 한다 |

**파생 이득**

- **기기 교체 시 개인 프레임 유실**이 해결된다(iOS 앱 재설치, Android 기기 교체, 웹 저장소 회수 전부).
- [90 §1](../analysis/90-roadmap-and-future-work.md)에 대기 중인 두 이슈 — "power가 사본 저장한 공용 로컬 프레임을 다시 편집할 수 없다", "공용 로컬 프레임 삭제가 소유자로 제한되지 않는다" — 는 모두 **로컬 저장분에 소유자 메타가 없어서** 생긴 것이다. 서버 문서에 `userId`가 생기면 자연히 정리된다.
- 웹 P3가 개인 프레임까지 지원할 수 있게 된다.

**비용·주의**

- **`it8 A2` 하이브리드 결정을 뒤집는 정책 변경**이다(개인 프레임 = 로컬 전용). 사용자 결정 사항.
- 저장 비용은 미미하고(계정당 10개, PNG), 보안 규칙 영향은 없다(`frameTemplates`·`frames/`는 웹 접근 전면 차단, TTL 비대상).
- 로컬 저장과 서버 저장이 **공존**하게 되면 동기화 정책(어느 쪽이 진실원인가, 충돌 해결)을 정해야 한다. 가장 단순한 안은 **서버를 진실원으로 하고 로컬은 캐시로 강등**하는 것이며, 이는 공용 프레임이 이미 쓰는 방식이다.
