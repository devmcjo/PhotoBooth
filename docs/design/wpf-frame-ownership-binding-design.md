## 1. 사실 확인 — 사용자 우려 1건은 발생하지 않는다

> "a@google.com과 a@google2.com이면 둘 다 `a`라서 헷갈릴 것 같다"

서버 `deriveAccountId`가 충돌을 처리한다(`domain/accountId.ts`, 테스트 `accounts.test.ts:274`): `a@google.com` → `a`, `a@google2.com` → `a-2`. 계정 id는 **전역 유일**이다.

그럼에도 `#owner`에 이메일을 쓰는 이유: ① `a-2`가 누구인지 사람이 알아볼 수 없다 ② **재가입 허용(D-5)과 논리적으로 맞다**(계정 id는 재사용 여부가 서버 규칙에 좌우되지만 이메일은 확정적).

## 2. 서버는 이미 개인 프레임을 지원한다

| 기능 | 현황 |
|------|------|
| `saveFrame({userId, ...})` | **userId를 이미 받는다** |
| `getUserFrames(userId)` | **이미 존재** |
| 계정 삭제 cascade `deleteAllByUser` | **이미 존재** |
| 역할 `advanced_user` | `domain/roles.ts`에 **이미 정의**(랭크 2) |

막고 있는 것은 라우트 하나다 — `POST /frames`가 `userId: null, isDefault: true`를 하드코딩한다(`routes/frames.ts:76-83`).

### 2.1 ⚠️ 발견한 잠재 결함 — 계정 id `default` 충돌

```ts
const owner = input.userId ?? "default";        // services/frames.ts
const storagePath = `frames/${owner}/${frameId}.png`;
```

`validateAccountId`는 형식(`[A-Za-z0-9._-]{3,40}`)만 검사한다. **`default@gmail.com`으로 가입하면 계정 id가 `default`가 되어 개인 프레임이 공용 프레임 경로에 저장된다.** 공용 목록 오염, 최악의 경우 `deleteAllByUser`가 공용 프레임을 지운다.

→ **D-14**(`frames/users/{계정id}/`)가 이 충돌을 원천 차단한다. 예약어 금지보다 근본적이다.

## 3. `.slots` 포맷 v2

### 3.1 구조

```
파일(UTF-8) = base64( payload + "\n#sig=" + HMAC_SHA256_hex(key, payload) )

payload:
  #v=2
  #owner=a@google.com     ← 개인. 공용/DB default는 "default"
  #imagesize=1200,1600
  #dbid=8f2c1a90-...      ← 서버 문서 id. 공용·개인 **모두** 기록(§5.3·§10 동기화 키)
  0,80,140,480,640
  1,640,140,480,640
```

payload를 JSON이 아닌 **기존 텍스트 포맷 확장**으로 두는 이유: 서명 대상 바이트가 명확해진다(JSON은 키 순서·공백 canonical 규약이 따로 필요). 기존 파서도 거의 재사용된다.

### 3.2 필드

| 필드 | 필수 | 값 |
|------|:----:|-----|
| `#v` | ○ | `2` |
| `#owner` | ○ | 소문자 정규화 이메일 또는 예약어 `default` |
| `#imagesize` | ○ | `W,H` |
| `#dbid` | ○ | 서버 문서 id. **없으면 서버 미동기 상태**(삭제 동기화 비대상) |
| `#sig` | ○ | HMAC-SHA256 hex 64자. payload 마지막 줄, **서명 대상 제외** |
| 슬롯 줄 | ○ | `index,x,y,w,h` |

### 3.3 서명·검증

```
payload = 파일에서 마지막 "\n#sig=..." 줄을 뺀 나머지
sig     = HMAC-SHA256(key, UTF8(payload)) → 소문자 hex
비교    = CryptographicOperations.FixedTimeEquals
```

### 3.4 읽기 절차

```
1. base64 디코딩 실패        → 제외(v1 평문 파일이 여기서 걸러진다)
2. #sig 분리 → HMAC 재계산   → 불일치면 제외(로그에 owner 값은 남기지 않는다)
3. #owner 판정(§4.2)
```

**예외를 던지지 않는다.** 한 파일이 깨져도 나머지 목록은 정상 노출돼야 한다.

## 4. 저장 레이아웃과 노출 판정

### 4.1 로컬 레이아웃

```
{실행경로}\Frame\
  베이직 4컷.png                    ← 공용(번들·DB default 캐시). 루트
  베이직 4컷.slots
  users\
    3f9a2c1b8d4e7a05\               ← SHA256("a@google.com") 앞 16hex
      내 프레임.png
      내 프레임.slots               ← #owner=a@google.com (서명 안)
```

**파일시스템 어디에도 이메일이 평문으로 남지 않는다.** 폴더는 해시, 파일 내용은 base64+서명.

- 폴더는 **저장 위치일 뿐 권위가 아니다.** 옮겨도 `#owner`가 그대로라 다른 계정에서 보이지 않는다.
- 파일명은 **프레임 이름**이다(D-17이 계정 내 이름 유일성을 보장하므로 충돌하지 않는다).
- 해시 폴더라 사람이 소유자를 알 수 없는 문제는 진단 도구(§6.1)로 해소한다.

### 4.2 노출 판정 (`FrameOwnership.CanShow` — 순수)

```
1. 서명 검증 실패           → false
2. #owner == "default"      → true   (게스트 포함 전원)
3. 로그인 이메일 == null    → false  (게스트는 개인 프레임 미노출)
4. #owner == 로그인 이메일  → true   (소문자 정규화 후 Ordinal 비교)
5. 그 외                    → false
```

### 4.3 `#owner` 결정

| 저장 경로 | `#owner` | 위치 |
|-----------|----------|------|
| DB default 캐시 · power 공용 생성 · 번들 | `default` | 루트 |
| 개인 생성 | 로그인 이메일 | `users/{해시}/` |

## 5. 서버 정본 전환

### 5.1 목표 상태

| 항목 | 현행 | 전환 후 |
|------|------|---------|
| 정본 | 로컬 파일 | **Firestore `frameTemplates` + Storage** |
| Storage 경로 | `frames/{owner}/` | **개인 `frames/users/{계정id}/` · 공용 `frames/default/`**(D-14) |
| 로컬 | 정본 | **캐시** |
| 다른 기기 | 안 보임 | **같은 계정 로그인 시 보인다** |
| 개수 상한 | (미작동) | **없음**(D-10) |
| 이미지 크기 | 무제한 | **8MB**(D-11) |
| 프레임 수정 | 가능 | **폐지**(D-16, §8) |
| 오프라인 생성 | 가능 | **거부** |
| 로그아웃 시 캐시 | — | **삭제하지 않는다**(서명이 격리를 보장) |

### 5.2 서버 변경 (전부)

| # | 파일 | 변경 |
|---|------|------|
| S1 | `domain/roles.ts` | `canWriteFrames(role)` = `MANAGE_RANK[role] >= MANAGE_RANK["advanced_user"]`. ⚠️ `isPower`는 **건드리지 않는다**(power 축과 저작 축 분리 계약) |
| S2 | `http/auth.ts` | `requireFrameWrite()` 추가 |
| S3 | `routes/frames.ts` | **`POST /frames/mine`** 신설: `requireBearer` + `requireFrameWrite` → `saveFrame({userId: principal.id, isDefault: false, ...})` |
| S4 | `routes/frames.ts` | `DELETE /frames/{id}` 게이트 완화(D-12): 본인 소유면 허용, 공용은 power만 |
| S5 | `services/frames.ts` | **`MAX_PER_USER` 상한 검사 제거**(D-10) |
| S6 | `services/signing.ts` | 서명 URL에 **`x-goog-content-length-range: 0,8388608`** 조건 추가(D-11) |
| **S7** | `services/frames.ts` | Storage 경로를 **`frames/users/{userId}/`** 로(D-14). ⚠️ **`deleteAllByUser`의 접두도 함께 변경** — 안 고치면 계정 삭제 시 이미지가 영구 잔존한다 |
| **S8** | `services/frames.ts` | **계정 내 이름 중복 거부**(D-17): 같은 `userId` + 같은 `name`이면 409. 멀티 기기 동시 생성 방어 |
| **S9** | `routes/frames.ts` | `PUT /frames/{id}`는 **앱이 호출하지 않는다**(D-16). 라우트는 운영 도구용으로 유지하되 주석에 명시 |

**왜 새 라우트인가**(S3): 기존 `POST /frames`는 "공용 기본 프레임 생성"이라는 의미가 문서·테스트·클라에 고정돼 있고 게이트가 다르다(`requirePower` vs `requireFrameWrite`). 한 라우트에서 body로 분기하면 권한 오판 위험이 커진다 — it16이 두 권한 축을 분리한 정신과 같다.

### 5.3 클라이언트 동기화

```
프레임 선택 화면 진입(= 목록 로딩) 시에만:
  1. GET /frames/default            → 공용 정본
  2. GET /frames?userId={계정id}    → 개인 정본(로그인 시에만)
  3. 로컬 캐시 열거 → #dbid 기준 대조(§10)
  4. 서버에만 있는 것 → 다운로드 + v2 캐시 기록
  5. 로컬에만 있는 것(#dbid 보유) → 캐시 삭제 ← 안전장치 3종 필수(§10)
```

⚠️ **선택 이후에는 동기화하지 않는다.** 세션이 쓰는 프레임 파일이 사라지면 합성이 `FileNotFoundException`으로 실패한다. 목록 로딩 중에만 수행하고, 사용자가 프레임을 고른 뒤에는 그 세션이 끝날 때까지 잠근다 — **고른 프레임은 서버에서 지워졌더라도 그 세션 끝까지 정상 사용된다.**

### 5.4 오프라인 정책

| 상황 | 동작 |
|------|------|
| 오프라인 + 프레임 **생성** | **거부** — 저장 전 사전 안내 + 실패 시 재시도 안내 |
| 오프라인 + 프레임 **삭제** | 거부(정본 갱신 불가) — 로컬 파일은 **보존**(D-19) |
| 오프라인 + 기존 프레임 **사용(촬영)** | 허용(로컬 캐시) |
| 오프라인 + **삭제 동기화** | **수행하지 않는다**(§10 안전장치 1) |

#### 5.4.1 실패 안내 문구 (D-26)

예외 메시지를 그대로 노출하지 않는다. 실제로 새어 나가던 것들:

| 상황 | 노출되던 문장 | 문제 |
|------|--------------|------|
| 서버 주소 미설정 | `An invalid request URI was provided…` | .NET 영문. `BaseAddress`가 null인 채 상대 URL을 보내 HttpClient가 던진 것으로, 네트워크 catch에도 걸리지 않았다 |
| 토큰 만료(401) | `토큰 검증 실패: jwt expired` | **토큰 수명이 8시간**이라 하루 운영 중 반드시 발생한다 |
| 네트워크 끊김 | `백엔드에 연결할 수 없습니다.` | 사실이지만 **무엇을 하라는 말이 없다** |

**원인 판정은 예외 타입으로 한다** — 우리가 쓴 문구를 되짚어 분기하면 문구를 고칠 수 없게 된다.

| 타입 (`MCPhoto.Core.Backend`) | 던지는 곳 | 기반 타입(기존 catch 호환) |
|---|---|---|
| `BackendNotConfiguredException` | `SendCoreAsync` — 전송 **전** 판정 | `InvalidOperationException` |
| `BackendUnavailableException` | 네트워크·타임아웃, 이미지 PUT 실패 | `InvalidOperationException` |
| `BackendLoginRequiredException(Expired)` | 무토큰(false) / 401(true) | `UnauthorizedAccessException` |

문구 조립은 `BackendFailureMessage`가 전담한다. 규칙 = **①무엇이 안 됐는지 ②왜 ③무엇을 하면 되는지** + 오해 방지 사실:

- 저장 실패 → `"편집 중인 내용은 그대로 남아 있습니다."` (없으면 처음부터 다시 만든다)
- 삭제 실패 → `"이 PC의 파일은 그대로 둡니다."` (없으면 "지웠는데 목록에 남아 있다"로 읽힌다)

**사전 안내**: 편집기 저장 캡션이 *"프레임은 서버에 보관되므로 저장하려면 인터넷 연결이 필요합니다"*를 항상 표시한다 — 다 만들고 [저장]을 눌러서야 실패를 알게 되는 것을 막는다.

⚠️ **`PUT /accounts/me/pin`의 401은 예외다.** 이 라우트에서 401은 *현재 PIN 불일치*이거나 *토큰 만료*인데 서버가 둘 다 `code:"unauthorized"`로 준다. 공용 매핑을 그대로 쓰면 PIN을 틀린 사용자에게 "다시 로그인하세요"라는 틀린 안내를 하므로, 이 라우트만 원인을 단정하지 않는 일반 `UnauthorizedAccessException`으로 올린다. *(서버가 토큰 실패에 별도 코드를 주면 해소되는 문제 — 추후 개선 후보)*

## 7. 마이그레이션 — **없음** (D-13)

Release 전이라 기존 로컬 개인 프레임·DB default 캐시가 없다. v1 → v2 변환, 파일 이동, 계정 id → 이메일 매핑, 서버 이관 UI가 전부 불필요하다.

개발 PC에 v1 평문 파일이 남아 있어도 **별도 코드가 필요 없다** — base64 디코딩 실패로 §3.4 1단계에서 제외된다.

> ⚠️ 이 면제는 **Release 전에만 유효**하다. 배포 후 같은 변경을 하려면 마이그레이션이 반드시 필요하다.

## 8. 프레임 수정 기능 폐지 (D-16)

**개인·공용 모두 "수정"을 제공하지 않는다.** 잘못 만들었으면 새로 만든다.

| 항목 | 처리 |
|------|------|
| 진입점 | `FrameSelectView`의 **[선택 편집] 버튼 제거** |
| VM | `FrameEditorViewModel`의 `LoadForEdit`·`_isEditing`·`IsCreateMode` 분기 제거(항상 생성 모드) |
| 정책 | `FrameEditPolicy`에서 **편집 판정 제거**, 삭제 판정만 남긴다(D 지적: 죽은 코드를 남기면 오해와 잘못된 부활을 부른다) |
| 서버 | `PUT /frames/{id}`는 **앱이 호출하지 않는다**. 라우트는 운영 도구로 유지(S9) |
| 재활용 경로 | **[기존 프레임 불러오기]** 가 유일한 경로가 된다 → §11.3 |

### 8.1 ⚠️ 과금과의 충돌 — 미리 정리해 둔다

수정이 없으면 슬롯 하나를 5px 옮겨도 새로 만들어야 한다. 과금이 붙으면 **"새로 만들기(과금) + 잘못 만든 것 삭제(환불 없음) = 오타 하나에 2배 비용"** 이 된다.

→ **이미 있는 장치로 해결한다**: `billing/04 §3.4`의 "**생성 후 10분 내 삭제면 크레딧 환급**(계정당 일 3회)"을 **실수 수정 창구**로 명시한다. 실질적으로 무료 재작업이 된다.

  = 공용 프레임 이름 ∪ 본인 개인 프레임 이름

| 결과 | 설명 |
|------|------|

- 이름의 `_` 금지는 **유지**한다(서버 `validateFrameName`이 강제하고, 웹·모바일이 아직 접두 규약을 쓴다).

## 10. 삭제 동기화 (D-18) — 안전장치가 본체다

```
서버에 없고 로컬에 있으면 캐시를 삭제한다(공용·개인 모두).
```

이는 **대량 삭제를 자동 실행**하는 로직이다. 판정이 틀리면 사용자 프레임이 통째로 사라진다. 아래 3종은 **선택이 아니다**.

| # | 위험 | 안전장치 |
|---|------|----------|
| **1** | **오프라인** — 서버 목록을 못 받으면 "DB에 없다"로 오판해 전부 삭제 | 서버 응답이 **성공했을 때만** 삭제 판정. 실패·타임아웃이면 **아무것도 지우지 않는다** |
| **2** | **서버 장애로 빈 배열** — 0개를 받으면 역시 전부 삭제 | 응답이 **비어 있으면 삭제하지 않는다**(보수적). 실제로 다 지운 경우는 다음 동기화에서 정리돼도 늦지 않다 |
| **3** | **번들 프레임 오삭제** — 앱 동봉 프레임은 서버에 없다 | **`#dbid`가 있는 것만** 삭제 대상. 번들은 `#dbid`가 없어 자동 보호된다 |

추가 규칙

- **개인 프레임 판정은 로그인 상태에서만.** 게스트는 개인 목록을 조회할 수 없으므로 판정 자체를 하지 않는다.
- **dedup·삭제 판정 모두 `#dbid` 기준**(D-20). 종전 공용 dedup은 **이름 기준**(`PublicFrameNames()`)이었는데, 두 기준이 섞이면 "다운로드는 건너뛰는데 삭제 대상으로 잡히는" 모순이 생긴다.
- 로컬 삭제 실패(파일 잠금)는 **다음 동기화에서 재시도**한다. 그 세션에서는 목록에서만 제외한다.

## 11. UI 변경

### 11.1 저장 스코프 선택 (D-21)

**power + 신규 생성 시에만** 표시된다(advanced_user는 개인 저장 하나뿐이라 팝업 없음 — 과금 도입 시 차감 확인 팝업을 추가한다).

```
이 프레임을 저장하시겠습니까?
[프레임 이름]

  ○ 개인 프레임으로 저장  (권장)
     나만 사용합니다. 다른 계정에는 보이지 않습니다.

  ○ 서버 공용 프레임으로 저장
     모든 사용자와 게스트에게 노출됩니다.

           [저장]  [닫기]
            ↑ 선택 전까지 비활성
```

| 항목 | 규격 |
|------|------|
| 컨트롤 | **라디오 2개**(상호배타). 종전 체크박스는 "선택 안 함" 상태를 표현할 수 없어 강제 선택이 불가능했다 |
| 기본값 | **미선택**. 공용 저장은 전원에게 노출되는 되돌리기 어려운 작업이라 명시적 선택을 요구한다 |
| 배치 | **개인이 위 + "권장"** — 안전한 쪽을 시각적으로 우선한다 |
| 버튼 | [저장](선택 전 비활성) · **[닫기] 별도**(항상 활성) |
| 리셋 | 팝업을 열 때마다 미선택으로 되돌린다(직전 선택 잔존 금지) |

### 11.2 삭제 확인 (D-22)

| 대상 | 문구 | 확인 절차 |
|------|------|-----------|
| 개인 프레임 | "**영구적으로 삭제됩니다.** 이 PC와 서버에서 모두 지워지며, 다른 기기에서도 사라집니다. 복구할 수 없습니다." | [삭제] / [닫기] |
| 공용 프레임 | "⚠️ **공용 프레임입니다.** 삭제하면 **모든 사용자와 게스트**의 목록에서 사라집니다. 복구할 수 없습니다." | **☐ 모든 사용자에게서 사라진다는 것을 이해했습니다** → 체크 전 [삭제] 비활성 |

- 종전 "서버에서도 제거" **체크박스는 제거**한다. 선택이 아니라 **항상 둘 다** 지운다.
- **삭제 순서는 서버 → 로컬**(D-19). 서버 삭제가 실패하면 **아무것도 지우지 않는다** — 로컬만 지우면 다음 동기화에서 되살아나 "지웠는데 돌아왔다"가 된다.
- 확인 컨트롤은 **체크박스**를 쓴다. 선택지가 하나뿐인 라디오는 해제가 불가능하고 접근성 표현도 어색하다. **디자인 통일은 공용 스타일 리소스**(`Themes/Controls.xaml`의 `Choice.Option`)로 달성한다.

### 11.3 기존 프레임 불러오기 게이트 (D-23)

| 역할 | 불러올 수 있는 범위 |
|------|---------------------|
| advanced_user | **본인 개인 프레임만** |
| power(manager·admin) | **전체**(공용 + 본인 개인) |

수정 기능이 폐지되면서 이것이 **유일한 재활용 경로**가 된다. advanced_user에게 완전히 막으면 자기 프레임을 다시 쓸 방법이 사라진다(파일이 해시 폴더에 있어 탐색기로 찾을 수 없다). 자기 것 재활용은 "남의 것/공용을 함부로 가져다 쓰는" 문제가 없으므로 열어 둔다.

## 12. 슬롯 키보드 이동 (D-25) — **독립 기능, 커밋 분리**

소유권 바인딩과 무관한 편집기 UX 개선이다.

### 12.1 현재 구조

`FrameEditorView.xaml.cs`가 Canvas에 `Rectangle`을 그리고 마우스 드래그로 슬롯을 옮긴다(`_dragIndex`). **슬롯 "선택" 상태가 없다** — 드래그 중에만 유효하고 놓으면 `-1`로 돌아간다.

### 12.2 규격

| 항목 | 규격 |
|------|------|
| 선택 상태 | `SelectedSlotIndex` 신설. 클릭 시 선택되고 **드래그 후에도 유지** |

## 18. 운영 — 기존 데이터 점검·이관

`web/functions/scripts/migrate-frame-storage-paths.mjs`

```
cd web/functions && npm run build          # 스크립트가 lib/domain/framePaths.js를 참조한다
node scripts/migrate-frame-storage-paths.mjs --project mcphoto-955fb           # 점검(dry-run)
node scripts/migrate-frame-storage-paths.mjs --project mcphoto-955fb --apply   # 이관 실행
```

| 대상 | 처리 |
|------|------|
| **공용(default) 프레임** | 경로가 `frames/default/{id}.png`로 **변경되지 않았다** → 이관 대상이 아니다. 이미지 존재 여부·이름 규약만 점검한다 |
| 개인 프레임(레거시 `userId != null`) | `frames/{userId}/` → `frames/users/{userId}/` 이관. **복사 → imageUrl 갱신 → 원본 삭제** 순(삭제 먼저면 실패 시 유실) |
| 이미지 없는 고아 문서 | 보고만 한다(**삭제하지 않는다**) |
| 이름에 `_`가 있는 문서 | 보고만 한다. 조회·사용은 정상이나 서버가 재저장을 거부한다 |

⚠️ 경로 규칙은 `src/domain/framePaths.ts` **한 곳**에 있고 서버·스크립트가 함께 쓴다. 복제하면
스크립트가 멀쩡한 파일을 옮기거나 고아로 오판한다 — 회귀는 `__tests__/framePaths.test.ts`가 잡는다.
