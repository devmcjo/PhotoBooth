## 1. 롤아웃 6단계

플래그는 전부 `config/billing`([07 §5.3](./07-api-and-data-contract.md))에 있고 **코드 배포 없이 전환**된다.

| 단계 | 이름 | 플래그 상태 | 사용자에게 보이는 것 | 종료 조건 |
|:---:|------|-------------|----------------------|-----------|
| **P0** | 골격 | `enabled:false, dryRun:true, enforceQuota:false` | **없음**(완전 무영향) | 지갑·원장·usage 문서가 생성되고 정합성 감사 통과 |
| **P1** | 계측(dry-run) | 동상 | 없음 | 2~4주 실사용 데이터로 **가격 확정**(§2) |
| **P2** | 표시 | `enabled:true, dryRun:true` | 상단바 잔량·상점(구매 가능) — **차단은 없음** | 구매 흐름 검증 완료(사내 결제 포함) |
| **P3** | 경고 | `enforceQuota:false` + 소진 경고 배너 | "정원을 초과했습니다(현재는 계속 사용 가능)" | 2주간 문의·오탐 0 |
| **P4** | 강제 | `enforceQuota:true` | 정원 초과 시 QR 차단 | 이행 지급 완료 + 고지 2주 경과 |
| **P5** | 세션·purge | `singleSessionEnabled:true`, `purgeLocalUserFramesOnBoot:true` | 단일 세션 + 로그아웃 프레임 정리 | 다중 사용 계정 개별 안내 완료 |

### 1.1 단계별 리스크와 중단 조건

| 단계 | 최대 리스크 | 즉시 중단(롤백) 조건 |
|:---:|-------------|----------------------|
| P0 | 트랜잭션 성능 저하로 업로드 지연 | commit p95 지연이 기존 대비 +30% 초과 |
| P1 | 없음(기록만) | — |
| P2 | 결제 사고(이중 지급·미지급) | 지급 불일치 1건 |
| P3 | 잘못된 정원 계산으로 오탐 경고 | 오탐 문의 3건 |
| P4 | **QR 전면 중단**(가장 위험) | 정상 계정의 차단 1건 → `enforceQuota:false` 즉시 |
| P5 | 영업 중 로그아웃 / 프레임 유실 | 유실 신고 1건 → `purge...:false` 즉시 |

> ✅ **P4·P5는 같은 날 켜지 않는다.** 최소 2주 간격. 문제가 생겼을 때 원인을 구분할 수 없게 되는 것을 막는다.

## 2. dry-run 계측 (P1) — 가격을 데이터로 확정하기

### 2.1 무엇을 기록하나

| 기록 | 방법 | 용도 |
|------|------|------|
| QR 전송 건수(계정·일자별) | `usage` 문서(실제 생성, 차단은 없음) | 플랜 정원 구간 설계 |
| "차감했을 것"(dry-run spend) | 원장에 `type:spend, deltaMc:0, reason:"dryrun_*", memo:"would spend N"` 기록 — **잔액을 바꾸지 않는다** | 실질 매출 추정 |
| 업로드 파일 크기(사진·타임랩스) | commit 요청 시 클라가 바이트 수를 함께 전송(신규 필드 `sizes`) 또는 Storage 메타 집계 | **단위 원가 실측**([01 §5](./01-currency-catalog-and-pricing.md)) |
| 다운로드 페이지 열람·파일 GET 수 | Storage/Hosting 로그 또는 GCP 청구 대조 | egress 원가 |
| 프레임 생성 빈도 | `frameEvents` | 프레임 단가 |
| 계정별 기기 수·세션 교체 | `sessions` + 이벤트 | 좌석 상품 수요 |

> ⚠️ **dry-run 원장 항목을 실제 `spend`와 섞지 않는다.** `deltaMc: 0` + `reason` 접두 `dryrun_`으로 구분하고, 정합성 감사는 `deltaMc` 합만 보므로 영향이 없다. P2 진입 시 dry-run 기록을 **삭제하지 않는다**(분석 자산).

### 2.2 산출물

| # | 산출물 | 쓰임 |
|:--:|--------|------|
| 1 | 세션당 실측 원가(원) | 가격 하한([01 §5.2](./01-currency-catalog-and-pricing.md)) |
| 2 | 계정별 일 사용량 분포(p50·p90·p99) | 플랜 정원 구간(10/30/50/100/200이 맞는지) |
| 3 | 월 사용량 분포 | 30일 플랜 vs 1일권 비중 |
| 4 | 프레임 생성 빈도 | 생성권 단가·묶음 구성 |
| 5 | 다중 기기 계정 목록 | P5 사전 안내 대상 |

## 6. 수락 기준 (출시 게이트)

### 6.1 기능

| # | 기준 | 판정 |
|:--:|------|:---:|
| A1 | 정원 내 QR 전송이 정상 동작하고 `usage`가 정확히 1 증가 | ☐ |
| A2 | 정원 소진 시 촬영·로컬 저장은 성공하고 QR만 빠진다(U1) | ☐ |
| A3 | 첫날 프로레이션이 [03 §5.3](./03-qr-daily-quota.md) 표와 일치 | ☐ |
| A4 | KST 자정에 정원이 리셋된다(수동 시각 검증 포함) | ☐ |
| A5 | MC 충전 → 잔액 증가 → 아이템 구매 → 정원 증가 전 과정 동작 | ☐ |
| A6 | 프레임 생성 시 과금되고, 이름 변경 저장이 신규 과금으로 안내된다 | ☐ |
| A7 | 로그아웃 후 개인 프레임이 사라지고 재로그인 시 복원된다 | ☐ |
| A8 | 공용·번들 프레임은 로그아웃 후에도 남는다 | ☐ |
| A9 | 2기기 로그인 시 기존 기기에 강제 로그아웃 팝업이 뜬다 | ☐ |
| A10 | 촬영 중 강제 로그아웃은 촬영 완료 후 표시된다 | ☐ |
| A11 | 게스트 촬영 흐름이 과금 도입 전과 동일하다 | ☐ |
| A12 | temp_user 무료 티어가 기존 문구·동작으로 유지된다 | ☐ |

| 마일스톤 | 서버(TS) | Windows(C#/XAML) | 웹(TS/React) | 문서·검증 |
|----------|:---:|:---:|:---:|:---:|
| A 골격 | 중 | 소 | 소 | 중 |
| B 구매·결제 | 대 | 중 | 중 | 중 |
| C 프레임 | 중 | 중 | 중 | 중 |
| D 세션 | 중 | 중 | 소 | 중 |
| E 마감 | 소 | 소 | 소 | 대 |

**착수 순서 권장**: A → (가격 확정) → B → C → D → E. **C와 D는 병행 가능**하나, 둘 다 로그아웃 경로를 건드리므로 purge 배선(Step 20)과 세션 처리(Step 23)는 **한 사람이 연달아** 하는 편이 안전하다.
