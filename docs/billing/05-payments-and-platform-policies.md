## 1. 채널 개요

| 채널 | 배포 형태 | 결제 수단 | 스토어 수수료 | 자사 정산 |
|------|-----------|-----------|:---:|:---:|
| **Windows** | 자체 인스톨러(Inno Setup 유력 — 상용화 단계) | **국내 PG**(카드·계좌·간편결제) | 없음 | ○ |
| **웹 클라이언트** | PWA(Firebase Hosting) | 국내 PG | 없음 | ○ |
| **iOS** | App Store | **IAP 강제** | 15~30% | 스토어 경유 |
| **Android** | Google Play | **Play Billing 강제**(국내는 대체결제 여지) | 15~30%(대체결제 26%) | 스토어 경유 |

> ✅ **Windows·웹은 스토어를 거치지 않으므로 IAP 제약이 없다.** MC포토의 주 사용자(B2B 부스 = Windows)가 여기에 있으므로 **초기 상용화는 PG만으로 충분**하다. 모바일 IAP는 클라이언트 개발 시점에 착수한다([11 D-15](./11-open-decisions.md)).

## 2. 스토어 정책 제약 (모바일 착수 전 필수 이해)

### 2.1 무엇이 강제되나

| 항목 | Apple | Google Play |
|------|-------|-------------|
| 앱 내 디지털 아이템 판매 | **IAP 필수**(App Review Guideline 3.1.1) | **Play Billing 필수**(Payments policy) |
| MC(소비형 크레딧)의 분류 | Consumable IAP | Consumable(managed product) |
| 앱 내에서 외부 결제 유도 | **원칙 금지.** 미국 스토어프론트는 2025년 법원 명령 이후 외부 링크 허용(수수료 관련 조건 변동) · EU는 DMA로 별 규정 | 원칙 금지. **한국은 전기통신사업법(2021) 개정으로 제3자 결제 허용**(대체결제 수수료 26%) |
| 크로스플랫폼 소비 | **허용** — 다른 플랫폼에서 구매한 콘텐츠를 앱에서 쓰는 것은 정당하다("multiplatform service") | 허용 |
| 앱 내에서 "웹에서 더 싸게 살 수 있다" 안내 | 스토어프론트별로 다르다(미국·EU 완화, 그 외 제한) | 한국은 대체결제 안내 가능 |
| 가격 동등성 | **요구하지 않는다** — 자사 채널을 더 싸게 팔 수 있다 | 동상 |

### 2.2 이것이 설계에 미치는 영향 (핵심)

| # | 함의 | 설계 대응 |
|---|------|-----------|
| 1 | **iOS/Android 앱 안에서는 PG 결제 화면을 띄울 수 없다**(리젝 사유) | 모바일 앱은 IAP 상품만 노출. `catalog/packs.channels`로 채널별 노출 제어([01 §6.3](./01-currency-catalog-and-pricing.md)) |
| 2 | 스토어 수수료 15~30%가 마진을 깎는다 | IAP 채널 가격을 **별도 책정**(§3.3). 같은 MC를 더 비싸게 팔거나, 같은 가격에 더 적은 MC |
| 3 | **크로스플랫폼 지갑은 정책상 안전하다** | iOS에서 충전한 MC를 Windows에서 쓰는 것은 문제없다. 지갑을 계정 단위로 두는 설계가 정합 |
| 4 | 소비형 IAP는 **소비 처리(consume/finish)** 를 반드시 해야 한다 | Google은 acknowledge를 3일 안에 하지 않으면 **자동 환불**된다. Apple은 finishTransaction 누락 시 트랜잭션이 계속 재전달된다 → §4.4 |
| 5 | 스토어 환불은 **우리 승인 없이** 일어난다(사용자가 스토어에 직접 요청) | 환불 알림(RTDN·App Store Server Notifications V2)을 **반드시 구독**해 MC를 회수한다 → §5.2 |
| 6 | 심사에서 "계정이 없으면 아무것도 못 하는 앱"은 리젝 위험 | 게스트 촬영이 이미 가능하므로 문제없다(현행 강점) |
| 7 | 미성년자 결제·부모 통제 | 스토어가 1차 통제. PG 채널은 자체 고지 필요 → [09 §6.4](./09-security-abuse-and-compliance.md) |

## 3. 상품 매핑과 채널별 가격

### 3.1 상품 id 매핑

`catalog/packs/{packId}.storeProductIds` = `{ios: "...", android: "..."}`

| 규약 | 내용 |
|------|------|
| 스토어 상품 id 형식 | `mcphoto.mc.100`(권장) — 소문자·점 구분. 스토어에서 **삭제·재사용 불가**하므로 처음부터 안정된 이름을 쓴다 |
| MC 수량의 진실원 | **서버 카탈로그**다. 스토어 상품 설명의 수량은 표시용 복제이며 불일치 시 서버가 정본(단, 사용자 오인 방지를 위해 배포 전 대조 스크립트 필수) |
| 매핑 부재 | 해당 채널에서 그 팩은 **노출하지 않는다**(클라 필터 + 서버 검증) |
| 상품 추가 | 스토어 등록 → 심사 → 카탈로그 매핑 갱신 순서. **카탈로그를 먼저 켜면 구매 불가 상품이 노출된다** |

### 3.2 채널별 노출 규칙

| 채널 | 노출 팩 | 근거 |
|------|---------|------|
| Windows | `channels`에 `pg` 포함 전량 | 제약 없음 |
| 웹 | 동상 | 제약 없음 |
| iOS | `storeProductIds.ios`가 있는 팩만 | 정책 §2.1 |
| Android | `storeProductIds.android`가 있는 팩만 | 동상 |

### 3.3 IAP 채널 가격 (초안)

수수료 30% 가정, [01 §3.2](./01-currency-catalog-and-pricing.md) 대안 A 기준.

| 팩 | PG 가격 | PG 순수령 | IAP 가격(초안) | IAP 순수령(70%) | 순수령 차 |
|----|--------:|----------:|---------------:|----------------:|----------:|
| `mc_10` | 1,000 | ~970 | **1,500** | 1,050 | +80 |
| `mc_30` | 2,800 | ~2,716 | **3,900** | 2,730 | +14 |
| `mc_50` | 4,500 | ~4,365 | **6,500** | 4,550 | +185 |
| `mc_100` | 8,500 | ~8,245 | **12,000** | 8,400 | +155 |
| `mc_300` | 24,000 | ~23,280 | **34,000** | 23,800 | +520 |

- PG 순수령은 수수료 3% 가정.
- **정책상 가격 차이는 허용**되지만, 사용자가 두 채널을 비교하면 불만이 생긴다 → 모바일 앱에는 "웹에서 더 싸다"를 **안내하지 않는다**(정책 위반 위험 + 스토어프론트별 차이). 대신 웹·Windows 쪽에서 "웹 충전이 더 저렴합니다"를 안내한다(우리 채널이므로 자유).
- 대안: **IAP 가격을 PG와 동일하게 하고 마진을 포기**(단순·공정, 사용자 불만 0). 소규모 개발자 프로그램(15%)에 해당하면 손실이 작다 → [11 D-16](./11-open-decisions.md).

## 4. 결제 흐름

### 4.1 상태 머신 (전 채널 공통)

```
        created ──> pending ──> paid ──> granted
           │           │         │          │
           │           ├──> failed          ├──> refund_requested ──> refunded
           │           └──> canceled        └──> partially_refunded
           └──> expired(30분 미완료)                     │
                                                    chargeback
```

| 상태 | 의미 | 전이 주체 |
|------|------|-----------|
| `created` | 주문 생성(서버) — 금액·팩·계정 고정 | 클라 요청 |
| `pending` | 결제창 진입 / 스토어 구매 진행 | 클라 통보 또는 PG 리다이렉트 |
| `paid` | **결제 승인 확인**(PG 서버 검증 또는 영수증 검증 성공) | 서버 |
| `granted` | MC 지급 완료(원장 `purchase` 기록) | 서버(트랜잭션) |
| `failed` / `canceled` / `expired` | 미결제 종료 | 서버 |
| `refund_requested` → `refunded` / `partially_refunded` | 환불 | 서버(웹훅·관리자) |
| `chargeback` | 카드사 분쟁 | 서버(PG 통보) |

**불변식**

| # | 내용 |
|---|------|
| PM1 | `granted`는 **`paid` 이후에만** 도달한다(B8) |
| PM2 | 상태는 **역행하지 않는다.** 늦게 도착한 하위 상태 알림은 무시하고 로그만 남긴다(웹훅 순서 미보장) |
| PM3 | `granted` 전이는 **멱등**하다. 같은 `paymentId`로 두 번 지급하지 않는다 |
| PM4 | 금액·MC 수량은 `created` 시점 스냅샷을 쓴다. 카탈로그가 바뀌어도 진행 중 주문은 옛 값 |
| PM5 | 클라이언트가 보낸 "결제 성공"만으로는 `paid`가 되지 않는다 |

### 4.2 PG 채널 — 웹

| 순서 | 주체 | 동작 |
|:---:|------|------|
| 1 | 클라 | `POST /payments/orders` `{packId, packVersion, idempotencyKey, channel:"pg", platform:"web"}` → `{paymentId, amountKrw, mcAmount, pgParams}` |
| 2 | 클라 | PG SDK/리다이렉트로 결제창 진입(`pending`) |
| 3 | PG | 사용자 결제 완료 → 리턴 URL로 복귀 + **서버 웹훅** 전송 |
| 4 | 서버(웹훅) | 서명 검증 → PG 조회 API로 **금액·주문 대조** → `paid` → 트랜잭션(원장 `purchase` + 잔액 증가 + `granted`) |
| 5 | 클라 | 복귀 후 `GET /payments/{paymentId}` 폴링(2초 간격, 최대 60초) → `granted`면 잔액 갱신 + 성공 화면 |

| 규칙 | 내용 |
|------|------|
| **웹훅이 정본**이다 | 클라 복귀는 UX 신호일 뿐. 복귀가 없어도(브라우저 종료) 웹훅으로 지급이 완료된다 |
| 금액 대조 필수 | 클라가 보낸 금액이 아니라 **서버 주문 금액**과 PG 조회 결과를 대조한다(금액 위조 방어) |
| 폴링 종료 | 60초 내 `granted` 미도달 시 "처리 중입니다. 잠시 후 잔액을 확인해 주세요" 안내(실패 단정 금지) |

### 4.3 PG 채널 — Windows (loopback 재사용)

Windows는 앱 안에 결제 웹뷰를 넣지 않는다. **Google SSO와 동일한 loopback 패턴**을 재사용한다.

| 순서 | 동작 | 근거 |
|:---:|------|------|
| 1 | `POST /payments/orders` → `{paymentId, checkoutUrl}` | 서버가 결제 페이지 URL 생성(자사 Hosting에 결제 브릿지 페이지) |
| 2 | 빈 loopback 포트 확보 → `HttpListener` 시작 → **시스템 기본 브라우저**로 `checkoutUrl?return=http://127.0.0.1:{port}/` 오픈 | `GoogleSignInService.cs`가 이미 하는 일과 동일(포트·리스너·타임아웃·정리 규약 재사용) |
| 3 | 결제 완료 → 브릿지 페이지가 loopback으로 리다이렉트 → 앱이 복귀 감지 | |
| 4 | 앱이 `GET /payments/{paymentId}` 폴링 → `granted` | 웹훅이 정본(§4.2와 동일) |
| 5 | 리스너·CTS는 `try-finally`로 항상 정리. 타임아웃 10분 | SSO 규약과 동일 |

| 이점 | 설명 |
|------|------|
| WebView2 의존 없음 | 배포물 크기·보안 패치 부담 회피(현재 앱은 WebView2를 쓰지 않는다) |
| PCI 범위 회피 | 카드 정보가 우리 앱을 통과하지 않는다 |
| 검증된 패턴 | loopback 흐름의 함정(localhost→::1, 포트 점유, 취소 처리)이 이미 해결돼 있다 |
| 키오스크 주의 | 브라우저가 봉쇄된 키오스크에서는 결제 불가 → **"결제는 관리자 PC/휴대폰에서"** 안내 + `paymentId` QR 표시 대안 제공(§4.6) |

### 4.4 IAP 채널 (모바일)

| 순서 | 주체 | 동작 |
|:---:|------|------|
| 1 | 클라 | 스토어 SDK로 상품 조회 → 구매 요청 |
| 2 | 스토어 | 결제 처리 → 영수증/토큰 반환 |
| 3 | 클라 | `POST /payments/iap/verify` `{platform, productId, receipt|purchaseToken, idempotencyKey}` |
| 4 | 서버 | **스토어 서버 API로 검증**(Apple: App Store Server API — JWS 서명 검증 / Google: `purchases.products.get`) → 상품·환경·중복 확인 → `paid` → 지급(`granted`) |
| 5 | 클라 | 서버 성공 응답 후 **소비 처리**(Apple `finishTransaction` / Google `acknowledge`+`consume`) |
| 6 | 서버 | 스토어 알림(App Store Server Notifications V2 / RTDN) 구독 → 환불·취소 시 회수(§5.2) |

| 규칙 | 내용 |
|------|------|
| **클라 영수증을 신뢰하지 않는다** | 로컬 검증 금지. 서버가 스토어 서버에 직접 확인(B8) |
| 중복 방어 | `transactionId`(Apple) / `purchaseToken`(Google)에 **유니크 제약**(`payments` 문서 id로 사용 또는 별 인덱스 문서) |
| 소비 처리 순서 | **서버 지급 성공 후** 소비 처리. 먼저 소비하면 지급 실패 시 복구 수단이 사라진다 |
| Google 3일 규칙 | acknowledge 지연 시 자동 환불된다 → 클라가 5단계를 반드시 수행하고, **미완료 트랜잭션 복구 루틴**(앱 시작 시 pending purchase 조회)을 넣는다 |
| 샌드박스 구분 | Apple `environment`, Google 테스트 계정 → **테스트 결제로 실제 MC를 지급하지 않는다**(`payments.isSandbox` 기록 + 지급 차단 또는 별 계정 한정) |
| 계정 연결 | 스토어 계정 ≠ MC포토 계정. **로그인 필수** 후 구매(로그인 전 구매는 지급 대상 계정을 알 수 없다). Google `obfuscatedAccountId`에 계정 해시를 실어 사후 대조 |

### 4.5 관리자 지급 (오프라인 계약·보상)

| 항목 | 규격 |
|------|------|
| 경로 | `POST /admin/wallets/{userId}/grant` (Bearer + **admin**) `{mcAmount, reason, memo, idempotencyKey}` |
| 원장 | `grant`(환불 대상 아님) |
| 용도 | B2B 연간 계약, 장애 보상, 이벤트 |
| 감사 | `actor.id` = admin 계정, `memo` 필수. 조회는 [07 §3.6](./07-api-and-data-contract.md) |
| 상한 | 1회 5,000MC, 일 20,000MC(오조작 방어). 초과는 2인 승인 절차(범위 밖 — 수동) |

### 4.6 키오스크 결제 대안 (브라우저 봉쇄 환경)

| 방식 | 설명 |
|------|------|
| **다른 기기 결제** | 앱이 `checkoutUrl`을 **QR로 표시** → 운영자가 휴대폰으로 결제 → 앱은 폴링으로 감지 |
| 사전 충전 | 운영자가 사무실 PC/웹에서 미리 충전(권장 기본 동선) |
| 자동 충전(auto-topup) | 잔액이 임계 이하면 자동 재결제 — **범위 밖**(정기결제는 빌링키·약관·해지 UI가 별 프로젝트) → [11 D-17](./11-open-decisions.md) |

## 5. 환불 · 취소

### 5.1 사용자 요청 환불 (PG 채널)

| 항목 | 규격 |
|------|------|
| 접수 | **앱 내 자동 환불은 제공하지 않는다**(초기). 고객센터(이메일·전화) 접수 후 관리자 처리 |
| 근거 | 전자상거래법상 디지털 콘텐츠는 **사용 개시 시 청약철회 제한**이 가능하나, **미사용분은 환불 대상**이다 → [09 §6.2](./09-security-abuse-and-compliance.md) |
| 계산 | 미사용 MC × 결제 시 단가(원장 스냅샷). 부족분 처리는 [02 §5.3](./02-wallet-ledger-and-entitlements.md) |
| 실행 | 관리자 도구 → PG 부분/전체 취소 API → 성공 시 원장 `refund` + 활성 grant `revoked` |
| 기간 | 결제 후 **7일 이내 미사용분** 전액 환불(권장 기본). 7일 초과·부분 사용은 미사용분 기준 |
| 수수료 | **부과하지 않음**(권장). 부과하려면 약관에 명시 필수 |
| 고지 문구 | [08 §7](./08-ui-ux-and-copy.md) |

### 5.2 스토어 발 환불 (IAP)

| 항목 | 규격 |
|------|------|
| 인지 경로 | Apple `REFUND` 알림 / Google RTDN `SUBSCRIPTION_*`·voided purchases API | 
| 필수 구현 | **Voided Purchases API 폴링(Google)** + Server Notifications(Apple) 둘 다. 알림 유실 대비 |
| 처리 | `refunded` 전이 → 원장 `refund` 회수(부족분 기록) → 활성 grant `revoked` |
| 반복 환불 남용 | 환불 이력 N회 이상 계정은 **지갑 동결**(`frozen`) + IAP 구매 차단 → [09 §4](./09-security-abuse-and-compliance.md) |
| 부분 환불 | 스토어는 보통 전체 환불이다. 부족분(이미 사용)은 회수 불가 → **손실로 인식**하고 이력에 기록 |

### 5.3 아이템(MC → 정원·프레임) 취소

| 대상 | 취소 가능? | 규칙 |
|------|:---:|------|
| 정원 플랜 — **구매 후 미사용**(당일 소비 0) | △ 관리자 재량 | 구매 후 24시간 내 + 해당 플랜 소비 0이면 MC 환급 가능(원장 `adjust +`, grant `revoked`) |
| 정원 플랜 — 일부 사용 | × | 일할 환급은 계산 복잡·남용 여지. **불가**로 고지 |
| 1일권 | × | 당일 소멸 상품 |
| 프레임 생성권 — 미사용 | △ | 24시간 내 MC 환급 가능(관리자) |
| 프레임 생성 완료 | × | [04 §3.4](./04-custom-frames-billing-and-lifecycle.md) |
| 오버리지 차감 | × | 전송 완료 |

> ✅ **원칙**: "소비되지 않은 것만, 짧은 창 안에서, 관리자 승인으로" 되돌린다. 자동 취소를 열면 정원을 쓰고 취소하는 어뷰징이 반드시 나온다.

## 6. 크로스플랫폼 지갑 규칙

| 규칙 | 내용 |
|------|------|
| 지갑은 **계정 단위**다 | 플랫폼과 무관. iOS에서 충전 → Windows에서 소비 정상 |
| 충전 채널은 원장에 기록 | `entry.platform` — 환불 처리 시 어느 채널로 취소할지 판단 근거 |
| 환불 대상 식별 | `refId`(paymentId) → `payments.channel`로 PG/스토어 결정 |
| **혼합 잔액의 환불 우선순위** | 환불은 **특정 결제 건**에 대해 이뤄진다. 잔액이 여러 결제의 혼합이어도 "그 결제의 미사용분"을 계산하려면 **선입선출(FIFO) 소비 가정**을 쓴다 — 약관에 명시 |
| 표시 | 사용자에게는 단일 잔액만 보인다(채널별 잔액 분리 금지 — 복잡도만 늘고 이득 없음) |

**FIFO 소비 가정의 의미**(약관 문구 필요)

> MC는 충전된 순서대로 사용됩니다. 환불 시 해당 결제로 충전된 MC 중 사용되지 않은 수량을 기준으로 환불액을 산정합니다.
