## 1. 왜 과금 구조를 먼저 세우는가

사용자 판단(요청 원문): *"현재의 구조를 살짝 해칠 수 있으나, 우선 이 제도를 만들고 나서 제대로 수정이 되어야 다른 플랫폼(웹클라이언트, iOS, android) 개발 시에도 제대로 구현할 수 있을 것 같아."*

이 판단은 기술적으로 옳다. 근거 3가지:

| 근거 | 내용 |
|------|------|
| **과금은 서버 계약이다** | 과금 게이트는 클라이언트 4종에 각각 구현되는 것이 아니라 **서버가 한 번 강제**하고 클라는 그 결과를 표시한다. 클라를 늘린 뒤에 과금을 넣으면 각 클라에서 "차단 UI"를 4번 재설계해야 하고, 그 사이에 만든 클라는 과금 없는 흐름을 전제로 상태 머신을 굳힌다 |
| **소비 지점이 이미 3곳으로 좁혀져 있다** | 업로드 `prepare`/`commit`(서버 `web/functions/src/services/uploads.ts`)과 프레임 생성(`routes/frames.ts`). 이 3곳에 게이트를 넣는 구조는 it13에서 **이미 검증**됐다 — 지금이 가장 저렴한 시점이다 |
| **모바일은 스토어 정책 때문에 되돌리기가 비싸다** | iOS·Android는 디지털 아이템을 **IAP로만** 팔 수 있다([05 §2](./05-payments-and-platform-policies.md)). 지갑·상품 id·영수증 매핑을 나중에 끼워 넣으면 스토어 심사 리젝을 반복한다 |

**"구조를 해친다"의 실제 크기**(사실 기준): 아래 2개가 전부다. 나머지는 순수 추가다.

| # | 기존 구조 변경 | 파급 |
|---|----------------|------|
| 1 | 개인 프레임 저장 위치(로컬 전용 → 서버 정본 + 로컬 캐시) | 프레임 화면·편집기 저장 경로, 오프라인 동작, [04](./04-custom-frames-billing-and-lifecycle.md) |
| 2 | QR 게이트 판정축(역할 기반 TempUser → 정원 기반 전역) | `QrEffectivePolicy` 입력 확장, `qr-usage` 응답 확장 |

> ✅ **종전 이 표에 있던 두 행은 폐기되어 기존 구조를 건드리지 않는다.** ~~로그아웃 시 로컬 프레임 정리~~ → [04 §5](./04-custom-frames-billing-and-lifecycle.md) **2026-08-07 폐기**(소유권 서명으로 대체). ~~JWT에 `sid` 추가 + 세션 대조~~ → [06](./06-single-session-enforcement.md) **2026-08-10 폐기**. **JWT와 인증 미들웨어는 손대지 않는다**(stateless 유지).

## 2. 용어 (이 세트 전체에서 고정)

| 용어 | 정의 | 주의 |
|------|------|------|
| **MC** | 서비스 내 선불 크레딧의 단위. 현금으로 충전하고, 아이템 구매에만 쓴다. 현금 인출·계정 간 이전 불가 | 화폐가 아니라 **선불 크레딧**이다. 법적 성격은 [09 §6](./09-security-abuse-and-compliance.md) |
| **지갑(wallet)** | 계정별 MC 잔액. 서버 문서 1개 | 클라 표시값은 **캐시**다. 판정 근거로 쓰지 않는다 |
| **원장(ledger)** | 지갑 변동의 append-only 기록. 잔액 = Σ delta | 삭제·수정 금지. 정정은 반대 부호 항목 추가(`adjust`) |
| **아이템(item)** | MC로 사는 것. 소비형(consumable)과 권리형(entitlement)으로 나뉜다 | [01 §5](./01-currency-catalog-and-pricing.md) |
| **권리(entitlement)** | 기간·정원 형태로 계정에 붙는 사용 권리. 예: "QR 하루 50개, 30일" | 잔액이 아니라 **상태**다. 지갑과 별 컬렉션 |
| **정원(allowance)** | 하루에 쓸 수 있는 최대 횟수. 00시(KST)에 리셋 | "잔여 횟수"와 구분: 정원은 상한, 잔여는 상한−사용 |
| **영업일(billingDay)** | `Asia/Seoul` 기준 `yyyy-MM-dd`. 리셋·정산의 유일한 날짜 기준 | 클라 로컬 날짜가 아니다. 서버가 계산 → [03 §4](./03-qr-daily-quota.md) |
| **QR 1회(전송 세션 1건)** | `POST /uploads/commit` **최초 성공** 1건. 파일 개수 무관 | it13이 이미 확정한 단위(`services/uploads.ts` commit 트랜잭션). 재시도는 동일 `sessionId` → 409로 이중집계 차단 |
| **프레임 생성 1건** | 새 `frameTemplates` 문서 1개 생성 성공 | **이름을 바꿔 저장하면 신규 생성**이다(현행 fork 동작) → 과금 함정, [04 §3.3](./04-custom-frames-billing-and-lifecycle.md) |
| **소유자 계정(operator)** | 로그인한 계정. 지갑·정원의 귀속 주체 | 촬영 손님이 아니다(§4) |
| **드라이런(dry-run)** | 차감 없이 "차감했을 것"만 원장에 기록하는 모드 | 가격 확정 전 실사용 계측용 → [10 §2](./10-rollout-testing-and-wbs.md) |

## 3. 무료 / 유료 경계 (제도의 골격)

### 3.1 원칙

| 원칙 | 내용 | 근거 |
|------|------|------|
| P1 | **촬영·합성·로컬 저장은 영구 무료다** | 서버 비용이 0이다(전부 클라 연산 — [`analysis/14`](../analysis/14-media-pipeline-spec.md)). 여기에 과금하면 제품 가치의 본체를 막는다 |
| P2 | **서버 비용을 발생시키는 행위만 과금한다** | QR 전송(Storage 저장 + egress + Firestore write), 개인 프레임 서버 저장(Storage 영구 보관 — TTL 비대상) |
| P3 | **권한(역할)과 과금은 별개 축이다** | 역할은 "할 수 있는가", 과금은 "지금 남았는가". 두 축을 섞으면 결제로 권한이 올라가는 오설계가 된다 → §5 |
| P4 | **게스트(비로그인)는 과금 대상이 아니다** | 지갑이 없다. 게스트는 QR 자체가 불가(현행 `QrEffectivePolicy`: 미로그인 → false) |
| P5 | **무료 티어는 유지하되 남용 비용을 상한한다** | 기존 TempUser 48h/30회는 **평가판**으로 계속 필요하다. 다중 계정 남용은 [09 §3](./09-security-abuse-and-compliance.md) |

### 3.2 기능별 경계표

| 기능 | 무료 | 유료 | 근거·비고 |
|------|:----:|:----:|-----------|

| 공용 기본 프레임 사용 | ○ | — | 매니저 이상이 만든 자산. 게스트도 사용 |

### 3.3 "무료 편집"의 예외 (비용 누수 차단)

편집을 무료로 두면 다음 두 경로로 무한 저장이 가능해진다. 상한을 둔다.

| 경로 | 위험 | 대응(초안) |
|------|------|-----------|
| 같은 프레임을 **이미지만 계속 교체** | Storage write 반복(같은 경로 덮어쓰기라 용량은 1개분, 하지만 write·전송 비용 발생) | 프레임당 **이미지 교체 일 5회** 상한. 초과 시 "잠시 후 다시 시도" (429/`RATE_LIMITED`) |
| **이름을 바꿔 저장** → 신규 문서 | 과금 없이 프레임 개수 증가 | 현행 fork 동작을 **신규 생성으로 과금**한다. UI가 "새 프레임으로 저장됩니다(N MC 차감)"를 명시 → [04 §3.3](./04-custom-frames-billing-and-lifecycle.md) |

## 4. 사용자 프로파일 — 누가 돈을 내는가 (설계의 축)

MC포토는 **한 앱에 두 종류의 사용자**가 있다. 이 구분을 놓치면 UI가 전부 틀어진다.

| 프로파일 | 누가 | 결제 주체 | 촬영자 | 특징 |
|----------|------|-----------|--------|------|
| **B2B-부스**(현행 주 사용자) | 포토부스 운영자가 계정으로 로그인해 두고, 손님이 촬영만 한다 | 운영자(계정 소유자) | 손님(계정 무관) | 촬영 흐름에 결제 UI가 **있어서는 안 된다**. 손님이 운영자 지갑을 소진하는 구조이므로 잔량 관리는 운영자 화면(PIN 게이트 뒤) |
| **B2C-개인**(웹·모바일 확장 시) | 개인이 자기 계정으로 자기 기기에서 촬영 | 본인 | 본인 | 결과 화면에서 즉시 충전 유도가 자연스럽다 |

**설계 규칙**

| # | 규칙 | 이유 |
|---|------|------|
| R1 | 결제·충전 진입점은 **계정/설정 영역(PIN 게이트 뒤)** 에 둔다 | B2B에서 손님이 운영자 지갑에 결제하는 사고 방지. PIN 게이트는 이미 설정·계정 관리 진입에 있다([`analysis/60 §3.4`](../analysis/60-auth-accounts-and-roles.md)) |
| R2 | 촬영 흐름(결과·QR 화면)에서는 **잔량 안내와 "관리자에게 문의" 문구만** 노출한다. CTA(충전 버튼)는 **B2C 프로파일에서만** | it13이 정한 문구 관례와 동일한 방향 |
| R3 | 프로파일 판정은 **설정값**(`BoothMode` 초안: `booth`/`personal`)으로 하고 기본값은 `booth` | 자동 추론(화면 크기·플랫폼)은 오판한다. 웹 키오스크도 booth다 |
| R4 | 프로파일은 **UI 분기 전용**이다. 서버 게이트·가격·정원은 **동일**하다 | 프로파일로 가격을 다르게 하면 우회 인센티브가 생긴다 |

> ⚠️ **미결정**: `BoothMode`를 로컬 설정(장치별)로 둘지, 계정 속성(서버)으로 둘지 → [11 D-08](./11-open-decisions.md). 초안은 **로컬 설정**(같은 계정으로 부스와 개인 기기를 함께 쓰는 경우를 허용).

## 5. 역할 × 과금 매트릭스

역할 위계는 현행 그대로다: **TempUser(0) < User(1) < AdvancedUser(2) < Manager(3) < Admin(4)** ([`analysis/60 §1`](../analysis/60-auth-accounts-and-roles.md)).

| 항목 | 게스트 | temp_user | user | advanced_user | manager | admin |
|------|:---:|:---:|:---:|:---:|:---:|:---:|
| 지갑 보유 | × | ○ | ○ | ○ | ○ | ○ |
| MC 충전(결제) | × | ○ | ○ | ○ | ○ | ○ |
| **QR 전송** | × | △ 무료 티어 | △ 정원 | △ 정원 | △ 정원 | △ 정원 |
| 무료 티어(48h·30회) 적용 | — | **○** | × | × | × | × |
| QR 정원 플랜 구매 | × | ○¹ | ○ | ○ | ○ | ○ |
| **개인 프레임 생성** | × | × | × | **○ 유료** | ○ 유료² | ○ 유료² |
| 공용 기본 프레임 생성·삭제 | × | × | × | × | ○ **무료** | ○ **무료** |
| 타 계정 지갑 조회 | × | × | × | × | △³ | ○ |
| 관리자 MC 지급·회수(`adjust`) | × | × | × | × | × | ○ |
| 전역 한도·킬스위치 변경 | × | × | × | × | × | ○ |

¹ temp_user가 유료 플랜을 사면 무료 티어 판정을 **우회**하는가? → **아니다.** 무료 티어와 유료 정원은 OR가 아니라 **유료 우선 소비**다. 상세 [03 §3.3](./03-qr-daily-quota.md).
² manager·admin이 **개인 프레임**을 만들면 과금한다(개인 스코프 저장은 동일 비용). 공용 기본 프레임 생성은 무료 — 자사 운영 자산이므로. 이 비대칭은 [04 §3.2](./04-custom-frames-billing-and-lifecycle.md)에서 명시.
³ manager의 타 계정 지갑 조회는 `canManage` 위계를 따른다(잔액 조회만, 조정 불가) → [07 §3.6](./07-api-and-data-contract.md).

> ⚠️ **결제로 역할이 올라가지 않는다.** "MC를 사면 고급 유저가 된다"는 설계는 채택하지 않았다. 이유: ① 역할은 관리 위계(계정 관리·공용 프레임 권한)를 포함하므로 결제로 승격하면 권한 상승 경로가 열린다 ② 현행 `canSetRole` 매트릭스(서버 강제)와 충돌한다([`analysis/31 §4.7`](../analysis/31-backend-api-reference.md)). **프레임 생성 권한이 필요한 계정은 관리자가 `advanced_user`로 승격**하고, 승격된 계정이 **생성 시 과금**한다. → 대안(자동 승격 상품)은 [11 D-07](./11-open-decisions.md)에 기록.

## 6. 불변식 12개 (구현 시 회귀 테스트로 고정) — **B11 폐기 후 유효 11개**

| # | 불변식 | 위반 시 결과 | 검증 방법 |
|---|--------|--------------|-----------|
| **B1** | 잔액 변동은 **원장 항목 없이** 발생하지 않는다. `balanceMc == Σ entries.deltaMc` | 분쟁 시 증명 불가, 잔액 유실 은폐 | 원장 재계산 감사 잡 + 단위 테스트 |
| **B2** | 잔액은 **음수가 될 수 없다**. 부족하면 거래 전체를 거부한다 | 마이너스 잔액으로 무한 사용 | 트랜잭션 내 검사 + 테스트 |
| **B3** | 같은 **멱등키**로 두 번 요청하면 두 번 차감되지 않는다(동일 결과 반환) | 네트워크 재시도로 이중 차감 → 환불 민원 | 멱등 문서 + 동시 요청 테스트 |
| **B4** | **소비 판정과 실제 차감은 같은 트랜잭션**에서 일어난다 | 판정 후 차감 실패 → 무료 사용 또는 이중 차감 | it13 commit 트랜잭션 패턴 재사용(`services/uploads.ts`) |
| **B5** | 클라이언트가 보낸 **잔액·정원·가격은 어떤 판정에도 쓰이지 않는다** | 위조로 무한 사용 | 서버 코드 리뷰 + 위조 요청 테스트 |
| **B6** | 시각 판정(리셋·프로레이션·만료)은 **서버 시각(UTC) + KST 환산**만 쓴다 | 클라 시계 조작으로 정원 무한 리셋 | 순수 함수 테스트(경계 시각) |
| **B7** | **무제한 상품은 존재하지 않는다.** 모든 경로에 일 상한이 있고 전역 킬스위치가 그 위에 있다 | Storage/egress 폭주 | 카탈로그 스키마에 `dailyMax` 필수 + 상한 없는 값 거부 |
| **B8** | 유료 결제 성공은 **서버 영수증 검증 후**에만 MC를 지급한다 | 위조 영수증으로 무료 충전 | 검증 실패 경로 테스트 |
| **B9** | 로컬에 남는 개인 프레임은 **캐시**이며, 서버 저장 성공 **후에만** 기록한다 | 서버에 없는 로컬 전용 프레임 발생 → 로그아웃 삭제로 영구 유실 | 저장 순서 테스트(웹 Step15 원자성 선례) |
| **B10** | 로그아웃 purge는 **`{계정}_` 접두 파일만** 지운다. 공용(접두 없음)은 절대 지우지 않는다 | 공용/번들 프레임 유실 = 전 사용자 영향 | `LocalFrameStore` 규약 테스트 + 계정 id에 `_` 포함 케이스 |
| ~~**B11**~~ | ~~활성 세션이 교체되면 이전 세션의 **과금 유발 요청은 거부**된다(`SESSION_SUPERSEDED`)~~ **❌ 폐기(2026-08-10 — [06](./06-single-session-enforcement.md) 폐기와 함께)** | — | **번호를 재사용·재배열하지 않는다**([10 §G13](./10-rollout-testing-and-wbs.md)·[07](./07-api-and-data-contract.md)이 참조). ⚠️ 이 불변식이 막던 **정원 이중 소비는 이제 허용**된다 → 유일한 방어는 [02 §경합](./02-wallet-ledger-and-entitlements.md)의 commit 트랜잭션 직렬화(정원 **초과**만 차단, 이중 **소비**는 차단하지 않는다) |
| **B12** | 과금 기능이 꺼져 있어도(`killSwitch`) **무제한이 되지 않는다** — 무료 티어 한도로 복귀한다 | 킬스위치가 비용 사고를 유발 | 플래그 off 상태 게이트 테스트 |

## 7. 소비 지점 3곳 (게이트를 넣는 유일한 장소)

| # | 지점 | 현행 | 추가되는 것 | 문서 |
|---|------|------|-------------|------|
| ① | `POST /uploads/prepare` | `requireApiKey` + `optionalBearer`. TempUser면 한도 선검사 → 403(서명 URL 미발급) | 정원 선검사(로그인 전원). **차감하지 않는다**(선검사만) | [03 §6.1](./03-qr-daily-quota.md) |
| ② | `POST /uploads/commit` | 위 + TempUser는 트랜잭션(중복 409 → 한도 재판정 → 문서 생성 → `qrUsedCount+1`) | **모든 로그인 계정**을 트랜잭션 경로로. usage 문서 +1, 필요 시 MC 차감(오버리지) | [03 §6.2](./03-qr-daily-quota.md) |
| ③ | `POST /frames`(개인 스코프) | 존재하지 않음(현행은 power 공용 전용, `routes/frames.ts:58-80`) | 신설. `CanWriteFrames` + 프레임 생성권 차감 트랜잭션 | [04 §4](./04-custom-frames-billing-and-lifecycle.md) |

> ✅ **왜 3곳으로 충분한가**: 파일 바이트는 서명 URL로 Storage에 직접 올라가므로(백엔드 미경유, [`analysis/31 §5.2`](../analysis/31-backend-api-reference.md)) **서명 URL 발급을 막는 것이 곧 과금 차단**이다. it13이 prepare에서 거부하는 이유가 정확히 이것이다. 다운로드 페이지 소비(egress)는 commit된 세션에만 발생하므로 ②가 상류를 막는다.

> ⚠️ **하지만 ①만으로는 부족하다**: prepare 성공 후 15분 안에 여러 번 PUT할 수 있고, 정원은 그 사이에 소진될 수 있다. 그래서 ②의 트랜잭션 재판정이 최종 권위다(it13 §5.1의 결론과 동일).

## 8. 설계 대안과 채택 근거

| 쟁점 | 대안 | 채택 | 근거 |
|------|------|:----:|------|
| 과금 단위 | (a) 현금 직접 결제(건당) / (b) **MC 크레딧 2계층** | **(b)** | 사용자 요구. 부수 효과로 ① 소액 결제 수수료 회피(1회 200원 결제는 PG 수수료가 잠식) ② IAP 상품 수 최소화 ③ 프로모·보상 지급 통로 확보 |
| 잔액 저장 | (a) `users` 문서 필드 / (b) **`wallets` 별 컬렉션 + 원장** | **(b)** | `users`는 인증·권한 문서다. 돈을 섞으면 권한 read마다 지갑 경합이 생기고 감사 이력이 없다. 웹 접근은 이미 전면 차단이라 규칙 부담도 없다([`analysis/40 §5.1`](../analysis/40-database-firestore-and-storage-schema.md)) |
| QR 과금 형태 | (a) 1회당 MC 차감 / (b) **일일 정원 플랜** / (c) 하이브리드 | **(c)** = 플랜 기본 + 초과 시 1회당 차감(옵션) | 사용자 문장("하루 제한", "00시 초기화", "첫날 일할")이 (b)를 지시한다. (a)만 두면 "하루 제한"이 성립하지 않고, (b)만 두면 정원 초과 시 돈을 내고도 못 쓴다 → [03 §2](./03-qr-daily-quota.md) |
| 무료 티어 | (a) 폐지 / (b) **유지(temp_user)** | **(b)** | 신규 SSO 계정은 전원 temp_user다(서버 강제, [`analysis/31 §4.2`](../analysis/31-backend-api-reference.md)). 무료 체험 없이 결제부터 요구하면 온보딩이 끊긴다. 남용 상한은 [09 §3](./09-security-abuse-and-compliance.md) |
| 정원 리셋 | (a) 스케줄러가 매일 0시에 전 계정 리셋 / (b) **lazy reset(읽을 때 판정)** | **(b)** | 서버리스에서 (a)는 계정 수만큼 write가 발생하고 실패 시 정합성이 깨진다. (b)는 write 0, 판정은 순수 함수 → [03 §4.2](./03-qr-daily-quota.md) |
| 세션 통제 | (a) **무통제** / (b) ~~단일 활성 세션~~ / (c) ~~좌석(seat) 수 상품화~~ | **(a)** *(2026-08-10 재결정 — 종전 결론 "(b) 기본 + (c) 확장 여지"를 폐기)* | **사용량 과금이므로 세션 수를 통제할 이유가 없다.** 과금 단위가 QR 전송 세션 1건이므로([03](./03-qr-daily-quota.md)) 여러 기기가 나눠 써도 총 청구는 사용량에 비례한다. 프레임도 다운로드 1회만 과금한다. 부수 이득으로 **키오스크 다중 PC 운영과의 충돌이 소멸**했다. (c)는 "동시 세션 수" 정의가 무효가 되어 상품 축 재설계 대상 → [11 D-26](./11-open-decisions.md) · 이력 [06](./06-single-session-enforcement.md) |
| 개인 프레임 저장 | (a) 로컬 유지(현행) / (b) **서버 정본 + 로컬 캐시** | **(b)** | 사용자 요구(DB 저장 + 로그아웃 삭제). 로컬 전용인 채로 로그아웃 삭제만 하면 **영구 데이터 유실**이다 → [04 §2](./04-custom-frames-billing-and-lifecycle.md) |

## 9. 성공 기준 (제도가 "제대로 만들어졌다"의 정의)

| # | 기준 | 측정 |
|---|------|------|
| S1 | 클라이언트를 위조해도 무료 사용량이 늘지 않는다 | 위조 요청 테스트: 잔액·정원·시각·역할 조작 5종 전부 서버 거부 |
| S2 | 이중 차감·이중 지급이 0건이다 | 동시 요청·재시도·웹훅 중복 시나리오 테스트 |
| S3 | 어떤 사용자 조작으로도 하루 상한을 넘길 수 없다 | 플랜 최대치 + 하드캡 경계 테스트 |
| S4 | 결제 실패·환불·취소 후 사용 권리가 남지 않는다 | 환불 → 즉시 회수 테스트 |
| S5 | 잔액 분쟁 시 **원장으로 전 이력을 재현**할 수 있다 | 원장 합계 == 잔액 감사 통과 |
| S6 | 과금 도입 후에도 **게스트 촬영 흐름은 무변경**이다 | 기존 회귀 테스트 전량 통과(게스트 경로) |
| S7 | 새 플랫폼(웹·iOS·Android)이 [07](./07-api-and-data-contract.md) 문서만 보고 구현 가능하다 | 와이어 계약 완결성 리뷰 |
| S8 | 비용이 매출을 앞지르는 상황을 **사전에 감지**한다 | 단위 원가 대비 가격 하한 준수 + GCP 예산 알림 → [01 §8](./01-currency-catalog-and-pricing.md) |
