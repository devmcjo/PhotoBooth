## 1. 위협 모델 (T1~T15 · **T9 폐기 → 유효 14종**)

각 위협에 대해 **1차 방어**(구조적)와 **2차 방어**(탐지·완화)를 나눈다.

| # | 위협 | 공격 방법 | 1차 방어 | 2차 방어 |
|:--:|------|-----------|----------|----------|
| **T1** | 클라 위조로 무료 사용 | 잔액·정원·역할·가격을 조작해 전송 | **모든 판정은 서버**(B5). 클라 값은 어떤 판정에도 쓰이지 않는다 | 서버 로그에 클라 주장값 vs 서버값 불일치 기록 |
| **T2** | 시계 조작으로 정원 리셋 | 기기 시각을 다음 날로 변경 | 서버 시각만 사용(B6). `billingDay`는 서버가 계산 | — |
| **T3** | 다중 계정으로 무료 티어 파밍 | Gmail 별칭·신규 계정으로 48h/30회 반복 | 계정 생성 = Google SSO(전화·이메일 검증된 계정 필요) | §3.1 기기 단위 무료 상한 + 도메인 정책 |
| **T4** | 영수증 위조·재사용 | 위조 영수증, 다른 계정 영수증 재사용 | 스토어 서버 API 검증(B8) + `transactionId` 유니크 | 동일 트랜잭션 다계정 시도 알림 |
| **T5** | 웹훅 위조 | 우리 웹훅에 가짜 결제 성공 전송 | provider **서명 검증** + provider 조회 API로 금액 재확인 | 서명 실패 알림·차단 |
| **T6** | 이중 지급·이중 차감 | 재시도·중복 웹훅 | 멱등키 + provider 거래 id 유니크(B3) | 원장 정합성 감사(§2) |
| **T7** | 환불 후 사용(무료 취득) | 결제 → 즉시 소비 → 환불 요청 | 환불 시 즉시 회수 + 부족분 기록([02 §5.3](./02-wallet-ledger-and-entitlements.md)) | 환불 이력 N회 → 지갑 동결(§4) |
| **T8** | 정원 공유(계정 공유) | 한 계정을 여러 부스가 사용 | **수용 — 사용량 과금이므로 매출 누수가 아니다.** 나눠 쓰든 한 대가 다 쓰든 총 청구는 사용량에 비례한다(2026-08-10 [06](./06-single-session-enforcement.md) 폐기로 차단 수단 없음) | 탐지만 유지: **계정별 전송 성공의 시간대·동시성 분포**(같은 계정이 같은 분에 2건 이상 commit → 다중 사용 신호). 세션 없이 측정 가능한 유일한 지표다 |
| ~~**T9**~~ | ~~세션 위조로 다중 사용~~ | ~~`deviceId` 위조로 세션 여러 개~~ | **❌ 폐기(2026-08-10)** — 세션 레지스트리가 없으므로 위조할 세션도, `maxSessions` 상한도 없다. 다중 사용은 T8로 흡수(수용) | 번호 재사용 금지 |
| **T10** | prepare 남용(고아 파일) | 정원 없이 prepare만 반복해 Storage에 파일 업로드 | 정원 초과 시 **서명 URL 미발급**. 정원 있어도 commit 없이는 다운로드 페이지 미생성 | prepare rate limit(분 20회) + **고아 파일 정리**(§3.5) |
| **T11** | 대용량 프레임 업로드 | 40MB PNG로 Storage 비용 유발 | 서명에 `x-goog-content-length-range` 조건(F-2, [04 §2.2](./04-custom-frames-billing-and-lifecycle.md)) | 계정당 10개 상한 |
| **T12** | 카드 도난·분쟁(chargeback) | 도난 카드로 충전 후 소비 | PG 이상거래 탐지(FDS)에 의존 | 신규 계정 고액 결제 알림 + 소비 지연(§4.3) |
| **T13** | 내부자·관리자 오조작 | 임의 MC 지급, 잔액 조작 | admin만 가능 + 사유 필수 + 원장 불변(L1) + 1회 상한 | 지급·조정 알림 + 월 감사 |
| **T14** | 봇·스크립트 대량 요청 | API 자동 호출로 비용 유발 | 게이트 키 + Bearer + rate limit | 전역 일 상한·킬스위치(B7) |
| **T15** | **계정 탈취 시 즉시 차단 수단 없음** *(2026-08-10 신설)* | 탈취된 계정으로 정원·잔액을 소진 | **없다.** 종전에는 `POST /admin/sessions/{userId}/revoke-all`로 활성 세션을 끊었으나 [06](./06-single-session-enforcement.md) 폐기와 함께 사라졌다 → 탈취를 인지해도 **JWT 8시간 만료를 기다려야 한다** | 대체안 **`users.disabled` 플래그**(미구현): 세우면 인증 미들웨어가 다음 요청부터 401. 세션 레지스트리보다 싸고(이미 계정 문서를 읽는 경로가 많다) 목적을 달성한다 → [11 D-27](./11-open-decisions.md) |

> ⚠️ **T8 재검토 조건(중요)**: **정액 요금제**(무제한·대량 정액)를 도입하는 순간 T8이 **다시 실질 위협**이 된다 — 정액에서는 계정 공유가 곧 매출 누수다. 현재의 "수용" 판정은 **사용량 과금 모델을 전제**로만 성립한다. 상품 구성이 바뀌면 이 행을 먼저 다시 본다.

> ✅ **T15의 심각도는 낮다**(그러나 0은 아니다): ① 신원이 Google SSO 단독이라 비밀번호 유출 경로가 없다 ② 토큰이 **메모리 전용**이라 앱을 닫으면 사라진다(디스크·localStorage 저장 금지) ③ 8시간 상한이 이미 있다. 결제를 도입하기 전까지는 급하지 않다.

> 📌 **번호 규칙**: T9는 폐기됐고 T15가 신설됐다. **번호를 재사용·재배열하지 않는다** — 다른 문서가 T번호로 교차 참조한다.

## 3. 어뷰징 시나리오와 대응

### 3.1 무료 티어 파밍 (T3) — 가장 현실적인 남용

**현행 노출**: 신규 SSO 계정은 전원 `temp_user`이고 48시간·30회 무료다. Gmail은 `user+alias@gmail.com`·점(`.`) 변형으로 사실상 무한 계정을 만들 수 있으나, 서버가 **email을 소문자 정규화만** 하므로 별칭이 다른 계정으로 취급될 수 있다.

| 대응 | 내용 | 강도 | 채택 |
|------|------|:---:|:---:|
| (a) Gmail 별칭 정규화(`+` 이후 제거, `.` 제거) | 같은 계정으로 수렴 | 중 | **권장** — 단 다른 도메인에는 적용 불가(도메인별 규칙이 달라 위험) |
| (b) **기기 단위 무료 상한** | `deviceId`당 무료 전송 총 N회(계정 무관) | 강 | **권장** — 기기 1대로 계정을 바꿔가며 쓰는 패턴을 직접 막는다 |
| (c) 도메인 화이트리스트(`GOOGLE_ALLOWED_HD`) | 사내·계약 고객 한정 | 매우 강 | B2B 전용 배포에 적합. B2C 확장 시 불가 |
| (d) 무료 티어 축소(30회 → 10회) | 남용 이득 감소 | 중 | 온보딩 저해 트레이드오프 |
| (e) 무료 티어 폐지 | — | 최강 | ✕ 온보딩 붕괴 |

> ✅ **권장 조합**: (a) + (b). (b)는 `usage/_device_{deviceIdHash}` 문서로 구현하고 상한 **총 50회**(초안)를 둔다. 기기 교체·초기화로 우회 가능하지만 비용 대비 이득을 충분히 낮춘다.

> ⚠️ **(b)의 부작용**: 정당한 부스가 손님 계정으로 여러 번 로그인해 쓰는 경우(가능성 낮음)에 걸릴 수 있다. 상한 도달 시 문구는 "이 기기의 무료 사용량이 모두 소진되었습니다"로 하고, **유료 정원에는 영향을 주지 않는다**(유료는 계정 귀속).

> ⚠️ **(b)의 `deviceId`는 폐기된 06 §5.3의 세션 기기 식별자와 다른 것이다**(2026-08-10 확인). 06 폐기로 **세션 목적의 기기 식별자 수집은 사라졌지만**, (b)를 채택하면 **어뷰징 방어 목적으로 기기 식별자를 다시 수집**해야 한다 — 즉 §7의 개인정보 표면 축소는 **(b)를 채택하지 않는 경우에만** 온전히 성립한다. (b) 채택 시에는 §7의 해시+salt 규약을 그대로 적용한다. 채택 여부는 [11](./11-open-decisions.md)에서 관리한다.

### 3.2 환불 남용 (T7)

| 패턴 | 대응 |
|------|------|
| 충전 → 즉시 전량 소비 → 환불 요청 | 미사용분만 환불(부족분 기록). 사용분은 환불 불가 → **경제적 이득 0** |
| 반복 환불(스토어 경유) | 환불 3회 이상 계정: IAP 구매 차단 + 지갑 동결(수동 해제) |
| chargeback | PG 통보 시 즉시 회수 + 동결. 재발 계정은 PG 차원 차단 요청 |

### 3.3 신규 계정 고액 결제 (T12)

| 규칙 | 내용 |
|------|------|
| 탐지 | 계정 생성 후 24시간 내 누적 결제 5만원 초과 |
| 조치(초안) | 알림 + **소비 지연 없음**(정상 고객 방해 금지). 도난 카드는 PG FDS가 1차 방어 |
| 강화 옵션 | 24시간 내 환불 요청이 오면 즉시 회수(정상 경로) |

> ⚠️ **과잉 방어를 하지 않는다.** 신규 계정의 결제를 막으면 정상 신규 고객을 잃는다. 손실은 chargeback 수수료 수준이며, 그 비용이 고객 이탈 비용보다 작다.

### 3.4 정원 공유 (T8) — **수용(2026-08-10)**

| 항목 | 내용 |
|------|------|
| **판정** | **막지 않는다.** 사용량(QR 전송 세션 1건) 과금이므로 계정을 공유해도 **총 청구는 사용량에 비례**한다 → 매출 누수가 아니다(사용자 결정) |
| 관측 지표(차단 아님) | **계정별 전송 동시성** — 같은 계정이 같은 분에 2건 이상 commit. 세션 레지스트리 없이 측정 가능한 유일한 신호다 |
| 지표의 용도 | 좌석/다점포 상품의 **수요 판단**([11 D-26](./11-open-decisions.md))에만 쓴다. 경고·차단·안내를 하지 않는다 |
| 조치 | **없다.** 종전의 "기기 추가 문의" 안내는 좌석 상품(동시 세션 수 판매)을 전제로 했고, 그 상품 정의가 폐기됐다 |
| ⚠️ 남는 리스크 | **정원 이중 소비** — 2대가 동시에 쓰면 일일 정원이 2배 속도로 준다. 과금 정확성 문제는 아니지만 "내가 안 썼는데 정원이 없다"는 **체감 손실**이 남고, 기기 식별자를 수집하지 않으므로 **어느 부스가 썼는지 답해줄 수 없다** → 완화는 잔량 상시 노출([03 §8](./03-qr-daily-quota.md))과 전송 이력 조회([11 D-25](./11-open-decisions.md)) |
| ⚠️ 재검토 조건 | **정액 요금제 도입 시** 이 수용 판정은 무효다(§1 T8 주 참조) |

> ❌ **종전 규격(2026-08-10 폐기)**: 의심 신호를 "세션 교체 일 20회 초과"·"같은 계정의 서로 다른 `deviceId` 5개 이상/주"로 두고 좌석 상품 안내를 띄우는 설계였다. 세션 레지스트리와 기기 식별자가 둘 다 없어져 **측정 자체가 불가능**하다.

### 3.5 고아 파일 정리 (T10)

| 항목 | 내용 |
|------|------|
| 발생 | prepare로 서명 URL을 받아 PUT까지 했으나 commit을 하지 않은 경우 → `results/{sid}/` 파일만 존재, 문서 없음 |
| 현행 | **GCS Lifecycle(age 3일)이 `results/` 전체를 삭제**하므로 자동 정리된다([`analysis/40 §6.3`](../analysis/40-database-firestore-and-storage-schema.md)) ✅ |
| 남는 위험 | 3일간의 저장 비용 + 다운로드 URL을 아는 사람은 파일 접근 가능(문서 없어도 토큰 URL은 유효) |
| 추가 대응 | prepare rate limit(계정 분 20회) + 고아 발생 건수 모니터링. **별 정리 함수는 만들지 않는다**(Lifecycle이 이미 커버) |

### 3.6 프레임 관련 남용

| 패턴 | 대응 |
|------|------|
| 이미지 무한 교체 | 프레임당 일 5회 상한([00 §3.3](./00-scope-principles-and-model.md)) |
| 환급 창 악용(생성→삭제 반복) | 10분 창 + 일 3회 상한([04 §3.4](./04-custom-frames-billing-and-lifecycle.md)) |

| 대용량 이미지 | F-2 서명 조건 |

## 6. 국내 법규 쟁점

### 6.1 MC의 법적 성격 — 선불전자지급수단인가 (**변호사 확인 필수**)

| 쟁점 | 이해(참고) | 우리 설계의 위치 |
|------|-----------|------------------|
| 전자금융거래법상 **선불전자지급수단** 정의 | ① 이전 가능한 금전적 가치가 전자적으로 저장 ② **발행인 외 제3자**로부터 재화·용역 구입에 사용 ③ 구입 가능 업종이 **2개 이상** 등의 요건 | MC는 **자사 서비스에서만** 쓰이고 **제3자 가맹점이 없다** → 정의에 해당하지 않을 가능성이 높다 |
| 2024 개정(선불업 규제 강화) | 등록 면제 기준(발행잔액·총발행액)과 적용 제외 요건이 정비됐다 | 자사 전용 + 소규모이면 등록 대상이 아닐 가능성이 높다 |
| 우리가 취한 안전 조치 | **계정 간 이전 불가 · 현금화 불가 · 제3자 가맹점 없음 · 자사 재화만**([01 §2](./01-currency-catalog-and-pricing.md)) | 세 요건 중 ①②를 모두 회피하는 설계 |
| 확인이 필요한 시점 | 서비스 개시 전 + 누적 미사용 잔액이 커질 때 | [11 D-19](./11-open-decisions.md) |

> ⚠️ **설계 상 절대 하지 말 것**(규제 진입을 유발한다): 계정 간 MC 선물·이전, 현금 환급(결제 취소가 아닌 인출), 제3자 사업자 가맹점 결제, MC로 다른 회사 상품 구매.

### 6.2 전자상거래법 — 청약철회와 환불

| 쟁점 | 이해 | 우리 정책 |
|------|------|-----------|
| 디지털 콘텐츠의 청약철회 | 원칙 7일. 단 **사용을 개시한 콘텐츠**는 철회를 제한할 수 있다(고지·조치 요건 충족 시) | **미사용 MC는 7일 내 전액 환불.** 사용분은 환불 제외([05 §5.1](./05-payments-and-platform-policies.md)) |
| 고지 의무 | 철회 제한 사실을 **구매 전에 명확히** 알려야 한다 | 구매 확인 모달 + 상점 하단 환불 정책([08 §4.1·§10](./08-ui-ux-and-copy.md)) |
| 표시 의무 | 가격(VAT 포함 총액)·거래조건·사업자 정보 | 상점 화면 + 사업자정보 페이지 |
| 소비자 분쟁 해결 | 소비자분쟁해결기준 준용 | 고객센터 창구 운영 |

### 6.3 콘텐츠 이용자 보호

| 항목 | 내용 |
|------|------|
| 콘텐츠산업진흥법·이용자보호지침 | 결제 취소·환불 절차를 약관에 명시, 미성년자 결제 보호, 서비스 중단 시 이용자 보호 |
| 서비스 종료 시 | **미사용 MC 처리 방침을 약관에 명시**(환불 또는 유효기간 내 소진 안내). 사전 고지 기간(권장 30일 이상) |

### 6.4 미성년자 결제

| 쟁점 | 대응 |
|------|------|
| 민법상 미성년자 계약 취소권 | 법정대리인 동의 없는 결제는 취소될 수 있다 |
| PG 채널 | 결제 전 "만 19세 미만은 법정대리인의 동의가 필요합니다" 고지 + 약관 조항 |
| IAP 채널 | 스토어의 가족 결제 통제가 1차 방어 |
| 실무 | 취소 요청 시 **미사용분 환불 + 사용분도 다툼 여지** → 고액 결제 알림(§3.3)으로 조기 인지 |
| B2B 특성 | 부스 운영자는 사업자·성인이 대부분이라 리스크가 낮다(B2C 확장 시 중요도 상승) |

### 6.5 개인정보

| 항목 | 방침 |
|------|------|
| 결제 정보 | **카드번호를 저장·전송하지 않는다**(PG 결제창이 처리). PCI-DSS 범위 회피 |
| 저장하는 것 | `paymentId`, 금액, 상태, provider 거래 id, 마스킹된 수단명(예: `카드`) |
| `deviceId` | **세션 목적으로는 수집하지 않는다**(아래 축소 기록). 단 §3.1 **(b) 기기 단위 무료 상한을 채택하면** 어뷰징 방어 목적으로 필요하다 → 그때는 하드웨어 식별자 **원문 금지, 해시 + 앱 salt** 규약을 적용한다 |
| 처리 위탁 | PG·스토어·Google Cloud를 개인정보처리방침에 위탁·국외이전으로 명시 |
| 최소 수집 | IP·위치를 저장하지 않는다 |

> ✅ **개인정보 표면이 줄었다(2026-08-10)**: 단일 세션 강제([06](./06-single-session-enforcement.md)) 폐기로 **로그인 세션 목적의 기기 식별자를 아예 수집하지 않는다.** 종전 설계는 플랫폼별 원천 4종(Windows `MachineGuid` / 웹 `localStorage` UUID / iOS IDFV / Android `ANDROID_ID`)을 각각 구현하고, 그 해시·salt·보존을 개인정보처리방침에 기재하고, 세션 문서에 `deviceId`·`deviceLabel`·`lastSeenAt`을 계정별로 쌓을 계획이었다. **그 전부가 사라졌다** — 처리방침 기재 항목이 줄고, 기기-계정 연결 기록이 생기지 않는다.
>
> ⚠️ **단, 이 축소는 §3.1 (b)를 채택하지 않는 경우에만 온전하다.** (b)는 06과 무관한 별개 설계(다중계정 파밍 방어)이며 자체적으로 기기 식별자를 요구한다.

## 7. 회계 · 세무

### 7.1 수익 인식

| 시점 | 회계 처리 |
|------|-----------|
| MC 충전(결제 승인) | **선수금(부채)** 인식. 매출 아님 |
| MC 소비(아이템 구매) | 선수금 감소 → **매출 인식** |
| 무상 지급(`grant`) | 부채 인식하지 않음(마케팅비 처리 검토) |
| 환불 | 선수금 감소 + 현금 유출 |
| 장기 미사용 잔액 | **유효기간 없음** 정책이므로 부채로 계속 유지. 낙전(잡이익) 인식은 세무 검토 필요 → [11 D-20](./11-open-decisions.md) |
| 스토어 수수료 | 매출 총액 vs 순액 인식 판단 필요(통상 총액 인식 + 수수료 비용) — 세무 검토 |

> ✅ **원장이 회계의 근거 자료가 된다**: `type`별 집계(`purchase`·`spend`·`refund`·`grant`)가 그대로 선수금 증감·매출 인식 근거다([02 §2.4](./02-wallet-ledger-and-entitlements.md)). `type`을 6종으로 고정한 이유(L4).

| 8 | 환불 방법 | PG는 자사 처리, 스토어 결제는 스토어 요청 |
| 9 | 이용 제한 | 부정사용·환불 남용 시 지갑 동결·이용 제한 |
| 10 | **정원의 계정 귀속** *(2026-08-10 내용 교체 — 종전 "단일 세션" 조항 폐기)* | ~~동일 계정 동시 접속 제한·강제 로그아웃 가능성~~을 **삭제**한다(제한하지 않으므로 고지할 것이 없다). 대신 **"일일 정원은 계정에 귀속되며 같은 계정으로 접속한 모든 기기가 이를 공유한다"**를 명시한다 — 여러 부스가 한 계정을 쓸 때 "내가 안 썼는데 정원이 없다"는 분쟁의 근거가 되므로, 제한이 없다는 사실보다 **공유된다는 사실**을 고지하는 것이 실익이 있다 |
| 11 | 데이터 삭제 | 계정 삭제 시 프레임·잔액 소멸. ⚠️ 종전의 "로그아웃 시 기기 내 개인 프레임 삭제"는 [04 §5](./04-custom-frames-billing-and-lifecycle.md) **2026-08-07 폐기**(소유권 서명으로 대체)이므로 **약관에 넣지 않는다** |
| 12 | 서비스 변경 | 가격·상품 구성 변경 절차와 사전 고지(권장 30일, 기존 보유 권리는 유지) |
| 13 | 미성년자 | 법정대리인 동의, 취소권 |
| 14 | 사업자 정보 | 상호·대표자·사업자번호·통신판매업신고번호·주소·연락처·개인정보책임자 |
| 15 | 분쟁 해결 | 관할·준거법, 소비자분쟁해결기준 |

> ⚠️ **6번은 특히 중요하다**: 프로레이션은 사용자가 예상하지 못하는 규칙이다. 약관 + 구매 확인 모달 + 상점 설명 **3곳에 동일하게** 명시해야 "돈은 냈는데 오늘 15개만 준다"는 분쟁을 막을 수 있다.
