## 1. 왜 과금 문서에 세션이 들어오나

| 이유 | 설명 |
|------|------|
| **정원 이중 소비** | 같은 계정이 2대에서 동시에 촬영하면 정원이 2배 속도로 소진된다. 이는 과금 정확성 문제가 아니라 **사용자 체감 손실**이다("내가 안 썼는데 정원이 없다") |
| **정원 공유 = 계정 공유 유인** | 하루 200개 플랜을 여러 부스가 나눠 쓰면 상품 단가가 무의미해진다. 좌석 개념 없이 정원만 팔면 **계정 공유가 최적 전략**이 된다 |
| **프레임 로컬 purge의 전제** | 로그아웃 시 로컬 프레임을 지우려면 "지금 이 기기가 이 계정의 세션인가"가 서버에서 판정 가능해야 한다([04 §5](./04-custom-frames-billing-and-lifecycle.md)) |
| **부정 결제 대응** | 계정 탈취 시 활성 세션을 끊는 수단이 필요하다(현재는 **토큰 8시간 만료를 기다릴 수밖에 없다**) |

## 2. 현행 사실 (제약 조건)

| # | 사실 | 근거 | 함의 |
|---|------|------|------|
| 1 | JWT는 **stateless**다. 클레임 `{sub, role, iat, exp}`, 만료 8시간, **갱신 엔드포인트 없음** | [`analysis/31 §2.2`](../analysis/31-backend-api-reference.md) | 서버가 세션을 끊을 수단이 **현재 전혀 없다** |
| 2 | 서버에 활성 세션·기기 레지스트리가 **없다** | `web/functions/src/services/*` 전수 | 신설 필요 |
| 3 | 토큰은 **메모리 전용**이다(디스크·localStorage 금지) | `BackendSession.cs`, `webclient/src/shell/authStore.ts:5-13` | 앱 재시작 = 재로그인. **세션 수가 자연히 적다**(설계에 유리) |
| 4 | 로그아웃은 `CurrentUser == null` 통지 지점에서 토큰까지 폐기한다 | `BackendSessionSynchronizer.cs`, `authStore.installTokenLifecycle` | 강제 로그아웃도 **같은 지점**을 재사용하면 사각이 없다 |
| 5 | 웹은 401을 **한 곳**(`backendClient` 401 분기 → `handleSessionExpired`)에서 처리하고 멱등이다 | `webclient/src/shell/sessionExpiry.ts` | `SESSION_SUPERSEDED`도 같은 배선에 얹으면 토스트 중복이 없다 |
| 6 | 서버 → 클라 **푸시 채널이 없다**(FCM 미사용, Firestore 실시간 구독은 `users` 접근 차단) | [`analysis/40 §5.1`](../analysis/40-database-firestore-and-storage-schema.md) | 강제 로그아웃 팝업은 **폴링(하트비트)** 으로만 가능 |
| 7 | 유휴 타임아웃·홈 복귀는 **로그아웃하지 않는다**(it8 A1) | [`analysis/60 §3.5`](../analysis/60-auth-accounts-and-roles.md) | 유휴 상태에서도 세션은 살아 있다 → 하트비트가 필요한 이유 |
| 8 | 업로드는 **선택적 Bearer**다(무토큰 게스트 허용) | [`analysis/31 §2.1`](../analysis/31-backend-api-reference.md) | 세션 검증은 "토큰이 있을 때만" 적용해야 게스트가 깨지지 않는다 |

## 3. 정책 선택 (사용자 요구의 "또는"을 해소)

사용자 요구에 두 안이 병기돼 있다: **(ⓐ 새 로그인이 기존을 밀어낸다) 또는 (ⓑ 여러 PC 동시 로그인을 막는다)**. 이는 같은 문제의 두 해법이며 UX가 정반대다.

### 3.1 세 가지 정책

| 정책 | 규칙 | 새 로그인 시 | 장점 | 단점 |
|------|------|--------------|------|------|
| **S1 · 마지막 우선**(ⓐ) | 활성 세션은 1개. 새 로그인이 항상 성공하고 기존 세션이 끊긴다 | 기존 기기 → 강제 로그아웃 팝업 | **잠김이 없다**(기기 분실·앱 강제종료·크래시 후에도 로그인 가능) | 두 사람이 번갈아 로그인하면 서로를 밀어낸다(핑퐁) |
| **S2 · 선점 우선**(ⓑ) | 활성 세션이 살아 있으면 새 로그인을 **거부** | 새 기기 → "다른 기기에서 사용 중" | 계정 공유 억제가 강하다 | ⚠️ **잠김 위험**: 앱이 크래시하면 세션이 남아 최대 8시간 로그인 불가 |
| **S3 · 좌석제** | 계정당 동시 세션 N개 허용(N은 상품) | N 초과 시 가장 오래된 세션 종료 또는 거부 | 다점포 운영을 정상 지원 + **매출 상품화** | 구현·UI 복잡, 상품 설명 부담 |

### 3.2 권장 — S1 + 유예 확인 (하이브리드)

```
새 로그인 요청 도착
  ├─ 활성 세션 없음                        → 즉시 로그인
  ├─ 활성 세션 있음 & lastSeenAt > 3분 경과 → 즉시 교체(기존은 다음 요청/하트비트에서 로그아웃)
  └─ 활성 세션 있음 & lastSeenAt ≤ 3분     → 409 SESSION_ACTIVE_ELSEWHERE
                                             + {deviceLabel, platform, lastSeenAt}
                                             → 클라가 확인 모달:
                                               "다른 기기(Windows · 부스1)에서 사용 중입니다.
                                                계속하면 그 기기는 로그아웃됩니다."
                                               [계속 로그인] → force:true 재요청 → 교체
                                               [취소]
```

| 근거 | 설명 |
|------|------|
| 잠김 방지 | 3분 무응답 세션은 죽은 것으로 보고 자동 교체 → S2의 치명적 단점 제거 |
| 실수 방지 | 살아 있는 세션을 밀어내려면 **명시적 확인**을 받는다 → S1의 핑퐁 완화 |
| 요구 충족 | "강제 로그아웃 팝업 필수"(기존 기기 측) + "다른 세션 차단"(새 기기 측 확인) 둘 다 만족 |
| 확장 경로 | `maxSessions`를 계정 속성으로 두면 S3로 자연 확장(기본 1) |

> ⚠️ **미결정**: S1+유예(권장) vs S2 vs S3 기본값 → [11 D-09](./11-open-decisions.md). 유예 시간(3분)·하트비트 주기도 함께 확정.

### 3.3 좌석제(S3)를 열어 두는 이유

[01 §5.4](./01-currency-catalog-and-pricing.md)의 시나리오 분석에서 **다점포 운영자가 한 계정으로 여러 부스를 쓰는 것이 자연스러운 사용 패턴**임이 드러났다. 단일 세션을 강제하면 이들은:

| 우회 | 결과 |
|------|------|
| 부스마다 별 계정 생성 | 정원·MC를 부스별로 따로 사야 한다 → 매출은 늘지만 **관리 부담**(계정 5개 로그인·PIN·프레임 각각) |
| 게스트로 운영 | **QR 전송 불가**(게스트는 업로드 안 함) → 서비스 가치 하락 |
| 로그인/로그아웃 반복 | 로컬 프레임이 매번 지워지고 다시 내려온다([04 §5](./04-custom-frames-billing-and-lifecycle.md)) → 최악 |

→ **좌석 상품(`seat`)** 이 정답에 가깝다: "동시 로그인 기기 3대 = 월 N MC". 초기에는 **관리자가 계정별 `maxSessions`를 수동 설정**하는 형태로 시작하고(운영 개입), 수요가 확인되면 상품화한다.

### 3.4 ⚠️ 시행 전 반드시 확인해야 할 운영 리스크

| 리스크 | 내용 | 완화 |
|--------|------|------|
| **현재 운영 중인 다중 PC 계정** | 단일 세션을 켜는 순간 그 부스들이 **영업 중에 로그아웃**된다 | 시행 전 세션 로그(하트비트 계측)로 다중 사용 계정을 **먼저 식별**하고 개별 안내 + `maxSessions` 상향 |
| 사내 개발·검증 계정 | 여러 개발 PC에서 같은 계정을 쓴다 | `admin`은 예외 또는 `maxSessions` 크게 |
| 웹 새로고침 | 웹은 새로고침 = 재로그인(토큰 메모리 전용) → 같은 기기에서 세션 id가 바뀐다 | `deviceId`가 같으면 **같은 기기로 간주**해 교체(팝업 없음) → §5.3 |
| 촬영 중 강제 로그아웃 | 손님 촬영 도중 로그아웃되면 사고 | §6.3 촬영 보호 규칙 |

## 4. 서버 설계

### 4.1 세션 레지스트리

**옵션 비교**

| 안 | 위치 | read 비용 | 다중 세션 확장 | 채택 |
|----|------|-----------|:---:|:---:|
| A | `users.activeSession` 필드(단일) | 인증 시 users read 1회(이미 필요한 경우 많음) | 어렵다 | |
| B | `sessions/{sessionId}` 문서 | 검증마다 read 1 | 쉽다 | |
| **C** | **`sessions/{userId}` 문서 1개에 세션 배열**(최대 N) | 검증마다 read 1 | 쉽다 | **○** |

**채택 C의 스키마**

`sessions/{userId}`

| 필드 | 타입 | 의미 |
|------|------|------|
| `userId` | string | 문서 ID |
| `maxSessions` | int ≥ 1 | 허용 동시 세션 수(기본 1, 관리자 조정 가능) |
| `sessions` | array(≤ 8) | 아래 항목 |
| `sessions[].sid` | string | 세션 id(UUID). JWT `sid` 클레임과 대조 |
| `sessions[].deviceId` | string | 기기 식별자(§5.3) |
| `sessions[].deviceLabel` | string | 사용자에게 보여줄 이름(예: `Windows · DESKTOP-A1B2`) |
| `sessions[].platform` | string | `windows`/`web`/`ios`/`android` |
| `sessions[].issuedAt` | timestamp | 로그인 시각 |
| `sessions[].lastSeenAt` | timestamp | 마지막 하트비트/요청 |
| `sessions[].expiresAt` | timestamp | JWT 만료와 동일(8시간) |
| `sessions[].revokedAt` | timestamp? | 교체·강제 종료 시각 |
| `sessions[].revokeReason` | string? | `superseded` / `admin` / `logout` |
| `updatedAt` | timestamp | |

| 규칙 | 내용 |
|------|------|
| 배열 상한 8 | 만료·폐기된 항목은 정리해 배열이 커지지 않게 한다(로그인 시 lazy 정리) |
| 폐기 항목 보존 | 최근 3건만 남긴다(강제 로그아웃 사유를 기존 기기에 알려 주기 위해) |
| 문서 미존재 | 세션 없음(첫 로그인) |
| 이력 | 장기 이력은 남기지 않는다(개인정보 최소화). 필요 시 `sessionEvents` 별 컬렉션 + TTL 30일 |

### 4.2 JWT 변경

| 항목 | 현행 | 변경 |
|------|------|------|
| 클레임 | `{sub, role, iat, exp}` | **`{sub, role, sid, iat, exp}`** |
| 검증 | 서명·만료·`sub`·`role` 화이트리스트 | + **`sid` 존재 확인**(형식만) |
| 하위 호환 | — | `sid` 없는 토큰(구버전 발급)은 **세션 검증을 건너뛴다**(전환 기간). 전환 종료 후 401 |
| 만료 | 8시간 | 불변 |
| 갱신 | 없음 | 불변(리프레시 도입은 별 과제) |

### 4.3 세션 대조 게이트 — 어디까지 검증하나 (비용 설계)

세션 대조는 `sessions/{userId}` **read 1회**를 추가한다. 모든 요청에 붙이면 Firestore read가 요청 수만큼 늘어난다.

| 라우트 그룹 | 세션 대조 | 이유 |
|-------------|:---:|------|
| `POST /uploads/prepare`·`commit` | **○** | 과금 지점(B11) |
| `POST /frames/mine`, `DELETE /frames/*` | **○** | 과금·데이터 변경 |
| `POST /payments/*`, `POST /items/*`(구매) | **○** | 돈 |
| `POST /sessions/heartbeat` | **○** | 이 자체가 검증 목적 |
| `GET /accounts/me/qr-usage`, `GET /wallet` | **△ 선택** | 조회. 검증하면 강제 로그아웃 감지가 빨라진다(권장 ○) |
| `GET /frames/default`, `GET /health` | × | apiKey 게이트, 계정 무관 |
| `PUT /accounts/me/pin` 등 계정 라우트 | ○ | 자격증명 변경 |

| 최적화 | 내용 |
|--------|------|
| 캐시 금지 | Functions 인스턴스 메모리 캐시는 **쓰지 않는다** — 강제 로그아웃이 지연되면 요구를 만족하지 못한다 |
| 병합 | 트랜잭션이 이미 `users`를 읽는 경로(commit)에서는 `sessions` read 1개만 추가 |
| 비용 | 하트비트 90초 주기 = 계정당 일 960 read. 활성 계정 50개면 일 48,000 read ≈ **$0.03/일** → 무시 가능 |

### 4.4 로그인 흐름 변경 (`POST /auth/google`)

```
기존: id_token 검증 → 계정 조회/생성 → JWT 발급
변경: id_token 검증 → 계정 조회/생성 →
      (트랜잭션) sessions/{uid} 읽기
        ├─ 만료·폐기 세션 정리
        ├─ 같은 deviceId 세션 존재 → 그 항목 교체(팝업 없음)
        ├─ 활성 수 < maxSessions → 새 세션 추가
        ├─ 활성 수 ≥ maxSessions
        │    ├─ 가장 오래된 세션 lastSeenAt > graceSeconds → 그것을 revoke하고 추가
        │    └─ 아니면 force 플래그 확인
        │         ├─ force:true  → revoke하고 추가
        │         └─ force:false → 409 SESSION_ACTIVE_ELSEWHERE + 기존 기기 정보
        └─ sid 생성 → JWT에 실어 발급
```

**요청 확장**

| 필드 | 필수 | 의미 |
|------|:---:|------|
| `deviceId` | ✅ | 기기 식별자(§5.3) |
| `deviceLabel` | — | 표시용(예: `부스1 · DESKTOP-A1B2`). 없으면 서버가 platform으로 생성 |
| `platform` | ✅ | `windows`/`web`/`ios`/`android` |
| `force` | — | 기본 false. true면 기존 세션을 밀어낸다 |

**응답 409 `SESSION_ACTIVE_ELSEWHERE`**

```json
{ "error": { "code": "SESSION_ACTIVE_ELSEWHERE",
             "message": "다른 기기에서 로그인되어 있습니다.",
             "detail": { "deviceLabel": "Windows · 부스1", "platform": "windows",
                         "lastSeenAtMs": 1786000000000 } } }
```

> ⚠️ **`detail`에 담는 정보 범위**: 기기 라벨·플랫폼·마지막 활동 시각만. **IP·위치·계정 이메일은 넣지 않는다**(계정 탈취 시도자에게 정보를 주지 않는다).

### 4.5 하트비트 엔드포인트

| 항목 | 규격 |
|------|------|
| 경로 | `POST /sessions/heartbeat` (Bearer + 세션 대조) |
| 요청 | `{}`(토큰의 `sid`가 정보 전부) |
| 응답 200 | `{ok: true, serverTimeMs, billingDay, quota: {remainingToday, dailyAllowance}, walletBalanceMc}` |
| 응답 401 | `SESSION_SUPERSEDED` + `{revokedAt, revokeReason, byDeviceLabel?}` |
| 동작 | `lastSeenAt` 갱신(write 1) |
| 주기(초안) | **90초**. 화면이 활성이고 로그인 상태일 때만. 유휴 경고 이후·백그라운드는 **5분**으로 늘린다 |
| 비용 | 계정당 일 read 960 + write 960 ≈ $0.0003/일. 무시 가능 |
| 응답 재사용 | 잔량·잔액을 함께 실어 **별 조회를 줄인다**(폴링 금지 원칙과 상충하지 않음 — 하트비트가 그 역할을 흡수) |

> ✅ **하트비트에 잔량을 실은 이유**: 별도 `qr-usage` 폴링을 금지하면서도 상단바 잔량 표시를 신선하게 유지할 수 있다. 요청 수가 늘지 않는다.

### 4.6 명시적 로그아웃

| 항목 | 규격 |
|------|------|
| 경로 | `POST /sessions/logout` (Bearer) |
| 동작 | 자기 `sid`를 `revoked`(reason=`logout`) → 배열에서 정리 |
| 실패 허용 | 네트워크 실패 시에도 **클라는 로컬 로그아웃을 진행**한다(fail-open). 서버 세션은 만료·교체로 정리된다 |
| 관리자 강제 종료 | `POST /admin/sessions/{userId}/revoke-all` (admin) — 계정 탈취 대응 |

## 5. 클라이언트 설계

### 5.1 강제 로그아웃 감지 → 팝업 (요구: 팝업 필수)

| 감지 경로 | 동작 |
|-----------|------|
| 하트비트 401 `SESSION_SUPERSEDED` | **즉시** 팝업 |
| 임의 API 401 `SESSION_SUPERSEDED` | 동상(웹은 `handleSessionExpired` 배선 확장 — 코드 분기로 문구만 달리) |
| 하트비트 네트워크 실패 | 세션 만료로 **단정하지 않는다**. 재시도(지수 백오프, 최대 5분). 연속 실패는 서버 연결 배지로 표시 |

**팝업 규격**

| 항목 | 내용 |
|------|------|
| 형태 | 모달(닫기 전 다른 조작 불가). 자동 닫힘 없음 |
| 문구 | "다른 기기에서 로그인되어 이 기기에서는 로그아웃되었습니다." + (있으면) "기기: {byDeviceLabel}" |
| 버튼 | [확인] 1개(누르면 홈으로) + [다시 로그인] |
| 부수 처리 | ① 세션 해제(`CurrentUser = null`) → 토큰 폐기(기존 단일 지점) ② **로컬 개인 프레임 purge**([04 §5.3](./04-custom-frames-billing-and-lifecycle.md)) ③ **촬영 데이터는 유지**(웹 `expireSession` 규약과 동일 — 손님 사진을 지우지 않는다) |
| 예외 | 촬영·업로드 진행 중이면 §6.3 |

### 5.2 새 로그인 측 확인 모달

| 항목 | 내용 |
|------|------|
| 트리거 | 로그인 응답 409 `SESSION_ACTIVE_ELSEWHERE` |
| 문구 | "이 계정은 다른 기기({deviceLabel})에서 사용 중입니다. 계속 로그인하면 해당 기기는 자동으로 로그아웃됩니다." |
| 버튼 | [계속 로그인](→ `force:true` 재요청) / [취소](로그인 화면 유지) |
| 마지막 활동 표시 | "마지막 활동: 2분 전" — 사용자가 판단할 근거 |

### 5.3 `deviceId` 규격 (플랫폼별)

| 플랫폼 | 원천 | 저장 | 주의 |
|--------|------|------|------|
| Windows | 레지스트리 `MachineGuid`(HKLM\SOFTWARE\Microsoft\Cryptography) **+ 앱 salt** 를 SHA-256 해시 | 계산값 캐시(ini 또는 LocalAppData) | 원본 GUID를 서버로 보내지 않는다(기기 식별자 최소화) |
| 웹 | 최초 접속 시 `crypto.randomUUID()` 생성 → **`localStorage`** 저장 | localStorage | ⚠️ **토큰은 localStorage 금지**지만 `deviceId`는 비밀이 아니므로 허용. 시크릿 모드·저장소 삭제 시 새 기기로 인식됨(수용) |
| iOS | `identifierForVendor` 해시 | Keychain | 앱 삭제 시 변경(수용) |
| Android | `ANDROID_ID`(앱 서명·사용자별) 해시 | 앱 저장소 | |

| 규칙 | 내용 |
|------|------|
| 형식 | `^[A-Za-z0-9_-]{16,64}$`(해시 base64url 권장) |
| 안정성 | **같은 기기·같은 앱에서 안정적**이어야 한다. 매 실행 랜덤이면 세션 배열이 폭증하고 "같은 기기 교체" 최적화가 죽는다 |
| 개인정보 | 하드웨어 식별자를 **원문 전송 금지**. 해시 + 앱 salt |
| 위조 | 위조 가능하다(클라 값). 위조하면 **자기 세션을 여러 개로 늘릴 수 있다** → `maxSessions` 상한이 최종 방어(위조해도 1개를 넘지 못한다) |
| 라벨 | `deviceLabel`은 사용자 입력 허용(예: "부스1") — 설정에 기기 이름 항목 추가 권장. 미입력 시 `{platform} · {hostname 일부}` |

### 5.4 웹의 특수 사정 — 새로고침

웹은 토큰이 메모리 전용이라 **새로고침마다 재로그인**이다([`analysis/61`](../analysis/61-auth-platform-integration.md) 규약). 그러면 세션이 계속 새로 생긴다.

| 문제 | 해법 |
|------|------|
| 새로고침 → 새 `sid` → 자기 자신을 밀어냄 | 서버가 **같은 `deviceId`면 기존 항목을 교체**(§4.4) → 팝업 없음, 세션 수 불변 |
| 같은 브라우저 탭 2개 | 같은 `deviceId`(localStorage 공유) → 서로 교체된다. 나중 탭이 유효, 먼저 탭은 다음 요청에서 401 → ⚠️ **문구가 "다른 기기"라서 오해를 준다** → `byDeviceLabel`이 자기 자신과 같으면 문구를 "다른 창에서 로그인되었습니다"로 분기 |
| 시크릿 모드 | 새 `deviceId` → 정상적으로 다른 기기로 취급 |

## 6. 상호작용 규칙 (기존 동작과의 충돌 해소)

### 6.1 유휴·홈 복귀와의 관계

| 경로 | 세션 | 근거 |
|------|------|------|
| 유휴 타임아웃 만료 | **유지**(로그아웃 금지 — it8 A1) | 하트비트 주기만 5분으로 늘린다 |
| 유휴 경고 "메인 화면으로" | 유지 | 동상 |
| 홈 버튼(사용자 취소) | 유지 | 동상 |
| 전역 예외 복구 | 유지 | 동상 |
| 명시적 로그아웃 | `POST /sessions/logout` | |
| 앱 종료 | 세션은 서버에 남아 8시간 후 만료 → ⚠️ S2 정책이면 잠김 원인. **S1+유예(3분)** 가 이 문제를 흡수한다 | §3.2 |

### 6.2 게스트 전환

게스트(비로그인)는 세션이 없다. 세션 대조는 **토큰이 있을 때만** 수행한다(현행 `optionalBearer` 정신 유지, 사실 8).

### 6.3 촬영·업로드 진행 중 강제 로그아웃 (중요)

| 상황 | 처리 | 이유 |
|------|------|------|
| 촬영 중(카운트다운·셔터) | 팝업을 **지연**한다. 촬영 세션이 끝나 결과 화면에 도달하면 표시 | 손님 앞에서 촬영이 끊기는 것이 최악 |
| 업로드 중(`prepare`~`commit`) | 서버가 이미 401을 반환하므로 **업로드는 실패**한다 → 기존 실패 경로(로컬 보존 + [재시도])로 흡수 + 팝업은 업로드 실패 처리 후 | `QrPopupViewModel`의 우아 처리 선례(`:105-120`) |
| 결과 화면 | 즉시 팝업 | |
| 프레임 편집 중(미저장) | 팝업 + "저장되지 않은 변경은 사라집니다" 경고. **로컬 purge는 팝업 확인 후** | 편집 중 파일 삭제는 파일 잠금·예외 유발 |
| 설정 화면 | 즉시 팝업. 설정 저장은 로컬이므로 영향 없음 | |

**구현 규약**: 강제 로그아웃 처리기는 **"지금 팝업 가능한 상태인가"를 셸에 묻고**, 불가하면 pending 플래그로 보류한다. 보류 상한 **60초**(초과 시 강제 표시 — 무한 보류로 세션 상태가 어긋나는 것을 막는다).

### 6.4 로컬 프레임 purge 연계

| 이벤트 | purge |
|--------|:---:|
| 강제 로그아웃(`SESSION_SUPERSEDED`) | ○ |
| 명시적 로그아웃 | ○ |
| JWT 만료(401 `unauthorized`) | ○ — 계정이 해제되므로 동일 취급 |
| 유휴·홈·예외 | × |
