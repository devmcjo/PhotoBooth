## 0. ❌ 폐기 고지 (2026-08-10)

> 🚫 **이 문서의 규격은 구현 대상이 아니다.** 같은 계정의 동시 로그인 차단·강제 로그아웃 팝업·
> 하트비트·세션 레지스트리·JWT `sid` 클레임을 **모두 도입하지 않는다.** 모든 플랫폼(Windows·web·
> iOS·Android)에 동일하게 적용되는 결정이다.
>
> **폐기 사유(사용자 결정)**: 과금 단위가 **QR 전송 세션 1건**이므로([03](./03-qr-daily-quota.md)),
> 같은 계정을 여러 기기에서 써도 **청구 총액은 사용량에 비례한다.** 세션을 1개로 묶어 얻으려던 것은
> "계정 공유로 인한 매출 누수 차단"이었는데, 사용량 과금에서는 그 누수가 성립하지 않는다.
> 프레임 역시 **다운로드는 1회만 과금**되므로 여러 PC에 설치되어도 과다 청구가 없다.
>
> **구현된 적이 없다**: 이 문서는 처음부터 미래 계획서였다(§2 사실표 2번 "서버에 활성 세션·기기
> 레지스트리가 없다"). 따라서 폐기는 코드·DB·API에 아무 변경을 만들지 않는다.
>
> **함께 폐기되는 것**: JWT `sid`(§4.2) · `sessions/{userId}` 컬렉션(§4.1) · `requireActiveSession`
> 미들웨어(§4.3) · `POST /sessions/{heartbeat,logout}`·`GET /sessions`·`admin revoke-all`(§4.5·§4.6) ·
> `deviceId`/`deviceLabel` 전송(§5.3) · 강제 로그아웃 팝업과 보류 규칙(§5.1·§6.3) ·
> 불변식 **B11**([00 §6](./00-scope-principles-and-model.md)) · 롤아웃 마일스톤 **D**(Step 21~23,
> [10](./10-rollout-testing-and-wbs.md)) · 미결정 **D-09**([11](./11-open-decisions.md)).
>
> **살아남는 것**: §3.3 **좌석(seat) 상품 논의**. 근거가 세션 통제가 아니라 "다점포 운영자가 한 계정을
> 여러 부스에서 쓴다"는 사용 패턴([01 §5.4](./01-currency-catalog-and-pricing.md))이고, 그 패턴은
> 폐기와 무관하게 참이다. 단 **"동시 세션 수 판매"라는 형태는 함께 폐기된다**(셀 수 없는 것을 팔 수
> 없다) → 좌석은 훗날 다른 축(부스 등록 수 등)으로 재설계해야 한다([11 D-26](./11-open-decisions.md)).
>
> **남는 리스크**: **정원 이중 소비**([03](./03-qr-daily-quota.md)) — 같은 계정이 2대에서 동시에 촬영하면 일일 정원이 2배 속도로
> 준다. 사용자는 이를 **수용**했다("QR 횟수 과금이라 무해"). 과금 정확성 문제는 아니지만
> **사용자 체감 손실**("내가 안 썼는데 정원이 없다")은 남는다 → 완화책은 [03 §8](./03-qr-daily-quota.md)의
> 잔량 표시를 상단바에 상시 노출하는 것뿐이다. 차단 수단은 없다.

> ⚠️ **착수자 주의 — 이름만 같은 것을 건드리지 마라.** 이 리포에서 "세션"은 **네 가지 다른 것**을 가리킨다.
> 폐기 대상은 마지막 줄 하나뿐이며, 그것은 **코드에 존재하지 않는다.**
>
> | 이름 | 실체 | 폐기와의 관계 |
> |------|------|---------------|
> | `SessionContext` (`src/MCPhoto.App/`) | 한 손님의 **촬영 세션** 상태 + 계정 단일 소스 | **무관.** 절대 손대지 않는다 |
> | `IBackendSession`/`BackendSession` (`src/MCPhoto.Http/Session/`) | 메모리 JWT 홀더 | **무관.** 로그인 토큰 보관은 그대로 유지 |
> | `BackendSessionSynchronizer` | 로그아웃 시 JWT 폐기 배선 | **무관.** 오히려 반드시 살아 있어야 한다 |
> | `sessionId`·`ResultSession`·`resultSessions/{sid}`·OPFS `sessions/` | **업로드 전송 세션** 식별자(Storage 경로·QR URL) | **무관. 과금 단위 그 자체다** |
> | `sessionExpiry.ts`·`handleSessionExpired` | **JWT 401 만료** 처리 | **무관.** 현행 동작이며 유지된다 |
> | ~~`sessions/{userId}`·`sid` 클레임·하트비트~~ | 이 문서가 신설하려던 **로그인 세션 레지스트리** | **이것만** 폐기 대상. 코드에 0건이므로 지울 것이 없다 |

## 1. ~~왜 과금 문서에 세션이 들어오나~~ *(이력)*

> 아래 4개 이유는 전부 소멸하거나 다른 방법으로 처리됐다: ① 정원 이중 소비 → **수용**(§0) ② 계정 공유 유인 → **사용량 과금에서는 누수가 아니다**([09 T8](./09-security-abuse-and-compliance.md)) ③ purge 전제 → [04 §5](./04-custom-frames-billing-and-lifecycle.md)가 2026-08-07에 **먼저 폐기**됐다(소유권 서명으로 대체) ④ 부정 결제 대응 → 대체안 **`users.disabled` 플래그**([09 T15](./09-security-abuse-and-compliance.md) · [11 D-27](./11-open-decisions.md)).

| 이유 | 설명 |
|------|------|
| **정원 이중 소비** | 같은 계정이 2대에서 동시에 촬영하면 정원이 2배 속도로 소진된다. 이는 과금 정확성 문제가 아니라 **사용자 체감 손실**이다("내가 안 썼는데 정원이 없다") |
| **정원 공유 = 계정 공유 유인** | 하루 200개 플랜을 여러 부스가 나눠 쓰면 상품 단가가 무의미해진다. 좌석 개념 없이 정원만 팔면 **계정 공유가 최적 전략**이 된다 |
| **프레임 로컬 purge의 전제** | 로그아웃 시 로컬 프레임을 지우려면 "지금 이 기기가 이 계정의 세션인가"가 서버에서 판정 가능해야 한다([04 §5](./04-custom-frames-billing-and-lifecycle.md)) |
| **부정 결제 대응** | 계정 탈취 시 활성 세션을 끊는 수단이 필요하다(현재는 **토큰 8시간 만료를 기다릴 수밖에 없다**) |

## 3. ~~정책 선택 (사용자 요구의 "또는"을 해소)~~ *(이력)*

> 🚫 **어느 정책도 채택하지 않는다.** [00 §8](./00-scope-principles-and-model.md)의 세션 통제 결론은 **(a) 무통제**로 재결정됐다(2026-08-10). 아래 S1/S2/S3 비교는 **운영 지식으로만** 남긴다 — 좌석제 수요가 확인되면 다시 열릴 자료다. **§3.3만 예외로 유효**하다.

### 3.3 좌석제(S3)를 열어 두는 이유 — **이 절만 유효** ⚠️ 단서 있음

> ⚠️ **이 절의 "동시 세션 수" 정의는 무효다.** 관찰(다점포 운영자가 한 계정으로 여러 부스를 쓴다)만 유효하며, **상품 축 재설계가 필요하다** → [11 D-26](./11-open-decisions.md). 아래 "우회" 표는 **단일 세션을 강제했다면 무슨 일이 벌어졌을지**를 분석한 것으로, 폐기 결정의 근거로 읽어야 한다 — 강제하지 않으므로 이 우회는 **발생하지 않는다.**

[01 §5.4](./01-currency-catalog-and-pricing.md)의 시나리오 분석에서 **다점포 운영자가 한 계정으로 여러 부스를 쓰는 것이 자연스러운 사용 패턴**임이 드러났다. 단일 세션을 강제하면 이들은:

| 우회 | 결과 |
|------|------|
| 부스마다 별 계정 생성 | 정원·MC를 부스별로 따로 사야 한다 → 매출은 늘지만 **관리 부담**(계정 5개 로그인·PIN·프레임 각각) |
| 게스트로 운영 | **QR 전송 불가**(게스트는 업로드 안 함) → 서비스 가치 하락 |
| 로그인/로그아웃 반복 | 로컬 프레임이 매번 지워지고 다시 내려온다([04 §5](./04-custom-frames-billing-and-lifecycle.md)) → 최악 |

> 🚫 **아래 §4.1~§4.6은 신설하지 않는다.** `sessions/{userId}` 컬렉션·규칙·인덱스·TTL, JWT `sid` 클레임과 전환 기간 처리, `requireActiveSession` 미들웨어, 로그인 흐름의 409/`force` 분기, `POST /sessions/heartbeat`·`POST /sessions/logout`·`GET /sessions`·`POST /admin/sessions/{userId}/revoke-all` — **전부 폐기**됐다([07](./07-api-and-data-contract.md)에서도 제거됨). **JWT는 `{sub, role, iat, exp}` 그대로이고 인증 미들웨어는 stateless를 유지한다.**

### 4.1 ~~세션 레지스트리~~ *(이력)*

**옵션 비교**

| 안 | 위치 | read 비용 | 다중 세션 확장 | 채택 |

**채택 C의 스키마**

`sessions/{userId}`

| 필드 | 타입 | 의미 |
|------|------|------|
| `userId` | string | 문서 ID |
| `maxSessions` | int ≥ 1 | 허용 동시 세션 수(기본 1, 관리자 조정 가능) |

| `sessions[].revokeReason` | string? | `superseded` / `admin` / `logout` |
| `updatedAt` | timestamp | |

|------|------|

### 4.3 ~~세션 대조 게이트 — 어디까지 검증하나 (비용 설계)~~ *(이력)*

세션 대조는 `sessions/{userId}` **read 1회**를 추가한다. 모든 요청에 붙이면 Firestore read가 요청 수만큼 늘어난다.

| 라우트 그룹 | 세션 대조 | 이유 |
|-------------|:---:|------|
| `POST /uploads/prepare`·`commit` | **○** | 과금 지점(B11) |
| `POST /frames/mine`, `DELETE /frames/*` | **○** | 과금·데이터 변경 |
| `POST /payments/*`, `POST /items/*`(구매) | **○** | 돈 |
| `POST /sessions/heartbeat` | **○** | 이 자체가 검증 목적 |
| `GET /accounts/me/qr-usage`, `GET /wallet` | **△ 선택** | 조회. 검증하면 강제 로그아웃 감지가 빨라진다(권장 ○) |
| `GET /frames/default`, `GET /health` | × | apiKey 게이트, 계정 무관 |
| `PUT /accounts/me/pin` 등 계정 라우트 | ○ | 자격증명 변경 |

| 최적화 | 내용 |
|--------|------|
| 캐시 금지 | Functions 인스턴스 메모리 캐시는 **쓰지 않는다** — 강제 로그아웃이 지연되면 요구를 만족하지 못한다 |
| 병합 | 트랜잭션이 이미 `users`를 읽는 경로(commit)에서는 `sessions` read 1개만 추가 |
| 비용 | 하트비트 90초 주기 = 계정당 일 960 read. 활성 계정 50개면 일 48,000 read ≈ **$0.03/일** → 무시 가능 |

### 4.4 ~~로그인 흐름 변경 (`POST /auth/google`)~~ *(이력 — 로그인 라우트는 변경 없음)*

```
기존: id_token 검증 → 계정 조회/생성 → JWT 발급
변경: id_token 검증 → 계정 조회/생성 →
      (트랜잭션) sessions/{uid} 읽기
        ├─ 만료·폐기 세션 정리
        ├─ 같은 deviceId 세션 존재 → 그 항목 교체(팝업 없음)
        ├─ 활성 수 < maxSessions → 새 세션 추가
        ├─ 활성 수 ≥ maxSessions
        │    ├─ 가장 오래된 세션 lastSeenAt > graceSeconds → 그것을 revoke하고 추가
        │    └─ 아니면 force 플래그 확인
        │         ├─ force:true  → revoke하고 추가
        │         └─ force:false → 409 SESSION_ACTIVE_ELSEWHERE + 기존 기기 정보
        └─ sid 생성 → JWT에 실어 발급
```

**요청 확장**

| 필드 | 필수 | 의미 |
|------|:---:|------|
| `deviceId` | ✅ | 기기 식별자(§5.3) |
| `deviceLabel` | — | 표시용(예: `부스1 · DESKTOP-A1B2`). 없으면 서버가 platform으로 생성 |
| `platform` | ✅ | `windows`/`web`/`ios`/`android` |
| `force` | — | 기본 false. true면 기존 세션을 밀어낸다 |

**응답 409 `SESSION_ACTIVE_ELSEWHERE`**

```json
{ "error": { "code": "SESSION_ACTIVE_ELSEWHERE",
             "message": "다른 기기에서 로그인되어 있습니다.",
             "detail": { "deviceLabel": "Windows · 부스1", "platform": "windows",
                         "lastSeenAtMs": 1786000000000 } } }
```

> ⚠️ **`detail`에 담는 정보 범위**: 기기 라벨·플랫폼·마지막 활동 시각만. **IP·위치·계정 이메일은 넣지 않는다**(계정 탈취 시도자에게 정보를 주지 않는다).

### 5.3 ~~`deviceId` 규격 (플랫폼별)~~ *(이력)*

> ✅ **개인정보 표면이 줄었다**: 세션 목적의 기기 식별자를 **수집하지 않는다** → [09 §6.5](./09-security-abuse-and-compliance.md). ⚠️ 단 [09 §3.1 (b)](./09-security-abuse-and-compliance.md)의 **기기 단위 무료 상한**은 이 문서와 **무관한 별개 설계**이며, 그것을 채택하면 어뷰징 방어 목적으로 기기 식별자가 다시 필요하다. 그때는 아래 표의 해시+salt 규약을 참고할 수 있다.

| 플랫폼 | 원천 | 저장 | 주의 |
|--------|------|------|------|
| Windows | 레지스트리 `MachineGuid`(HKLM\SOFTWARE\Microsoft\Cryptography) **+ 앱 salt** 를 SHA-256 해시 | 계산값 캐시(ini 또는 LocalAppData) | 원본 GUID를 서버로 보내지 않는다(기기 식별자 최소화) |
| 웹 | 최초 접속 시 `crypto.randomUUID()` 생성 → **`localStorage`** 저장 | localStorage | ⚠️ **토큰은 localStorage 금지**지만 `deviceId`는 비밀이 아니므로 허용. 시크릿 모드·저장소 삭제 시 새 기기로 인식됨(수용) |
| iOS | `identifierForVendor` 해시 | Keychain | 앱 삭제 시 변경(수용) |
| Android | `ANDROID_ID`(앱 서명·사용자별) 해시 | 앱 저장소 | |

| 규칙 | 내용 |
|------|------|
| 형식 | `^[A-Za-z0-9_-]{16,64}$`(해시 base64url 권장) |
| 안정성 | **같은 기기·같은 앱에서 안정적**이어야 한다. 매 실행 랜덤이면 세션 배열이 폭증하고 "같은 기기 교체" 최적화가 죽는다 |
| 개인정보 | 하드웨어 식별자를 **원문 전송 금지**. 해시 + 앱 salt |
| 위조 | 위조 가능하다(클라 값). 위조하면 **자기 세션을 여러 개로 늘릴 수 있다** → `maxSessions` 상한이 최종 방어(위조해도 1개를 넘지 못한다) |
| 라벨 | `deviceLabel`은 사용자 입력 허용(예: "부스1") — 설정에 기기 이름 항목 추가 권장. 미입력 시 `{platform} · {hostname 일부}` |

### 5.4 ~~웹의 특수 사정 — 새로고침~~ *(이력 — 문제 자체가 소멸)*

> ✅ 웹 새로고침이 재로그인이 되어도 **밀어낼 세션이 없으므로** 자기 자신을 로그아웃시키는 문제가 발생하지 않는다. 탭 2개 동시 사용도 정상이다.

웹은 토큰이 메모리 전용이라 **새로고침마다 재로그인**이다([`analysis/61`](../analysis/61-auth-platform-integration.md) 규약). 그러면 세션이 계속 새로 생긴다.

| 문제 | 해법 |
|------|------|
| 새로고침 → 새 `sid` → 자기 자신을 밀어냄 | 서버가 **같은 `deviceId`면 기존 항목을 교체**(§4.4) → 팝업 없음, 세션 수 불변 |
| 같은 브라우저 탭 2개 | 같은 `deviceId`(localStorage 공유) → 서로 교체된다. 나중 탭이 유효, 먼저 탭은 다음 요청에서 401 → ⚠️ **문구가 "다른 기기"라서 오해를 준다** → `byDeviceLabel`이 자기 자신과 같으면 문구를 "다른 창에서 로그인되었습니다"로 분기 |
| 시크릿 모드 | 새 `deviceId` → 정상적으로 다른 기기로 취급 |

## 6. ~~상호작용 규칙 (기존 동작과의 충돌 해소)~~ *(이력 — 충돌이 발생하지 않는다)*

> ✅ **이 절 전체가 불필요해졌다.** 세션을 도입하지 않으므로 유휴 타임아웃·홈 복귀·게스트 전환·촬영 중 팝업·프레임 purge와의 충돌을 해소할 규칙이 필요 없다. **it8 A1(유휴는 로그아웃하지 않는다)은 그대로 유효**하다([`analysis/60 §3.5`](../analysis/60-auth-accounts-and-roles.md)).
>
> ⚠️ **§6.3의 "팝업 보류 60초" 상태 기계가 이 설계에서 가장 위험했던 부분이다** — 손님 촬영 도중 로그아웃 팝업이 뜰 수 있었고, 그것을 막으려고 셸에 "지금 팝업 가능한가"를 묻는 상태 기계를 4개 플랫폼에 심어야 했다. 폐기의 가장 큰 안전 이득이다.

### 6.1 ~~유휴·홈 복귀와의 관계~~ *(이력)*

| 경로 | 세션 | 근거 |
|------|------|------|
| 유휴 타임아웃 만료 | **유지**(로그아웃 금지 — it8 A1) | 하트비트 주기만 5분으로 늘린다 |
| 유휴 경고 "메인 화면으로" | 유지 | 동상 |
| 홈 버튼(사용자 취소) | 유지 | 동상 |
| 전역 예외 복구 | 유지 | 동상 |
| 명시적 로그아웃 | `POST /sessions/logout` | |
| 앱 종료 | 세션은 서버에 남아 8시간 후 만료 → ⚠️ S2 정책이면 잠김 원인. **S1+유예(3분)** 가 이 문제를 흡수한다 | §3.2 |

### 6.2 ~~게스트 전환~~ *(이력)*

게스트(비로그인)는 세션이 없다. 세션 대조는 **토큰이 있을 때만** 수행한다(현행 `optionalBearer` 정신 유지, 사실 8).

### 6.3 ~~촬영·업로드 진행 중 강제 로그아웃 (중요)~~ *(이력 — 가장 위험했던 설계)*

| 상황 | 처리 | 이유 |
|------|------|------|
| 촬영 중(카운트다운·셔터) | 팝업을 **지연**한다. 촬영 세션이 끝나 결과 화면에 도달하면 표시 | 손님 앞에서 촬영이 끊기는 것이 최악 |
| 업로드 중(`prepare`~`commit`) | 서버가 이미 401을 반환하므로 **업로드는 실패**한다 → 기존 실패 경로(로컬 보존 + [재시도])로 흡수 + 팝업은 업로드 실패 처리 후 | `QrPopupViewModel`의 우아 처리 선례(`:105-120`) |
| 결과 화면 | 즉시 팝업 | |
| 프레임 편집 중(미저장) | 팝업 + "저장되지 않은 변경은 사라집니다" 경고. **로컬 purge는 팝업 확인 후** | 편집 중 파일 삭제는 파일 잠금·예외 유발 |
| 설정 화면 | 즉시 팝업. 설정 저장은 로컬이므로 영향 없음 | |

**구현 규약**: 강제 로그아웃 처리기는 **"지금 팝업 가능한 상태인가"를 셸에 묻고**, 불가하면 pending 플래그로 보류한다. 보류 상한 **60초**(초과 시 강제 표시 — 무한 보류로 세션 상태가 어긋나는 것을 막는다).

## 8. ~~테스트 목록~~ *(이력 — SE1~SE14 전량 폐기)*

> 🚫 **SE1~SE14는 실행하지 않는다.** [10 §4](./10-rollout-testing-and-wbs.md)의 해당 참조(마일스톤 D Step 21~23·게이트 G13·수락 기준 A9·A10)도 함께 폐기됐다.
>
> ⚠️ **판정이 뒤집힌 케이스가 있다**: SE1("기기 B는 409")·SE5("4번째만 409")·SE2("A가 401")는 **이제 반대가 정답이다** — 여러 기기가 동시에 로그인하고 **어느 쪽도 끊기지 않아야 한다.** 대체 수락 기준은 [10 §6.1 A13](./10-rollout-testing-and-wbs.md)이다. 이 표를 참고 자료로 재사용하지 말 것.

| # | 케이스 | 기대 |
|---|--------|------|
| SE1 | 기기 A 로그인 → 기기 B 로그인(A 활동 1분 전) | B는 409, A 유지 |
| SE2 | 위에서 B가 `force:true` | B 성공, A는 다음 요청/하트비트에서 401 SUPERSEDED |
| SE3 | A 활동 5분 전 → B 로그인 | 팝업 없이 B 성공(유예 초과) |
| SE4 | 같은 `deviceId`로 재로그인(웹 새로고침) | 팝업 없음, 세션 수 1 유지 |
| SE5 | `maxSessions=3` 계정에서 3대 동시 | 전부 성공, 4번째만 409 |
| SE6 | A 세션 폐기 후 A가 업로드 시도 | 401, **정원 미소비** |
| SE7 | A 세션 폐기 후 A가 게스트로 촬영 | 정상(세션 검증은 토큰 있을 때만) |
| SE8 | 촬영 중 강제 로그아웃 | 팝업 보류 → 결과 화면에서 표시 |
| SE9 | 강제 로그아웃 후 로컬 개인 프레임 | 삭제됨. 공용 프레임 잔존 |
| SE10 | 유휴 타임아웃 30분 경과 후 하트비트 | 세션 유지(로그아웃 없음, it8 A1 보존) |
| SE11 | `sid` 없는 구버전 토큰 | 과금 라우트 통과(전환 기간) |
| SE12 | 로그아웃 API 실패 | 클라는 로컬 로그아웃 완료 |
| SE13 | 관리자 revoke-all | 모든 기기 401 |
| SE14 | 동시 로그인 2건(경합) | 트랜잭션 직렬화로 한 건만 세션 등록, 다른 건 409 또는 교체 |
