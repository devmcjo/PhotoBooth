## 0. 2026-08-07 개정 요약 — 무엇이 왜 바뀌었나

[`design/wpf-frame-ownership-binding-design.md`](../design/wpf-frame-ownership-binding-design.md)가 확정되면서 **이 문서의 전제 세 가지가 무너졌다.** 초판(2026-08-06)은 "로컬 파일로는 타 계정 격리를 보장할 수 없다"를 출발점으로 삼았는데, 그 문제가 로컬에서 해결됐기 때문이다.

| # | 초판 내용 | 개정 | 근거 |
|---|-----------|------|------|
| 1 | **로그아웃 시 로컬 개인 프레임 삭제**(§5 전체) | **폐지** | `.slots`에 소유자를 서명해 넣으므로 파일이 남아 있어도 **다른 계정에게 보이지 않는다**. 지울 이유가 사라졌고, 지우지 않으면 재로그인 시 재다운로드도 없다 |
| 2 | **계정당 10개 상한 유지 + 확장 상품 `frame_slot_ext`** (§3.5) | **상한 폐지 · 상품 폐기** | 프레임은 **1회성 구매 + 영구 사용**이다. 생성마다 과금하면 ① 원가는 이미 커버되고(500원 = 40년치) ② 유료라 오남용 유인이 없다. 남는 것은 "돈 내고 만드는데 개수까지 막나"는 **이중 과금 반발**뿐이다 |
| 3 | **레거시 로컬 프레임 이관**(§7 전체) | **불필요** | Release 전이라 기존 개인 프레임·default 캐시가 없다(클린 상태 전제) |
| 4 | 결함 A — 접두 매칭 유출(§2.1) | **소멸** | 파일명 접두 규약 자체가 폐지되고 소유자 판정이 서명된 필드로 옮겨갔다 |
| 5 | 결함 B — 이미지 바이트 상한 없음(§2.2) | **이번에 수정** | 개수 상한을 없애면 **크기 상한이 유일한 총량 방어선**이 된다. F-2(8MB 서명 조건)를 함께 넣는다 |

> ⚠️ **개수 상한을 없앤 대가**: 총량 방어가 `8MB × 구매 수` 하나뿐이다. 프레임은 TTL 비대상(영구 보관)이므로 F-2 서명 조건은 **선택이 아니라 필수**다.

## 2. ⚠️ 현행 규약에서 발견한 결함 2건 (과금 전에 고쳐야 한다)

### 2.1 결함 A — 계정 id가 다른 계정 id의 접두일 때 **개인 프레임이 유출된다** ✅ **소멸(2026-08-07)**

> **이 결함은 소유권 바인딩 설계로 원인 자체가 사라졌다.** 파일명 접두 규약이 폐지되고 소유자 판정이 **서명된 `#owner` 필드**로 옮겨갔기 때문이다. 아래 서술과 F-1 규칙은 **이력으로만** 남긴다(구현 대상 아님).

**재현**

| 계정 | 프레임 이름 | 로컬 파일 |
|------|-------------|-----------|
| `ab` | `myframe` | `ab_myframe.png` |
| `ab_c` | `myframe` | `ab_c_myframe.png` |

`ab`로 로그인 → `LoadUser("ab")` → 필터 `name.StartsWith("ab_")`(`LocalFrameStore.cs:67`) → **`ab_c_myframe`도 매칭**된다. `displayName`은 접두 제거 후 `c_myframe`이 되어 목록에 나타난다.

| 항목 | 내용 |
|------|------|
| 영향 | **타 계정의 개인 프레임이 목록에 노출되고 촬영에 사용된다.** 사용자 요구("다른 계정으로 로그인 시 미제공")의 정면 위반 |
| 실현 가능성 | 계정 id는 Google email local-part 파생이고 `_`를 허용한다(사실 6). `ab@…`와 `ab_c@…`가 같은 부스를 쓰면 성립 |
| 추가 영향 | **로그아웃 purge를 접두 매칭으로 구현하면 타 계정 파일을 삭제한다**(더 심각 — 데이터 유실) |

**수정 규약 (F-1)**

```
파일이 계정 X의 개인 프레임인가?
  = fileName.StartsWith(X + "_")  &&  fileName.Substring(X.Length + 1)에 '_'가 없다
```

- 성립 근거: **프레임 이름에 `_`가 금지**(사실 5)이므로 접두 제거 후 잔여에 `_`가 있으면 그것은 **다른 계정의 접두**다.
- `ab_c_myframe`: 잔여 `c_myframe` → `_` 포함 → `ab`의 것이 **아니다** ✅
- `ab_myframe`: 잔여 `myframe` → `_` 없음 → `ab`의 것 ✅
- 적용 지점: `LoadUser`(로드) · purge(삭제) · 이름 충돌 가드(`FrameEditorViewModel.cs:527`) **3곳 모두**. 판정은 **순수 함수 1개**(`FrameNaming.IsOwnedLocalFile(fileName, accountId)`)로 뽑아 3곳이 같은 기준을 쓰게 한다.

### 2.2 결함 B — 프레임 이미지 **바이트 크기 상한이 서버에 없다** ⬆️ **필수로 승격(2026-08-07)**

> 개수 상한을 폐지했으므로(§0 #2) **이 크기 상한이 유일한 총량 방어선**이 됐다. F-2는 선택이 아니라 **소유권 바인딩 구현과 함께 반드시 들어간다**.
> 참고로 클라이언트 `FrameImageValidator`는 이미 **장변 4000px 축소 + 10MB 상한**을 갖고 있다 → **8MB로 낮춘다**(서버 서명 조건과 동일 값).

| 항목 | 내용 |
|------|------|
| 사실 | 서버는 `imageSize`(픽셀)만 검증한다([`analysis/31 §4.12`](../analysis/31-backend-api-reference.md)). 파일 바이트는 **서명 URL로 Storage에 직접 PUT**되므로 백엔드를 경유하지 않는다 |
| 위험 | 40MB PNG를 올려도 통과한다. 프레임은 **TTL 비대상**(사실 12)이라 영구 비용이 된다. 과금 단가(5MC)는 2MB 기준으로 산정했다([01 §5.3](./01-currency-catalog-and-pricing.md)) |
| 수정 규약 (F-2) | ① 서명 URL 발급 시 **`x-goog-content-length-range: 0,8388608`(8MB) 조건을 서명에 포함** → GCS가 초과 업로드를 거부한다(클라 우회 불가) ② 클라도 사전 검증(`FrameImageValidator` 확장, 즉각 피드백) ③ 문구: "프레임 이미지는 8MB 이하여야 합니다" |
| 대안 | Cloud Storage 트리거 함수로 사후 검사·삭제 — **미채택**(함수 추가 비용 + 이미 결제된 프레임을 사후 무효화하는 UX가 나쁘다) |

> ✅ 두 결함은 **과금과 무관하게 현재도 존재한다.** 다만 과금 도입으로 ① 유출이 유료 자산 유출이 되고 ② 용량이 직접 원가가 되므로 **선행 수정 대상**으로 승격한다. [10 §5 Step 1](./10-rollout-testing-and-wbs.md)에 배치.

### 3.2 왜 power의 개인 프레임도 과금하는가 (비대칭 근거)

| 스코프 | 저장 위치 | 노출 | 과금 |
|--------|-----------|------|:---:|
| 공용 기본(`userId=null`, `isDefault=true`) | `frames/default/` | **모든 계정 + 게스트** | × 무료 |
| 개인(`userId={id}`, `isDefault=false`) | `frames/users/{id}/` | 본인만 | **○ 유료**(단 power는 무료 — 아래) |

- 공용 프레임은 **제품 자산**이다(전 사용자에게 가치 제공). 무료로 두는 것이 서비스에 이롭다.
- 개인 프레임은 **개인 편의**다.
- ⚠️ **2026-08-07 정정 — power의 개인 프레임은 무료다**(설계 D-15). 아래 우회 유인 때문에 과금이 **실효가 없다**:
  power는 개인 프레임 대신 공용 프레임을 **무료로** 만들 수 있고 그 편이 노출도 넓다. 유료로 둬도 아무도
  사지 않으므로 규칙만 복잡해진다. 대신 공용 프레임 오염이라는 운영 리스크가 남는다(→ [`analysis/90`](../analysis/90-roadmap-and-future-work.md) 공용 목록 관리).
- ⚠️ 이 규칙은 **우회 유인**을 만든다: power는 개인 프레임 대신 공용 프레임을 만들면 무료다(그리고 전원에게 보인다). 이는 운영상 수용한다 — power는 자사·고객사 운영자이고, 공용 프레임 오염은 별도 운영 문제([`analysis/90 §1`](../analysis/90-roadmap-and-future-work.md)에 유사 항목 존재)로 다룬다.

### 3.3 "이름 바꿔 저장"이 과금되는 함정 (반드시 UI에 노출)

현행 동작: `FrameEditorViewModel`이 이름을 바꿔 저장하면 **새 파일명으로 새로 쓴다**(옛 파일은 남는다 — [`analysis/90 §1`](../analysis/90-roadmap-and-future-work.md) "프레임 편집 fork 시 옛 이름 파일 잔존"에 이미 등재된 성질).

| 문제 | 사용자는 "수정"이라고 생각하는데 서버는 "신규 생성"으로 과금한다 |
|------|------|
| 대응 1 | 저장 확인 모달이 **분기 결과를 명시**한다: "이름이 변경되었습니다. **새 프레임으로 저장**되며 5 MC가 차감됩니다. 기존 프레임은 유지됩니다." + [새로 만들기] / [원래 이름으로 저장] 2버튼 |
| 대응 2 | 이름 변경 없는 저장은 **확인 없이 무료 저장**(마찰 최소) |
| 대응 3 | 옛 파일 잔존 문제를 이번 기회에 정리: 서버 정본 전환 후 **로컬은 캐시**이므로, 캐시는 서버 목록과 동기화하며 고아 파일을 정리한다(§6.3) |

### 3.4 삭제·환불

| 규칙 | 내용 |
|------|------|
| 삭제 시 환불 | **없다.** 생성 시점에 소비가 완료된다(문서·Storage가 실제로 만들어졌다) |
| 고지 | 삭제 확인 모달에 "삭제한 프레임은 복구할 수 없고 사용한 MC는 환불되지 않습니다" 필수 |
| 삭제 후 재생성 | **재과금**한다 |
| 예외 — **생성 직후 실패 환급** | 이미지 PUT 실패 등으로 사용 불가 프레임이 생긴 경우, **생성 후 10분 내 삭제**면 크레딧을 환급한다(계정당 **일 3회** 상한, 원장 `adjust +`). 남용 방지를 위해 상한과 시간 창을 둔다 → §4.4 |
| ⬆️ **실수 수정 창구로 승격**(2026-08-07) | 프레임 **수정 기능이 폐지**되어(설계 D-16) 슬롯 하나를 5px 옮기려 해도 새로 만들어야 한다. 과금 시 "새로 만들기(500원) + 잘못 만든 것 삭제(환불 없음) = 오타 하나에 1,000원"이 되므로, 위 10분 환급을 **실수 수정의 공식 경로**로 삼는다. UI가 이 창구를 안내해야 한다 |
| 계정 삭제 | 프레임 cascade 삭제(현행 유지). MC·크레딧 잔액은 소멸([01 §2](./01-currency-catalog-and-pricing.md)) |

### 3.5 개수 상한 — **폐지**(2026-08-07)

| 항목 | 값 |
|------|-----|
| 계정당 개인 프레임 | **상한 없음**. `services/frames.ts`의 `MAX_PER_USER` 검사를 제거한다 |
| 총량 방어 | **이미지 8MB 상한**(§2.2 F-2) 하나. 서명 조건이라 클라이언트가 우회할 수 없다 |
| 확장 상품 `frame_slot_ext` | **폐기**. [01 §6.4](./01-currency-catalog-and-pricing.md)의 예약 항목을 삭제한다 |

**폐지 근거**

| # | 이유 |
|---|------|
| 1 | **원가가 이미 커버된다.** 프레임 1개 영구 보관 ≈ 12.6원/년([01 §5.3](./01-currency-catalog-and-pricing.md)), 생성 단가 5MC(500원) = 약 40년치. 개수를 막아 방어할 원가가 없다 |
| 2 | **유료라 오남용 유인이 없다.** 무료 서비스의 상한 논리를 그대로 가져올 수 없다 |
| 3 | **1회성 구매 + 영구 사용과 모순된다.** 산 물건의 개수를 파는 쪽이 제한하는 구조다 |
| 4 | **확장 상품은 이중 과금으로 읽힌다.** "만들 때마다 500원 내는데 11개째부터 또 내라고?" — 반발 위험이 수익보다 크다 |
| 5 | **구독형 확장은 회수가 불가능하다.** 만료 시 초과분을 삭제하면 구매 자산 몰수, 잠그면 강한 반발, 유지하면 상한이 무의미하다 |

## 4. 서버 저장 전환 (사용자 요구 "DB 저장 필요")

### 4.1 목표 상태

| 항목 | 현행 | 전환 후 |
|------|------|---------|
| 정본 | 로컬 파일 | **Firestore `frameTemplates` + Storage `frames/{userId}/`** |
| 로컬 | 정본 | **캐시**(오프라인 사용·표시 성능) |
| 다른 기기에서 | 보이지 않음 | **같은 계정으로 로그인하면 보인다**(요구 만족의 부수 효과) |
| 로그아웃 후 | 파일 잔존 | **파일 잔존**(삭제하지 않는다 — 서명이 격리를 보장하므로 지울 이유가 없다. §0 #1) |
| 개수 상한 | (미작동) | **없음**(§3.5) |
| 이미지 크기 | 무제한 | **8MB**(서명 조건 강제, §2.2) |
| 오프라인 생성 | 가능 | **불가**(과금·정본이 서버) → §4.5 |

### 4.2 신규 엔드포인트 — 개인 프레임 생성

기존 `POST /frames`(power 전용 공용 강제)를 **건드리지 않고** 경로를 신설한다.

| 항목 | 규격 |
|------|------|
| 경로 | `POST /frames/mine` |
| 게이트 | `requireBearer` + **`requireFrameWrite`**(신규: `CanWriteFrames` = advanced_user 이상) + 과금 |
| 요청 | `{name, imageSize, slots, idempotencyKey, useCredit?: bool, itemVersion?: int}` |
| 서버 강제 | `userId = principal.id`, `isDefault = false`(클라 값 무시 — 기존 `POST /frames`가 반대 방향으로 강제하는 것과 대칭) |
| 검증 | 이름 1~100자·`_` 금지(기존 `validateFrameName` 재사용), `imageSize` > 0, slots 1~6(기존 재사용). **개수 상한 검사 없음**(§3.5 폐지) |
| 과금 | 트랜잭션 안에서 `frameCredits -= 1` 또는 `balanceMc -= priceMc` |
| 응답 201 | `{frame, upload, billing: {charged: "credit"|"mc", priceMc, balanceMc, frameCredits}}` |
| 서명 URL | 기존 `signing.ts` 재사용 + **`x-goog-content-length-range` 조건 추가**(F-2) |

**왜 새 경로인가**

| 이유 | 설명 |
|------|------|
| 기존 계약 보존 | `POST /frames`는 "공용 기본 프레임 생성"이라는 의미가 문서·테스트·클라에 고정돼 있다([`analysis/31 §4.12`](../analysis/31-backend-api-reference.md)) |
| 게이트가 다르다 | 공용 = `requirePower`, 개인 = `requireFrameWrite` + 과금. 한 라우트에서 body 값으로 분기하면 **권한 오판 위험**이 커진다(it16이 두 권한 축을 분리한 정신과 동일) |
| 회귀 안전 | 기존 power 흐름의 테스트가 그대로 유효하다 |

### 4.3 과금 방식 2경로

| 경로 | 요청 | 서버 동작 |
|------|------|-----------|
| 생성권 사용(기본) | `useCredit: true` | `entitlements.frameCredits ≥ 1` 확인 → −1. 부족하면 **자동으로 MC 경로로 폴백하지 않는다**(409 `NO_FRAME_CREDIT`) |
| MC 직접 차감 | `useCredit: false` | 카탈로그 `frame_create.priceMc` 확인(+`itemVersion` 대조) → 잔액에서 차감 + 원장 `spend` |

> ⚠️ **자동 폴백을 금지하는 이유**: 사용자가 "크레딧으로 만들겠다"고 눌렀는데 MC가 빠지면 항의한다. 클라가 잔량을 보고 **어느 경로인지 명시한 확인 모달**을 띄우고, 그 선택을 서버에 그대로 보낸다.

### 4.4 원자성 — 3단 저장의 실패 처리

```
① POST /frames/mine   → (트랜잭션) 과금 + 문서 생성 + 서명 URL 발급
② PUT {putUrl}        → PNG 바이트 직접 업로드(백엔드 미경유)
③ 로컬 캐시 기록      → ②가 성공한 뒤에만(B9)
```

| 실패 지점 | 상태 | 처리 |
|-----------|------|------|
| ① 실패 | 아무것도 없음 | 과금 없음(트랜잭션 롤백). 클라는 오류 표시 |
| **② 실패** | **문서 있음 + 이미지 없음 + 과금됨** | 클라가 즉시 `DELETE /frames/{id}` 호출 → 서버가 문서·(있으면)이미지 삭제 + **10분 내·일 3회 이내면 크레딧/MC 환급**(§3.4). 로컬 캐시는 기록하지 않는다 |
| ② 실패 + 삭제 호출도 실패(네트워크 단절) | 사용 불가 문서 잔존 | 다음 로그인 시 **캐시 동기화가 "이미지 로드 실패 프레임"을 감지** → "손상된 프레임 1개가 있습니다. 삭제할까요?" 안내. 이때 삭제해도 환급 창(10분)이 지났으면 환급 없음 → ⚠️ 사용자 불만 가능 → **환급 창을 24시간으로 늘리는 대안**을 [11 D-06](./11-open-decisions.md)에 올린다 |
| ③ 실패(디스크 오류·파일 잠금) | 서버 정본 있음 | 다음 로드에서 서버에서 다시 내려받는다(무해) |

> ✅ **이 구조는 웹 Step 15가 이미 확립한 원자성 규약과 동일하다**("문서 생성/이미지 PUT 실패 시 로컬 미저장 + 서버 문서 best-effort 정리" — [`design/web-step15`](../design/web-step15-frame-editor-and-picker.md)). 과금이 추가되면서 **환급**만 새로 붙는다.

### 4.5 오프라인 동작

| 상황 | 동작 | 문구 |
|------|------|------|
| 서버 미도달 + 프레임 생성 시도 | **거부** | "프레임을 만들려면 서버 연결이 필요합니다. 네트워크를 확인해 주세요." |
| 서버 미도달 + 기존 프레임 사용 | **허용**(로컬 캐시) | — |
| 서버 미도달 + 프레임 편집(같은 이름 저장) | **거부**(정본 갱신 불가) | 위와 동일 문구 |
| 서버 미도달 + 로그아웃 | 로컬 캐시 삭제는 **수행**(정본은 서버) | §5 |

## 5. 로그아웃 시 로컬 삭제 — ❌ **폐지(2026-08-07)**

> **이 절 전체(5.1~5.6)는 구현 대상이 아니다.** 소유권 바인딩([`design/wpf-frame-ownership-binding-design.md`](../design/wpf-frame-ownership-binding-design.md))이 `.slots`에 소유자를 서명해 넣으므로, **파일이 남아 있어도 다른 계정에게 보이지 않는다.** 삭제해야 할 이유가 사라졌다.
>

> | F-1 삭제 판정 함정(§5.2) | 접두 규약 폐지로 **소멸** |
> | 부팅 purge·유예 기간·플래그(§5.4) | **불필요** |
>
> 아래 소절은 **이력으로만** 남긴다. 구현하지 말 것.

### 5.1 ~~무엇을 지우고 무엇을 남기나~~ *(이력)*

| 대상 | 로컬 파일 패턴 | 로그아웃 시 | 근거 |

### 5.2 삭제 판정 (F-1 적용 필수)

```
IsOwnedLocalFile(fileName, accountId):
    return fileName.StartsWith(accountId + "_", Ordinal)
        && fileName.Substring(accountId.Length + 1).IndexOf('_') < 0
```

| 규칙 | 내용 |
|------|------|
| 순수 함수 1개 | `FrameNaming.IsOwnedLocalFile`. 로드·삭제·충돌 가드가 **같은 함수**를 쓴다(§2.1) |
| 삭제 짝 | `.png` + `.slots` **함께**. 한쪽만 남으면 `EnumerateFrames`가 `.slots` 없는 png를 스킵하므로(`LocalFrameStore.cs:109`) 조용히 고아가 된다 |
| 실패 허용 | 파일 잠금(썸네일 `Image`가 png를 잡는 알려진 함정 — [`analysis/90 §1`](../analysis/90-roadmap-and-future-work.md)에서 `FilePathToImageConverter` OnLoad+IgnoreImageCache로 해소됨) 시 삭제 실패할 수 있다 → **실패를 삼키지 말고 기록**하고 §5.4의 부팅 정리로 회수 |
| 정보 유출 여부 | 삭제 실패로 파일이 남아도 **다른 계정에게 노출되지 않는다** — `LoadUser`가 F-1로 정확히 판정하고, `LoadPublic`은 `_` 없는 파일만 본다(`LocalFrameStore.cs:59`). 즉 잔존은 **디스크 낭비**이지 유출이 아니다 |

### 5.3 언제 지우나 (트리거)

| 트리거 | 수행 | 근거 |
|--------|:---:|------|
| 명시적 "로그아웃" | ○ | 요구 |
| 세션 만료(401)·강제 로그아웃([06](./06-single-session-enforcement.md)) | ○ | 계정이 바뀌는 것과 동일 효과 |
| **유휴 타임아웃 · 홈 복귀 · 전역 예외 복구** | **×** | ⚠️ 이 경로들은 **로그아웃하지 않는다**(it8 A1, `clearUser: false` — [`analysis/60 §3.5`](../analysis/60-auth-accounts-and-roles.md)). 여기서 파일을 지우면 로그인 상태인데 프레임이 사라진다 |
| 앱 시작 | ○(§5.4 정리) | fail-safe |
| 계정 전환(A 로그아웃 → B 로그인) | A 파일 삭제 후 B 로드 | 순서 보장 필요 |

**배선 지점**: `SessionContext.CurrentUserChanged`에서 `CurrentUser == null`이 되는 **모든** 경로를 한 곳으로 덮는다 — `BackendSessionSynchronizer`가 JWT를 비우는 것과 **정확히 같은 패턴**(`src/MCPhoto.App/Services/BackendSessionSynchronizer.cs` 선례). 웹은 `authStore.installTokenLifecycle`과 같은 구독 지점(`webclient/src/shell/authStore.ts:56-66`).

> ⚠️ **단, 이벤트 핸들러에서 동기 파일 I/O를 하지 않는다.** 로그아웃은 UI 스레드에서 발생하고 파일이 잠겨 있을 수 있다. **큐에 넣고 백그라운드에서 수행 + 실패는 부팅 정리로 회수**한다.

### 5.4 부팅 정리 (fail-safe)

앱 시작 시(로그인 전 = 게스트 상태) **모든 `{X}_` 형태 개인 프레임 파일을 삭제**한다.

| 항목 | 내용 |
|------|------|
| 판정 | 파일명이 `IsOwnedLocalFile(name, X)`를 만족하는 어떤 `X`가 존재하면 개인 파일 → 즉 **"`_`를 포함하고, 마지막 `_` 이후에 `_`가 없는"** 형태. 실질적으로 `_`를 1개 포함한 파일명 전부 |
| 안전성 | 공용·번들은 `_`가 없어 대상이 아니다(사실 3·5). 개인 정본은 서버에 있다(B9) |
| 예외 | **마이그레이션 미완료 파일**(서버에 없는 레거시 로컬 전용 프레임)은 지우면 **영구 유실**이다 → §7의 이관 절차를 **먼저** 배포하고, 이관 유예 기간이 끝난 뒤에 이 정리를 활성화한다 |
| 플래그 | `config/billing.purgeLocalUserFramesOnBoot`(서버 플래그)로 단계 시행 |

### 5.5 웹 클라이언트 대칭 규격

| 저장소 | 내용 | 로그아웃 시 |
|--------|------|:---:|
| IndexedDB `mcphoto-frames`(메타) | 프레임 메타 레코드 | **개인 스코프 레코드 삭제** |
| OPFS(PNG 바이트) | 프레임 이미지 | 동상 삭제 |
| 공용/번들 | `isDefault` 또는 `userId == null` | **유지** |

- 웹은 파일명 접두 규약이 아니라 **레코드 필드(`userId`)** 로 구분하므로 F-1 함정이 없다(구조적으로 더 안전) — `webclient/src/adapters/storage/frameStore.ts`, `webclient/src/domain/frames/frameStorePolicy.ts`.
- ⚠️ 대신 웹은 **zip 내보내기/가져오기**가 있다([`design/web-step16`](../design/web-step16-account-usermgmt-diagnostics-pwa.md)). 가져오기로 들어온 프레임의 스코프 판정 규칙을 명확히 해야 한다 → **가져오기는 "개인 스코프 + 서버 미등록"이 되므로, 서버 정본 전환 후에는 가져오기 시 서버 등록(=과금)을 요구**하거나 "이 기기에서만 사용(로그아웃 시 삭제)"임을 고지한다 → [11 D-12](./11-open-decisions.md).

### 5.6 사용자 고지 (필수)

| 시점 | 문구 |
|------|------|
| 로그아웃 확인 모달 | "로그아웃하면 이 기기에 저장된 **내 커스텀 프레임 {N}개**가 삭제됩니다. 다시 로그인하면 서버에서 자동으로 복원됩니다. 기본 프레임은 유지됩니다." |

| 재로그인 후 | 프레임 로딩 오버레이에 "내 프레임 복원 중..."(it20 4국면 재사용) |

## 6. 로컬 캐시 동기화 규약

### 6.1 로드 순서 (프레임 선택 화면 진입)

| 순서 | 소스 | 실패 시 |
|:---:|------|---------|
| 1 | 번들 프레임(로컬, 즉시) | — |
| 2 | 공용 기본 프레임: 로컬 캐시 → `GET /frames/default`로 갱신 | 캐시로 진행(`Degraded`, it20 규약) |
| 3 | **개인 프레임: `GET /frames?userId=me` → 로컬 캐시와 대조 → 부족분 다운로드** | 캐시로 진행(오프라인) |

### 6.2 대조 규칙

| 상황 | 처리 |
|------|------|
| 서버에 있고 로컬에 없다 | 다운로드 후 캐시 기록 |
| 서버에 있고 로컬에도 있다 | 로컬 사용(재다운로드 금지). 무결성 판정은 이름+`imageSize`로 충분(해시 미보유) |
| **로컬에 있고 서버에 없다** | ⚠️ 두 경우가 섞인다: ① 레거시 로컬 전용(이관 필요 → §7) ② 다른 기기에서 삭제됨(캐시 삭제해야 함) → **구분 수단이 필요**: 캐시 `.slots`에 `#dbid=`가 있으면 서버 등록분(→ 삭제됨으로 판정), 없으면 레거시(→ 이관 대상). ✅ `#dbid` 메타는 **이미 존재**한다(`LocalFrameStore.cs:151-152`, 공용 캐시용) — 개인 프레임에도 기록하도록 확장한다 |
| 이미지 로드 실패(문서만 있음) | "손상된 프레임" 안내 + 삭제 유도(§4.4) |

### 6.3 고아 파일 정리

| 대상 | 정리 시점 |
|------|-----------|
| 이름 변경 저장으로 남은 옛 파일(현행 알려진 이슈) | 개인 프레임 동기화 시 "서버에 없고 `#dbid`가 있는" 파일 → 삭제 |
| `.slots` 없는 png / png 없는 `.slots` | 부팅 정리에서 함께 제거 |

## 7. 레거시 로컬 프레임 이관 — ❌ **불필요(2026-08-07)**

> **Release 전이라 이관할 대상이 없다.** 사용자 확인(2026-08-07): 기존 개인 프레임도, DB default 프레임을 내려받은 PC도 없다(테스트 PC뿐). 따라서 마이그레이션·유예 기간·선택 이관 UI가 **전부 불필요**하다.
>
> 개발 PC에 남은 구 포맷 파일은 base64 디코딩에 실패해 목록에서 자동 제외된다(별도 코드 없음).
>
> ⚠️ **이 면제는 Release 전에만 유효하다.** 배포 후 같은 변경을 하려면 이관 절차가 반드시 필요하다 — 아래 서술을 그때 되살릴 것.

### 7.1 *(이력)* 초판 이관 계획

현재 advanced_user 계정들은 **서버에 없는 로컬 전용 프레임**을 갖고 있다. §5의 purge를 켜면 **영구 유실**된다.

| 단계 | 내용 | 기간 |
|:---:|------|------|
| 1 | 로그인 시 레거시 프레임(=`#dbid` 없는 `{계정}_` 파일) 개수를 세어 **1회 안내 모달**: "이 기기에만 저장된 프레임 {M}개가 있습니다. 서버에 저장하면 다른 기기에서도 쓸 수 있고 로그아웃 후에도 복원됩니다." + [지금 저장(무료)] / [나중에] | 유예 기간 시작 |
| 2 | **이관은 무료**(`grant` 없이 과금 면제 플래그 `migration: true`) — 기존 자산에 과금하면 신뢰를 잃는다 | 유예 기간 |
| 3 | 이관 실패(10개 상한 초과 등)는 사유별 안내 + "내보내기(폴더 열기)"로 백업 유도 | 유예 기간 |
| 4 | 유예 종료(권장 **30일**) 후 `purgeLocalUserFramesOnBoot` 활성화 | — |
| 5 | Windows는 zip 내보내기가 없다 → **`Frame\` 폴더 열기 버튼**으로 대체(사용자가 직접 백업) | 유예 기간 |

> ⚠️ **10개 상한과 이관의 충돌**: 로컬에 15개를 가진 계정은 5개를 이관할 수 없다. 안내 문구에 "최대 10개까지 저장할 수 있어 {K}개는 이관되지 않습니다. 필요한 프레임을 먼저 선택해 주세요."를 넣고 **선택 이관 UI**를 제공한다.
