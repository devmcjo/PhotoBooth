# 12 · Web ↔ Windows 차이 보고서

| 항목 | 값 |
|------|-----|
| 문서 | 웹 클라이언트가 Windows 앱과 **다르게 동작하는 모든 항목**의 단일 목록 |
| 왜 필요한가 | 기능 1개를 추가할 때 **모든 클라이언트에 동일하게 반영**하려면, 이미 다른 부분이 어디인지가 한 표에 있어야 한다 |
| 규칙 | **여기 등재되지 않은 동작 차이는 버그다.** 웹에서만 다르게 만들었다면 반드시 행을 추가한다([10 §8](./10-testing-and-acceptance.md) 수락 기준) |
| 갱신 규칙 | 차이가 생기거나 해소될 때 즉시 갱신. 해소된 항목은 삭제하지 않고 **"해소"로 표시**해 이력을 남긴다 |
| **최종 재확인** | **2026-08-01 (Step 17)** — 그 시점 전 항목 재확인, 신규 차이 0건(근거 §0.1). ⚠️ **이후 2026-08-07 Windows 변경으로 미해소 차이 4건 발생**(C11~C14) — 웹 수정 대기 |

### 0.1 Step 17 재확인 기록 (2026-08-01)

Step 17이 E2E 44건을 실브라우저에서 돌리며 **문서에 없는 동작 차이가 나오는지** 확인했다.
**추가할 행은 없었다.** "조용히 넘어가지 않는다"는 규정에 따라 그 사실을 여기 남긴다.

| 관측한 것 | 왜 차이 행이 아닌가 |
|-----------|---------------------|
| dev에서 `uploads/prepare`가 2건 | React `<StrictMode>`의 **개발 빌드 전용** 이중 effect다. 운영 빌드는 1건이고 PUT·commit은 dev에서도 1건씩이다 → [10 §5.2](./10-testing-and-acceptance.md) |
| `logger.error`가 브라우저 콘솔에 보인다 | `mirrorToConsole`이 개발 빌드에서만 켜진다(05 §7.1의 설계값 그대로) |
| `/favicon.ico` 404 | 저장소에 favicon 파일이 없다. Windows 앱에는 대응 개념이 없고 기능 영향도 없다 — **차이가 아니라 미구현 자산**이다 |
| Worker terminate 시 `VideoFrame` GC 권고 | 브라우저가 찍는 권고 문구다. Worker와 함께 자원이 회수되므로 동작 차이가 아니다 |
| Playwright WebKit에 OPFS·`OffscreenCanvas`가 없다 | **테스트 브라우저 빌드의 한계**이지 Safari의 동작이 아니다(실제 Safari 17+에는 있다) → [10 §6.2b](./10-testing-and-acceptance.md) |

> ⚠️ 이 표는 **E2E가 관측할 수 있는 범위**만 닫는다. 실기기·실계정에서만 드러나는 차이는
> [16 실기기 절차서](./16-field-verification-runbook.md) 수행 중에 발견되며, 그때 §0.2 규칙(설계 결함이면
> 이 문서에 행 추가)을 따른다.

**가장 중요한 3가지 차이**

1. **결과물이 "기기 폴더"가 아니라 "브라우저 저장 공간(OPFS)"에 남는다** — 데스크톱 Chromium에서만 실제 폴더에도 저장 가능(C1).
2. **타임랩스를 만드는 방식이 다르다** — 세션 전체 녹화 없이 프레임 샘플링으로 직접 인코딩. 일부 브라우저에서는 **미제공**(C2·C3).
3. **새로고침·탭 종료 시 로그아웃된다** — JWT 메모리 전용 규칙(M2)의 결과(C6).

### C1. 결과물 로컬 보관 위치와 방식 (WD3 · M6-W)

| | Windows | Web |
|---|---------|-----|
| 어디에 | `{실행경로}\result\mcphoto_YYMMDD_HHMM\` | **OPFS**(브라우저 내부 저장 공간) `results/mcphoto_YYMMDD_HHMM/` |
| 실제 폴더 저장 | 항상 | **데스크톱 Chromium에서만**(운영자가 폴더를 1회 선택하면 그 폴더에도 기록) |
| 파일 탐색기에서 바로 보이나 | ○ | 폴더 지정 시 ○ / 아니면 **✕**(앱의 [보관된 결과물]에서 내보내야 함) |
| 설정의 경로 항목 | 경로 문자열 직접 입력 | **[폴더 선택] 버튼**(브라우저가 실 경로를 노출하지 않음) |
| 용량 정리 | 무기한 영구 보관 | **2GB / 200세션 초과 시 오래된 것부터 자동 삭제**(브라우저 할당량 때문) |
| 불변식 | M6("업로드 이전 저장") | **M6-W**("업로드 이전 **OPFS(또는 선택 폴더) 기록 완료**") |

**사용자 체감**: 데스크톱 Chromium + 폴더 지정이면 Windows와 사실상 동일하다. 태블릿·iOS에서는 "앱 안에 보관되고 [기기에 저장]으로 꺼낸다".

### C2. 타임랩스 생성 방식 (WD2)

| | Windows | Web |
|---|---------|-----|
| 방식 | 세션 전체를 30fps로 `session.mp4` 녹화 → ffmpeg `setpts` 배속 재인코딩 | **녹화 없음.** 촬영 중 OPFS에 스풀(≤15fps) → **종료 시 실제 세션 길이로 균등 선별 → 30fps 타임라인 mp4 인코딩**([04 §7.2](./04-media-pipeline-web.md)) |
| 산출물 | `session.mp4`(업로드 안 함) + `timelapse.mp4` | **`timelapse.mp4`만** |
| 결과 길이 | 10~15초(짧은 세션은 원속) | **동일**(같은 배속 함수를 실경과에 적용 — [바로 촬영] 다용 세션도 원속 산출) |
| **실효 소스 프레임레이트** | 30fps | **최대 15fps**(스풀 수집률 — 출력 타임라인은 30fps, 부족분은 프레임 duration 연장). 움직임이 많은 장면에서 약간 덜 부드러울 수 있다 |
| 계약 | `video/mp4` + H.264 무음 | **동일** |

**사용자 체감**: 결과물은 같다. 다만 웹은 **"세션 원본 영상"이 존재하지 않는다**(향후 원본 영상 기능을 추가하려면 웹은 별도 설계 필요).

### C5. 카메라 권한 (브라우저 정책)

| | Windows | Web |
|---|---------|-----|
| 권한 요청 | 없음(앱이 바로 장치 열기) | **브라우저 권한 대화상자**(최초, 또는 설정에 따라 매번) |
| 사전 요청 | (해당 없음) | **촬영 안내 화면의 [카메라 사용 허용] 버튼**(2026-08-01 신설). 프라이밍 스트림은 획득 즉시 정지해 LED가 켜진 채 남지 않는다 |
| 거부 시 | (해당 없음) | **사유 5종별 전용 안내**([03 §6.3](./03-screens-spec.md)). **앱에서 되돌릴 수 없고 브라우저 설정에서 재허용해야 한다** → [다시 시도]를 **일부러 숨긴다**(권한 거부·비보안 연결) |

**"자동으로 뜨게 해 달라"에 대한 답**(같은 요구가 반복되므로 여기 고정한다)

| 요구 | 가능? | 근거 |
|------|-------|------|
| 페이지가 뜨자마자 **자동으로** 권한 팝업 | **불가능** | 프롬프트는 `getUserMedia()` 호출로만 뜨고, 그 호출은 **사용자 제스처**를 요구한다 |
| **버튼 한 번**으로 촬영 전에 미리 받기 | **가능 · 구현됨** | 명시적 제스처가 있으므로 정상 경로다([03 §5](./03-screens-spec.md)) |
| 현재 권한 상태를 **묻지 않고 조회** | **가능(부분)** | `navigator.permissions.query({name:"camera"})`. Chromium 지원, **Firefox는 throw**, **Safari 미지원** → `null` 폴백 |
| `denied`를 앱이 되돌리기 | **불가능** | 브라우저 사이트 설정에서만 가능 → **복구 방법을 화면에 안내**하는 것이 앱이 할 수 있는 전부 |
| **매번 묻지 않게** 하기 | **가능 · 운영으로만** | Chrome 정책 `VideoCaptureAllowedUrls` 또는 전용 프로필 키오스크 기동([09 §3](./09-kiosk-operations.md)) |
| 장치 이름 | WMI FriendlyName | **권한 부여 전에는 빈 문자열** → "카메라 1/2"로 표시 |
| 장치 식별자 | 열거 인덱스 | `deviceId`(origin·저장소 상태에 따라 재생성될 수 있음 → label·첫 장치 폴백) |

### C11. 신규 설치 기본 컷 수 — Windows "자동" vs 웹 "6" ⚠️ **미해소 — 웹 수정 필요**

| | Windows | Web |
|---|---------|-----|
| `CutCount` **기본값**(신규 설치 · 설정 키 누락 · 파싱 실패) | **`0` = 자동** → 실제 컷 수 `max(6, 슬롯+2)`. 슬롯 5개 프레임이면 **7컷** | **`6` 고정** |
| 이미 저장된 값이 있을 때 | 저장값 우선(`6`이면 6컷) | 동상 |
| 해석식 · clamp · sentinel 가드 · "자동" 옵션 노출 | 동일(it17) | 동일 |

**원인**: Windows 앱만 기본값을 자동으로 바꿨다(2026-08-07, `src/MCPhoto.Core/Settings/AppSettings.cs`). **설정 기본값은 플랫폼 계약**([`analysis/41 §2.1`](../analysis/41-local-data-and-file-formats.md))이므로 이 차이는 등재로 끝낼 항목이 아니라 **해소 대상**이다. 해석 규칙 자체는 양쪽 동일하므로 바꿀 것은 기본값 한 줄뿐이다.

**해소 절차(웹 수정 지시)**

| # | 할 일 | 대상 |
|---|-------|------|
| 1 | `CutCount: 6` → `CutCount: AUTO_CUT_COUNT` (`AUTO_CUT_COUNT`는 같은 파일이 이미 import 중) | `webclient/src/domain/settings/appSettings.ts`의 `DEFAULT_SETTINGS` |
| 2 | 기본값 `6`을 단정하는 테스트를 자동(`0`)으로 갱신 + "기본값=자동" 회귀 1건 추가 | `tests/unit/storage/settingsRepo.test.ts` · `tests/unit/settings/settingsForm.test.ts` · `tests/unit/shell/bootstrap.test.ts` (실제 단정 위치는 실행해 확인) |
| 3 | **수정 불필요 확인** — 공유 벡터는 모든 케이스가 `CutCount`를 명시 주입하므로 기본값 변경에 영향받지 않는다 | `docs/spec-vectors/settings-clamp.json` · `cut-count.json` |
| 4 | **수정 불필요 확인** — e2e 촬영 헬퍼는 `CutCount`를 명시 시드한다(`CutCount: 6`) | `webclient/tests/e2e/fixtures/app.ts` |
| 5 | 문서 갱신 + 이 항목을 "해소"로 표시 | [05 §2](./05-storage-and-persistence.md) 기본값 표·저장 예시 · [`analysis/41 §2.1`](../analysis/41-local-data-and-file-formats.md) 미정합 경고 |

**마이그레이션 금지**: 기존 사용자의 `localStorage`에 `CutCount=6`이 이미 있으면 **그대로 6컷**이다. `6`은 유효한 사용자 선택과 구분할 수 없으므로 코드로 자동 전환하지 않는다(Windows와 동일한 취급).

**검증**: 빈 프로필(새 시크릿 창)에서 슬롯 5개 프레임을 고르고 [다음] → `Guide`에 **"7 (자동)"** 이 표시되면 해소.

### C12. 뷰티 필터 규격 개정 ⚠️ **미해소 — 웹 셰이더 수정 필요 + 골든 테스트 실패 중**

| | Windows | Web |
|---|---------|-----|
| 뷰티 알고리즘 | **개정판**: 피부톤 마스크(YCrCb) → 절반 해상도 bilateral 2회 → 마스크 가중 블렌드(0.85) → 감마 톤업(0.88) → 채도(1.08) → 언샵(0.22) | **종전판**: 전면 bilateral(`d=7`) + `smooth*0.6+src*0.4` + `alpha=1.03/beta=6` |
| 체감 | 피부만 매끄러워지고 톤이 올라 "보정했다"가 읽힌다 | 고해상도에서 효과가 거의 보이지 않는다(개정 이유 그 자체) |
| 흑백·밝게 | 동일 | 동일 |

**원인**: Windows만 뷰티를 개정했다(2026-08-07). 사용자 평가 "흑백·밝게는 알겠는데 뷰티는 구분이 안 된다"에 대한 대응이며, 근본 원인은 **커널이 절대 픽셀 고정**이라 1080p 이상에서 무력해지고 **전면 적용**이라 강도를 올릴 수 없던 구조였다. 규격은 [`analysis/14 §6.1`](../analysis/14-media-pipeline-spec.md).

> ⚠️ **웹 골든 테스트가 지금 실패한다.** `webclient/tests/golden/golden.test.ts`가 `docs/spec-vectors/golden/expected-beauty.png`를 기준으로 웹 합성 결과를 비교하는데, 그 기준 파일이 **새 규격으로 재생성**됐다. 웹 뷰티를 새 규격으로 맞추면 함께 통과한다 — 기준 파일을 되돌리지 말 것(그러면 Windows가 깨진다).

**해소 절차(웹 수정 지시)**

| # | 할 일 | 비고 |

### C13. 세션 완료 화면 폐지 ⚠️ **미해소 — 웹도 같은 폐지 필요**

| | Windows | Web |

| 촬영 완료 후 | **화면 없음** — 홈으로 즉시 복귀 + **비모달 완료 토스트**(하단 중앙, 5초 자동 소멸, [확인]으로 즉시 닫기) | **`Done` 전체화면**("감사합니다" + [처음으로] + 6초 자동 홈 복귀) |
| 상태 머신 | `AppState`에 `Done`이 **없다**(12개). 완료는 상태가 아니라 셸 동작(`CompleteSession`) | `Done` 상태 존재(13개) |
| 완료 경로 | ① effective QR off → `Result`에서 즉시 완료 ② `Qr` [완료] — **둘 다 단일 지점(`CompleteSession`)을 지난다** | 각 경로가 `Done`으로 전이 |
| 로그아웃 | 하지 않음(촬영 후 로그인 유지) | 동일 |

**원인**: 사용자 요청(2026-08-07) — "완료 화면 없이 그냥 홈으로 돌아가고, 완료 사실은 토스트나 확인 버튼 팝업으로". 화면을 하나 더 거치는 것보다 대기 화면으로 바로 돌리는 편이 키오스크 회전에 낫다. 규격은 [`analysis/13 §4.9`](../analysis/13-client-behavior-spec.md).

**해소 절차(웹 수정 지시)**

| # | 할 일 | 비고 |
|---|-------|------|
| 1 | `Done` 화면·상태 제거, 전이표에서 `Result`·`Qr`의 다음을 `Home`으로 | 상태 목록 13 → 12 |
| 2 | 셸에 완료 토스트 추가(문구·5초 자동 소멸·[확인]) | **모달 금지** — 무인 키오스크에서 아무도 닫지 않으면 다음 손님이 막힌다. 토스트는 **셸 소유**여야 한다(홈으로 전이한 뒤에 떠야 하므로 화면 수명과 분리) |

| 4 | 상태 전이·화면 스펙 문서 갱신 + 이 항목 "해소" 표시 | [02](./02-app-shell-and-navigation.md) · [03](./03-screens-spec.md) · [10](./10-testing-and-acceptance.md) |

### C14. 컷 선택 화면 배치 프리뷰 ⚠️ **미해소 — 웹에도 추가 필요**

## H. 후속 제안 (웹 작업에서 발견된 개선점)

웹을 만들며 드러난 것 중 **다른 클라이언트에도 적용할 만한 것**이다. 결정은 사용자·팀에 맡긴다.

| # | 제안 | 근거 |
|---|------|------|
| H1 | **PIN 기기 단위 잠금(5회 → 5분)을 Windows에도 적용** | `docs/analysis/61 §7.3`이 이미 권장. 웹이 먼저 구현(C9)하므로 규격을 맞추면 드리프트가 사라진다 |
| H2 | **로컬 결과물 정리 정책을 Windows에도 도입** | Windows는 무기한 영구 보관이라 디스크가 찬다(`analysis/41 §5` 개선 항목). 웹은 2GB/200세션 정책을 이미 갖는다(C1) |
| H3 | **설정·프레임 내보내기/가져오기를 Windows에도** | 기기 교체·백업 동선이 현재 없다. 웹의 zip 형식이 `Frame\` 규칙과 호환되므로 그대로 재사용 가능(E1·E2) |
| H4 | **`docs/spec-vectors/` 공유 벡터를 정식 자산으로 유지** | 두 클라이언트의 순수 로직 드리프트를 자동으로 잡는다([10 §3](./10-testing-and-acceptance.md)) |
| H5 | 개인 프레임 서버 저장(D7 결정) 재검토 | 도입하면 기기 교체·저장소 회수 문제가 함께 해소된다(`design/multiplatform-client-architecture.md §7.1`에 비용 분석 있음) |
| H6 | 진단 화면에 **실제 해상도·fps** 표시를 Windows에도 | 현장 품질 문의 대응에 유용(E7) |
| H8 | **Primary 버튼 명암비 3.19:1 해소** | `Color.OnAccent`(#FFFFFF) on `Color.Accent`(#FF4D79)는 WCAG AA 일반 텍스트(4.5:1) 미달이다. **색은 WPF와 일치시키기로 팀 리드가 승인했고**(2026-08-01), 대신 웹은 두 가지로 기준을 맞췄다 — ① Primary 버튼 폰트를 **16 → 19px**로 올려 large text(≥18.66px Bold, 3:1) 기준으로 통과, ② 키울 수 없는 작은 요소(세그먼트 선택·"자동" 배지·컷 순번 배지)는 **`--on-accent-ink`(#241F2B, 5.05:1)** 로 글자색만 뒤집음. ⚠️ `#FF4D79` 위에서 4.5:1을 만족하는 **밝은 색은 존재하지 않는다**(필요 상대휘도 1.43 > 1). 근본 해소는 `Color.Accent`를 **양 플랫폼에서 함께** 어둡게 하는 것뿐이다 — **웹 단독 색 변경 금지**. 실측표: [`design/web-fix-20260801-windows-visual-parity.md §4.4.1`](../design/web-fix-20260801-windows-visual-parity.md). 회귀 방지: `themeInvariants.test.ts`의 THEME-2 |
| H9 | **`.primary:hover` 2.71:1** | `Color.Accent.Hover`(#FF6B8F)는 accent보다 밝아 흰 글자가 large text 기준(3:1)도 못 넘는다. **포인터 기기의 일시 상태**(`@media (hover:hover)`)라 터치 키오스크에서는 도달하지 않으므로 남겨 두었다. 해소 조건은 H8과 같다(양 플랫폼 동시 변경) |
| H7 | **JWT 만료(401) 감지 시 세션 해제·재로그인 안내를 Windows에도** | `analysis/60 §5`가 "만료 감지 경로 없음"을 개선 여지로 등재해 둔 상태다. 웹이 먼저 구현(C10)하므로 규격을 맞추면 드리프트가 사라진다 |

## I. 기능 추가 시 규칙 (모든 클라이언트 동기화)

새 기능 1개를 추가할 때 **아래 순서**를 지킨다. 사용자가 이 문서 세트를 요청한 근본 이유가 이것이다.

```
1. 규격을 먼저 쓴다
     docs/analysis/13(동작·문구·타이밍) / 14(미디어) / 31(API) / 41(로컬 데이터) / 60·61(권한·인증)
     → "어떤 플랫폼에서든 이렇게 동작해야 한다"를 확정
2. 공유 테스트 벡터를 추가·수정한다
     docs/spec-vectors/*.json → 양쪽 테스트가 동시에 실패하는 상태를 만든다
3. 각 클라이언트를 구현한다
     Windows: src/MCPhoto.*        (설계는 docs/design/wpf-*)
     Web:     webclient/            (설계는 docs/web-client/)
4. 플랫폼 차이가 생겼다면 이 문서(12)에 행을 추가한다
     차이가 없으면 §A에 항목을 추가한다
5. 수락 체크리스트를 갱신한다
     docs/web-client/10 §8 + docs/analysis/05 §11
```

### I.1 새 기능을 넣기 전 확인할 질문

| 질문 | 왜 |
|------|-----|
| 이 기능은 **서버 계약**을 바꾸는가? | 바꾸면 모든 클라이언트가 동시에 배포돼야 한다. 웹은 즉시 배포되지만 Windows는 인스톨러가 필요하다 → **하위 호환 설계 필수** |
| 브라우저에서 **가능한가**? | 불가하면 이 문서 D 분류에 넣고 대체 수단을 정의한다. "웹은 나중에"로 미루면 드리프트가 굳는다 |
| **불변식 M1~M16 + WM1~WM5**를 건드리는가? | 건드리면 [00 §6](./00-scope-and-decisions.md)을 함께 갱신한다 |
| 설정 키가 추가되는가? | `docs/analysis/41 §2.1`에 키·기본값·범위를 먼저 등재한다. **웹에서 미노출이어도 값은 보존**한다 |
| 새 화면인가? | `docs/analysis/13 §1·§2`(화면 목록·전이표)와 [02 §2](./02-app-shell-and-navigation.md)·[03](./03-screens-spec.md)을 동시 갱신한다 |
| 사용자 문구가 생기는가? | `docs/analysis/13 §14` 카탈로그에 추가하고 양쪽이 같은 문자열을 쓴다(테스트로 고정) |

### I.2 절대 하지 말 것

| 금지 | 이유 |
|------|------|
| 웹에서만 계약 상수를 바꾸기(컷 수·슬롯 수·보관 시간 등) | 같은 프레임·같은 서버를 공유한다. 한쪽만 바꾸면 결과물이 깨진다(WD18) |
| 규격 문서를 건너뛰고 코드부터 고치기 | 두 클라이언트가 조용히 달라진다 |
| 이 문서에 등재하지 않고 웹만 다르게 만들기 | 다음 사람이 그것을 버그로 착각하거나, 반대로 버그를 "의도된 차이"로 오해한다 |
| 브라우저 저장소를 신뢰해 서버 데이터를 대체하기 | 저장소는 회수될 수 있다(F3) |
| JWT를 저장소에 넣어 새로고침 로그인 유지하기 | M2 위반. 필요하면 **HttpOnly 쿠키 세션을 별도 설계**로 다뤄야 한다(현 JWT 모델 변경) |
