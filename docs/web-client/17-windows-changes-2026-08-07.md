## 1. 서버 API 변경 — 웹도 같은 백엔드를 쓴다

같은 Firebase 백엔드를 공유하므로 이 절은 **웹이 코드를 안 고쳐도 이미 적용된** 변경이다.
"내 쪽은 안 건드렸는데 동작이 달라졌다"의 원인이 여기 있을 수 있다.

### 1.1 신설 — `POST /frames/mine` (개인 프레임 생성)

```
POST /frames/mine
게이트: requireBearer + requireFrameWrite(advanced_user 이상)
본문:  { name, imageSize:{width,height}, slots:[{index,x,y,width,height}] }
응답:  201 { frame, upload:{ putUrl, requiredHeaders } }
```

**서버가 `userId`·`isDefault`를 강제한다** — 본문에 넣어도 무시된다. 소유자는 항상 Bearer의 주체다.

`POST /frames`(공용 기본 프레임, `requirePower`)와 **라우트를 나눈 이유**: 한 라우트에서 본문 값으로
분기하면 권한 오판 위험이 커진다. 게이트가 다른 두 기능은 라우트도 나눈다.

### 1.2 완화 — `DELETE /frames/{id}` 게이트

| | 종전 | 현재 |
|---|---|---|
| 게이트 | `requirePower` | `requireFrameWrite` + **핸들러 내 소유자 분기** |
| 본인 개인 프레임 | 삭제 **불가**(서버에 지울 방법이 없었다) | 본인이 삭제 |
| 공용 기본 프레임 | power만 | power만(불변) |
| 타인 개인 프레임 | — | **403** |
| 문서 없음 | `200 {deleted:false}` | 동일(계약 유지 — 존재 여부를 오류로 노출하지 않는다) |

개인 프레임이 서버 정본이 되면서 필수가 된 완화다. 종전 게이트라면 advanced_user가 자기 프레임을
영원히 못 지운다.

### 1.3 신설 — `canWriteFrames` / `requireFrameWrite`

`web/functions/src/domain/roles.ts` · `http/auth.ts`. C#의 `UserRoleExtensions.CanWriteFrames` 이식.

> ⚠️ **`isPower`와 다른 축이다.** power(manager/admin)는 *공용* 프레임을 만들 수 있고,
> `canWriteFrames`는 *개인* 프레임을 만들 수 있는가를 답한다. 두 축을 합치면
> advanced_user에게 공용 생성이 열리거나 power에게 개인 생성이 막힌다.
> 회귀는 `web/functions/src/__tests__/authGates.test.ts`가 잡는다.

### 1.4 Storage 경로 분리 — 개인은 `frames/users/` 아래로

| 종류 | 종전 | 현재 |
|------|------|------|
| 공용 기본 | `frames/default/{frameId}.png` | **동일**(변경 없음) |
| 개인 | `frames/{userId}/{frameId}.png` | **`frames/users/{userId}/{frameId}.png`** |

**왜 `users/`를 끼웠나** — 계정 id는 형식 검증만 거친다. `default@…`로 가입하면 id가 `default`가 되고,
종전 규칙에서는 그 계정의 개인 프레임이 **공용 경로에 섞인다**. 게다가 계정 삭제 cascade가
`frames/{userId}/`를 통째로 지우므로 **공용 프레임이 삭제된다.**

경로 규칙은 `web/functions/src/domain/framePaths.ts` **단일 출처**다. 웹이 Storage 경로를 직접
조립하는 코드가 있다면 이 모듈을 쓰도록 바꿔라 — 규칙이 복제되면 이관 스크립트가 멀쩡한 파일을
고아로 오판한다.

### 1.5 업로드 크기 상한 8MB — **서명 조건**으로 강제

`x-goog-content-length-range: 0,8388608`을 **서명에 포함**해 발급한다. 클라이언트가 헤더를 빼거나
바꾸면 서명이 깨져 GCS가 거부한다. `requiredHeaders`에 같은 값이 실려 오므로 **그대로 전송**하면 된다.

- 클라 사전 검증은 즉시 피드백용일 뿐 방어선이 아니다. 그래도 두는 편이 낫다(8MB 업로드 후 거부는 낭비).
- ⚠️ **Emulator는 이 조건을 강제하지 못한다**(서명이 없다). 로컬에서 통과했다고 운영에서 통과하는 게 아니다.

### 1.6 폐지·신설된 제약

| 항목 | 변경 |
|------|------|
| 계정당 프레임 **개수 상한** | **폐지**(종전 10개). 상한을 과금 상품으로 만들려다 폐기 — 유료인데 못 만드는 상태가 생기고, 상한 하향 시 기존 프레임 처리가 곤란하다 |
| 계정 내 **이름 중복** | **409 신설**. 클라도 사전 검증하지만 PC 두 대 동시 생성은 서버만 막을 수 있다 |
| `PUT /frames/{id}`(수정) | **라우트는 유지, 클라 호출은 0.** 운영/관리 도구 전용. 앱에서 수정 기능이 폐지됐다(§2.3) |

### 1.7 이관 스크립트 (웹은 조치 불요, 인지만)

`web/functions/scripts/migrate-frame-storage-paths.mjs` — 기본 dry-run. 구 경로 개인 프레임을
신 경로로 옮긴다. **공용 프레임은 경로가 안 바뀌었으므로 대상이 아니다.**
실행은 사용자가 검증 후 직접 한다.

## 2. 클라이언트 동작 변경 — 웹도 맞춰야 한다

차이 보고서 [12](./12-web-vs-windows-differences.md)에 **C11~C16**으로 등재돼 있다. 여기서는 요지와 순서만 준다.

### 2.1 우선순위 제안

| 순서 | 항목 | 이유 |
|:----:|------|------|
| 1 | **C11** 기본 컷 수 자동 | 한 줄 + 테스트. 가장 싸다 |
| 2 | **C13** 완료 화면 폐지 | 상태 머신이 걸려 있어 뒤로 미룰수록 충돌이 커진다 |
| 3 | **C12** 뷰티 규격 | 골든 테스트가 지금 빨간불 |
| 4 | **C14** 배치 프리뷰 | 독립 기능. 앞의 것과 안 겹친다 |
| 5 | **C16** 실패 문구 계약 | 아래 §3 — C15 착수 전에 해두면 C15의 오프라인 처리가 쉬워진다 |
| 6 | **C15** 프레임 소유권·서버 정본 | 가장 크다. **미결정은 모두 해소됐다**(§4) |

### 2.2 C11~C14 요지

| # | 무엇이 바뀌었나 | 규격 |
|---|----------------|------|
| **C11** | `CutCount` 기본값 `6` → **`0`(자동)**. 해석식·clamp는 종전 그대로 | [12 C11](./12-web-vs-windows-differences.md#c11-신규-설치-기본-컷-수--windows-자동-vs-웹-6--미해소--웹-수정-필요) |
| **C12** | 뷰티가 **6단계 개정판**으로 교체(피부톤 마스크 → 절반 해상도 bilateral ×2 → 마스크 블렌드 → 감마 톤업 → 채도 → 언샵) | [`analysis/14 §6.1`](../analysis/14-media-pipeline-spec.md) |
| **C13** | 완료 화면(`Done`) **폐지** → 홈 즉시 복귀 + **비모달 토스트 5초** | [`analysis/13 §4.9`](../analysis/13-client-behavior-spec.md) |
| **C14** | 컷 선택 화면 **좌측 배치 프리뷰** 추가 | [`analysis/13 §4.5.1`](../analysis/13-client-behavior-spec.md) |

**C12에서 픽셀 동일은 불필요.** 지켜야 하는 것은 셋이다 —
① 커널이 **해상도 비례**(축소 후 처리 → 확대) ② **피부에만** 스무딩 ③ 톤업·채도·언샵 동반.
개정 이유가 "1080p에서 커널이 절대 픽셀이라 무력했다"이므로 ①을 빠뜨리면 개정한 의미가 없다.

**C13은 토스트를 셸이 소유해야 한다.** 홈으로 전이한 *뒤에* 떠야 하므로 화면 수명과 분리된다.
그리고 **모달 금지** — 무인 키오스크에서 아무도 닫지 않으면 다음 손님이 막힌다.

**C14는 매핑 함수를 공유하라.** 프리뷰용 매핑을 따로 구현하면 "미리보기와 결과물이 다르다"가 나온다.
Windows는 `SlotFillPlan.Build` 순수 함수를 합성과 공유한다.

### 2.3 C15 — 프레임 소유권·서버 정본 (가장 큰 변경)

| 축 | Windows 현재 |
|----|-------------|
| 개인 프레임 정본 | **서버**(`POST /frames/mine`), 로컬은 캐시 |
| 소유 판정 | **서명된 `#owner`(이메일)**. 파일명·폴더·id 접두는 판정에 쓰지 않는다 |
| `.slots` 포맷 | **v2** — `base64(payload + "\n#sig=" + HMAC-SHA256hex)` |
| 프레임 **수정** | **전면 폐지**(개인·공용 모두) |
| 삭제 | **서버 먼저 → 성공해야 로컬**. 실패 시 로컬 보존 |
| 삭제 동기화 | 서버에 없으면 로컬 캐시 삭제(공용·개인 모두) |
| 개수 상한 | 없음 |

#### `.slots` v2 payload 규격 — **참고용(웹 구현 불요)**

> §4.1 결정으로 **웹은 `.slots`를 만들지도 읽지도 않는다.** 아래는 Windows 내부 규격이며,
> 웹이 서버에 올린 프레임을 Windows가 캐시할 때 **Windows가 자기 키로 직접 서명해 기록**한다.
> 규격을 남겨 두는 이유는 진단·로그 해석 때 필요하기 때문이다.


```
#v=2
#owner=a@example.com        ← 공용은 default
#imagesize=1200,1600
#dbid=abc123                ← 없으면 줄 자체를 생략(서버 미동기)
0,80,117,490,653            ← index,x,y,width,height
1,630,117,490,653
```

파일 = `base64(위 payload + "\n#sig=" + HMAC-SHA256hex(key, payload))`.

> **필드 순서가 계약이다.** 순서가 흔들리면 같은 내용이 다른 서명을 낳는다.
> payload를 JSON으로 하지 않은 이유도 이것 — JSON은 키 순서·공백·이스케이프에 따라
> 같은 의미의 다른 바이트열이 나와 canonical 직렬화 규약을 따로 정의해야 한다.

벡터: `docs/spec-vectors/slots-file.json`(`expectedPayload` 필드가 정본).
서명 키는 벡터에 없다 — **payload 텍스트 규격과 파싱 규칙만** 고정한다.

#### 웹의 저장 구조 — 바뀌는 것과 안 바뀌는 것

**웹의 1차 저장소는 IndexedDB(메타) + OPFS(PNG)다.** 이건 그대로 둔다.
바뀌는 것은 **그 저장소의 지위**다 — 정본이었던 것이 **캐시**가 된다(§4.2).

| | 종전 | 확정 |
|---|---|---|
| IndexedDB + OPFS | **정본** | **캐시** |
| 서버 | 미사용(개인 프레임) | **정본** |
| `.slots` 파일 | 내보내기 형식 | **웹은 다루지 않는다**(§4.1) |
| 소유 판정 | `userId` 필드 | 그대로 — `frameStore.ts`의 `by_owner` 인덱스를 쓰면 된다 |

`.slots` v2 코덱을 구현할 필요가 없어져 C15의 작업량이 크게 줄었다. 실제로 할 일은
**저장 경로를 서버로 돌리고, 삭제 순서를 뒤집고, 삭제 동기화를 넣는 것**이다.

#### ✅ 서명 키 — 웹에 **넣지 않는다** (확정, §4.1)

Windows는 키를 소스 상수로 exe에 박는다. 리버싱하면 추출되지만 노력이 든다.
**JS는 그냥 읽힌다.** 웹에 키를 넣는 순간 키가 사실상 공개되고, **Windows의 방어까지 같이 무너진다**
(같은 키를 쓰므로). 이건 정도 차이가 아니라 방어선이 0이 되는 문제다.

**결정 완료**: 웹은 `.slots`를 다루지 않는다. 프레임 공유는 서버 경유가 유일한 경로다(§4.1).

#### 수정 폐지에서 반드시 같이 없앨 것

Windows에서 "수정 기능 제거"를 한 번 했는데 **경로가 남아 있었다.** 웹도 같은 함정에 빠질 수 있다:

| 함정 | 왜 위험한가 |
|------|------------|
| **"불러오기 후 같은 이름으로 저장"** | 사실상 수정 기능이다. 불러오기는 **항상 새 프레임**이어야 한다 |
| 그 세션만 이름 충돌 검사를 건너뛰는 예외 | 위 함정을 성립시키는 장치. 함께 제거 |
| id 접두(`local:` 등)로 소유를 판정하는 코드 | 개인 프레임이 서버 id를 갖게 되면 **공용으로 오판**한다. Windows에서 삭제 버튼이 사라지는 버그로 나타났다 → **소유자 필드로 판정** |
| "이 PC에만 적용됩니다" 류 안내 | 서버 정본 전환으로 **거짓말**이 된다 |

웹 관련 파일(추정 — 실제 위치는 확인 필요):
`webclient/src/screens/frameEditor/frameEditorEntry.ts` · `frameSelectActions.ts` · `frameSavePolicy.ts`

#### 삭제 동기화 안전장치 3종 (그대로 이식할 것)

서버에 없는 로컬 캐시를 지우는 기능인데, **잘못 만들면 프레임이 전부 사라진다.**

| # | 안전장치 |
|:-:|---------|
| 1 | 서버 **미도달**(오프라인·타임아웃)이면 **아무것도 지우지 않는다** |
| 2 | 서버 목록이 **비어 있으면** 지우지 않는다(장애 응답과 구분 불가) |
| 3 | **`#dbid`를 가진 항목만** 삭제 후보(번들·미동기 로컬은 자동 보호) |

그리고 **선택 이후에는 동기화하지 않는다** — 세션이 쓰는 프레임 파일이 사라지면 합성이 실패한다.
고른 프레임은 서버에서 지워졌더라도 **그 세션 끝까지 정상 사용**된다.

#### UI 규격 변경 (같이 반영)

| 항목 | 규격 |
|------|------|
| 저장 스코프 | **라디오**(개인/공용). **기본 미선택** → 고르기 전까지 [저장] 비활성. [닫기] 별도 |
| power | 개인 프레임 **무료**, 개인 저장이 기본 선택지 |
| 삭제 문구 | "**영구적으로 삭제됩니다**" |
| 공용 프레임 삭제 | **확인 체크(라디오 디자인 공용)** 필수 → 미체크면 확인 버튼 비활성 |
| 슬롯 이동 | **키보드 방향키**(1px, Shift 10px) + 선택 포커스 |
| 진단 화면 | 프레임 파일 검사 — 본인 것만, power는 전체 |

## 3. C16 (신규 등재) — 서버 실패 문구 계약

> 이 항목은 오늘 마지막에 추가돼 **차이 보고서에 아직 행이 없다.** 이 문서가 1차 규격이다.

### 3.1 무엇이 문제였나

Windows가 예외 메시지를 그대로 화면에 찍고 있었다. 실제 노출되던 문장:

| 상황 | 노출되던 문장 |
|------|--------------|
| 서버 주소 미설정 | `An invalid request URI was provided…` (.NET 영문) |
| 토큰 만료(401) | `토큰 검증 실패: jwt expired` |
| 네트워크 끊김 | `백엔드에 연결할 수 없습니다.` (사실이지만 조치가 없다) |

**토큰 수명이 8시간**이다. 아침에 로그인한 키오스크가 저녁에 `jwt expired`를 띄운다 — 예외가 아니라 일상이다.

### 3.2 계약

**원인 판정은 타입으로 한다. 메시지 문자열로 분기하지 않는다** — 그러면 문구를 고치는 순간 로직이 깨진다.

| 상황 | Windows 타입 | 웹 대응(제안) |
|------|-------------|--------------|
| 서버 주소 미설정 | `BackendNotConfiguredException` | 판별 가능한 오류 종류 하나 |
| 연결 실패·타임아웃·업로드 PUT 실패 | `BackendUnavailableException` | 〃 |
| Bearer 없음 | `BackendLoginRequiredException(Expired=false)` | 〃 |
| **401** | `BackendLoginRequiredException(Expired=true)` | 〃 |
| 403 | `UnauthorizedAccessException` | 〃 |
| 400 | `ArgumentException` — 서버 한국어 문구 인용 | 〃 |
| 404·409·5xx | 서버 한국어 문구 인용 | 〃 |

웹은 예외 클래스 계층이 없어도 된다 — `kind` 판별 필드를 가진 오류 객체면 충분하다.
**중요한 건 타입/코드로 갈린다는 것**이지 클래스 상속이 아니다.

### 3.3 문구 조립 규칙

**①무엇이 안 됐는지 ②왜 ③무엇을 하면 되는지** + 오해 방지 사실.

```
서버에 연결할 수 없어 저장하지 못했습니다. 프레임은 서버에 보관되므로 인터넷 연결이 필요합니다.
네트워크를 확인한 뒤 [저장]을 다시 눌러 주세요. 편집 중인 내용은 그대로 남아 있습니다.
```

| 맥락 | 반드시 붙일 사실 | 없으면 |
|------|----------------|--------|
| 저장 실패 | "편집 중인 내용은 그대로 남아 있습니다" | 다 날아간 줄 알고 처음부터 다시 만든다 |
| 삭제 실패 | "이 PC의 파일은 그대로 둡니다" | "지웠는데 목록에 남아 있다"로 읽힌다(서버우선 삭제의 정상 동작인데) |

**사전 안내도 함께**: 프레임 편집기 저장 캡션에
*"프레임은 서버에 보관되므로 저장하려면 인터넷 연결이 필요합니다"*를 상시 표시한다.
다 만들고 [저장]을 눌러서야 실패를 아는 것을 막는다.

### 3.4 ⚠️ 401을 일괄로 "로그인 만료"로 처리하지 말 것

`PUT /accounts/me/pin`의 401은 **"현재 PIN 불일치"이거나 "토큰 만료"**인데
서버가 둘 다 `code:"unauthorized"`로 준다. 만료로 단정하면 PIN을 틀린 사용자에게 재로그인을 시킨다.

**이 라우트만** 원인을 단정하지 않는 문구를 쓴다:
> "현재 PIN이 올바르지 않습니다. 계속 실패하면 로그인이 만료된 것일 수 있으니 다시 로그인해 주세요."

웹은 [C10](./12-web-vs-windows-differences.md#c10-jwt-만료401-감지-시-세션-해제-웹-추가-동작)으로
**401 감지 시 세션 해제**를 이미 하고 있다. 그 로직이 PIN 라우트에도 걸리면
**PIN을 한 번 틀렸다고 로그아웃**된다. 반드시 확인하라 — 웹에만 있는 동작이라 Windows 쪽 검증에 안 걸린다.

> 서버가 토큰 실패에 `token_invalid` 같은 별도 code를 주면 이 예외 케이스가 사라진다.
> 지금 바꾸면 구버전 클라이언트가 401 처리를 잃으므로 **클라이언트 배포 이후**로 미뤘다.

### 3.5 오프라인인데 **조용해야** 하는 곳 (변경 금지)

프레임 **목록 로딩**의 서버 실패는 안내하지 않는다. 로컬 캐시로 조용히 운영하는 것이 정상 동작이다 —
안내를 띄우면 매 진입 노이즈가 된다. Windows `FrameLoadPolicy`가 이를 명시하고 있고, 웹도 동일하게 두라.

**말해야 하는 곳은 사용자가 행동한 결과가 실패했을 때**(저장·삭제·한도 변경)뿐이다.

## 4. 사용자 결정 — **2026-08-07 확정 완료**

세 건 모두 결정됐다. 아래대로 진행하며, **재론하지 말 것**.

### 4.1 `.slots` 서명 키를 웹에 넣는가 → **(가) 넣지 않는다** ✅

**근거(사용자)**: *"프레임 내보내기라는 기능은 없다. 웹에서 만든 프레임을 Windows가 쓰는 경로는 **DB를 통한 다운로드**다."*

이 근거가 §4.1의 유일한 반대 사유(웹→Windows 파일 이동)를 없앤다. 실제 경로는 이렇게 돈다:

```
웹에서 프레임 생성 → POST /frames/mine → 서버(정본)
                                          ↓ 다운로드
Windows가 캐시하며 .slots v2를 **자기 키로 직접 서명해 기록**
```

**웹은 `.slots` 파일을 만들 일도 읽을 일도 없다.** 키 공유가 애초에 필요 없으므로 Windows 방어도 그대로 유지된다.

**웹이 할 일**:

| 할 일 | 내용 |
|---|---|
| 서명 키 | **넣지 않는다.** 어떤 형태로도 JS 번들에 포함 금지 |
| `.slots` v2 코덱 | **구현하지 않아도 된다** — 웹 1차 저장소는 IndexedDB + OPFS다 |
| `slots-file.json` 벡터 테스트 | 웹이 `.slots`를 다루지 않기로 했으므로 **해당 벡터를 웹 테스트 대상에서 제외**한다(삭제가 아니라 제외 — Windows가 쓴다). 제외 사유를 테스트 파일에 주석으로 남길 것 |

> ✅ **확인 완료 → 폐기 결정.** 웹의 프레임 zip 내보내기/가져오기는 사문이 아니라 **설정 화면에
> 버튼까지 노출된 실기능**이었다. 서버 정본 전환으로 명분이 사라져 **폐기**로 확정했다 — 삭제 범위는 §4.4.

### 4.2 웹 개인 프레임도 서버 정본으로 → **(가) 그렇게 한다** ✅

4.1의 근거("웹 프레임을 Windows가 DB로 받는다")가 곧 이 결정이다. **WD4의 "서버 저장 승격 없음"은 폐기된다.**

| 항목 | 확정 |
|---|---|
| 개인 프레임 저장 | `POST /frames/mine` — 서버가 정본 |
| 로컬(IndexedDB + OPFS) | **캐시**. 정본이 아니다 |
| 삭제 | 서버 먼저 → 성공해야 로컬 |
| 삭제 동기화 | 서버에 없으면 로컬 캐시 제거(안전장치 3종 필수) |
| 오프라인 프레임 **생성** | **거부**(Windows와 동일). 기존 프레임 **사용**은 계속 허용 |

**부수 효과 — 로컬 변조 위험이 스스로 줄어든다**: 로컬이 캐시가 되면서, 사용자가 IndexedDB를 편집해도
**다음 동기화에 서버 값으로 덮인다.** 4.1에서 서명을 포기해도 실질 손실이 없는 이유이기도 하다.

### 4.3 8MB 사전 검증 → **웹에도 넣는다** ✅

서버가 서명 조건으로 강제하지만, 8MB를 다 올린 뒤 실패를 아는 것은 낭비다. 저장 전 검증 + 안내.

### 4.4 프레임 zip 내보내기/가져오기 → **기능 폐기** ✅

**경위**: §4.1 결정 근거가 *"프레임 내보내기 기능은 없다"*였는데, 확인해 보니 **웹에는 실제로 구현돼
설정 화면에 버튼까지 노출돼 있었다**(`SettingsView.tsx` — [프레임 내보내기]·[프레임 가져오기]).

그대로 두면 **눈에 보이는 기능이 조용히 깨진다** — 웹이 만든 zip 속 `.slots`는 v1이라 Windows가
가져올 때 목록에서 제외한다. §4.1로 "zip에 v2를 담는다"는 선택지는 닫혔으므로 **폐기**로 확정.

**폐기 근거**: 이 기능의 명분은 `WB3`("브라우저 저장소가 회수돼도 내보내기로 복구 가능")이었다.
**프레임이 서버 정본이 되면서(§4.2) 복구가 서버 재동기화로 이뤄진다** — 명분이 소멸했다.
백업 수단을 하나 더 유지할 이유가 없다.

## 5. 함정 모음 — Windows에서 실제로 밟은 것들

같은 실수를 반복하지 않도록 남긴다.

| 함정 | 증상 | 교훈 |
|------|------|------|
| **id 접두로 소유 판정** | 개인 프레임이 서버 id를 갖자 공용으로 오판 → **삭제 버튼이 사라짐** | 소유는 **소유자 필드**로 판정. 판정 지점이 여러 곳이면 전부 고쳐야 한다(한 곳을 놓쳤다) |
| **삭제를 로컬 먼저** | 다음 동기화에서 서버에서 다시 받아와 **되살아남** | **서버 먼저 → 성공해야 로컬** |
| **삭제 실패를 조용히 처리** | "지웠는데 남아 있다" | 실패를 반드시 노출 + 로컬 보존 사실을 함께 |
| **부분 성공 허용** | 서버 실패 후 로컬만 저장 → 재시도 시 **이름 충돌 가드가 자기 자신과 충돌**해 영영 저장 불가 | 원자성: 서버 실패면 로컬도 안 쓴다 |
| **캐시 실패 재시도 루프** | 검증 실패한 프레임을 매 로딩마다 재다운로드 | 실패 id를 기억해 그 실행 동안 재시도 금지 |
| **`default@…` 계정 id 충돌** | 개인 프레임이 공용 경로에 섞이고 cascade가 공용을 지움 | 경로에 `users/` 세그먼트로 네임스페이스 분리 |
| **"수정 폐지"의 잔존 경로** | 불러오기 후 같은 이름 저장이 사실상 수정 | 폐지는 **진입 경로 전수**를 봐야 한다 |
| **예외 메시지 그대로 노출** | 영문·jargon이 손님 화면에 | 타입으로 분기해 문구 조립 |
