## 2. 클라이언트 설정

### 2.1 항목 전수

**범위를 벗어난 값은 로드·저장 시점에 보정(clamp)한다.** 열거형 값은 허용 집합에서 **가장 가까운 값**으로 보정하며, 동률이면 집합의 첫 값을 쓴다.

| 키 | 타입 | 기본값 | 범위·보정 | 영향 |
|----|------|--------|-----------|------|
| `CutCount` | int | **`0`=자동** (데스크톱. ⚠️ 웹 클라이언트는 아직 **6** — 아래 주의) | 허용 {6, 8, 10} — 최근접 보정. **`0`=자동은 보정 제외**(sentinel 보존); `-1` 등 다른 값은 종전대로 6 | 촬영 컷 수의 **의도**. 실제 컷 수는 슬롯 수 확정 후 산출(§2.7) |
| `CountdownSec` | int | **6** | 허용 {3, 6, 8, 10} — 최근접 보정 | 컷당 카운트다운 초 |
| `MirrorMode` | bool | **true** | — | 좌우반전(프리뷰=저장 동일) |
| `FlashMode` | bool | **false** | — | 셔터 직전 화면 하양 플래시 |
| `ShutterSound` | bool | **false** | — | 촬영 순간 효과음 |
| `RetakeEnabled` | bool | **false** | — | 재촬영 사용(상위 토글). off면 재촬영 UI 전부 미노출 |
| `RetakeLimit` | int | **1** | 허용 {1, 2, 3} — 최근접 보정 | 전체 재촬영 횟수 상한(`RetakeEnabled` on일 때만 의미) |
| `OutputFormat` | enum | **Jpg** | {Jpg, Png} | 최종 이미지 포맷·확장자 |

| `FilterBeauty` | bool | **true** | — | "뷰티" 노출 |
| `SaveLocalCopy` | bool | **true** | — | 결과물 로컬 보관(QR과 독립) |
| `LocalSavePath` | string | **""** | — | 빈 값이면 플랫폼 기본 결과물 위치 |
| `DisplayMode` | enum | **Windowed** | {Fullscreen, Windowed} | 키오스크 표시 모드. **데스크톱 전용** |
| `WindowBounds` | 구조 | Left/Top 미지정, W=1280, H=720 | Width ≥ 1280, Height ≥ 720. Left/Top는 **미보정** | 창 크기·위치. **데스크톱 전용** |
| `CameraDevice` | 장치 식별자 | **0** | 음수면 0 | 사용할 카메라(§2.2) |

| `ExternalCameraModel` | string | `NikonD5300` | 미지 Id → 기본 모델 | 모델 레지스트리 Id. md3 파일명은 여기서 유도 |
| `ExternalShutterSpeed` / `ExternalAperture` / `ExternalIso` | string | **""**(미지정) | 트림만 | 노출 3요소 표시 문자열(`1/125`·`f/5.6`·`400`). 빈 값 = 카메라 현재값 유지 |

**보조 상수**: 허용 컷수 {6,8,10} · 허용 카운트다운 {3,6,8,10} · 허용 재촬영 상한 {1,2,3} · 보관시간 1~72 · 슬롯 1~6 · 자동 컷수(sentinel **0**, 최소 **6**, 슬롯 여유분 **+2**).

> ⚠️ **`CutCount` 기본값은 플랫폼 간 미정합 상태다.** 데스크톱(WPF)은 **자동(`0`)** 이 기본이고, 웹 클라이언트(`webclient/src/domain/settings/appSettings.ts`)는 아직 **6**이다. clamp·해석 규칙(§2.7)은 양쪽이 동일하며 공유 벡터(`docs/spec-vectors/settings-clamp.json`·`cut-count.json`)는 모든 케이스에 `CutCount`를 명시하므로 벡터는 영향을 받지 않는다. 웹도 자동으로 맞출지는 미결정.
>
> ⚠️ 자동 sentinel `0`은 **허용 컷수 집합에 넣지 않는다.** 넣으면 `CutCount=3` 같은 오입력이 6이 아니라 0(자동)으로 보정된다(거리 동률 → 집합의 첫 값 승리). 최근접 보정 **앞에 sentinel 가드**를 두는 것이 규격이다.

> ⚠️ **`HostingBaseUrl`은 트레일링 슬래시를 제거하고 `BackendBaseUrl`은 부여한다.** 방향이 반대인 이유는 용도가 다르기 때문이다 — 앞은 문자열 연결(`{base}/?s={token}`)이고, 뒤는 HTTP 클라이언트의 base URL로서 상대 경로 결합에 슬래시가 필요하다. 두 값을 같은 정규화 함수로 처리하지 말 것.

### 2.2 `CameraDevice`의 플랫폼별 의미

Windows 구현은 이 값을 **장치 인덱스(int)** 로 쓴다. 플랫폼마다 안정적인 식별자가 다르므로, 각 클라이언트는 아래처럼 해석하고 **자기 플랫폼 안에서만 일관되면 된다**(이 값은 서버로 전송되지 않는다).

| 플랫폼 | 권장 식별자 |
|--------|-------------|
| Windows | 열거 인덱스(현행) |
| macOS / iOS / iPadOS | `AVCaptureDevice.uniqueID`(문자열) 또는 위치(전면/후면) |
| Android | `cameraId`(문자열) |
| 웹 | `MediaDeviceInfo.deviceId`(문자열) |

- 저장된 식별자가 현재 목록에 **없으면 첫 장치로 보정**한다([13 §8.6](./13-client-behavior-spec.md)).
- 장치 이름 표시는 best-effort다. 이름을 못 얻어도 **인덱스/식별자 기준 동작은 유지**해야 한다.

### 2.3 게스트 편집 제한 대상

게스트(비로그인)가 편집할 수 없는 항목: `MirrorMode` · `RetakeEnabled` · `RetakeLimit` · `FilterGrayscale` · `FilterBrightness` · `FilterBeauty` · `EnableQrDelivery` · `SendPhoto` · `SendTimelapse` · `HostingBaseUrl` · `StorageBucket`.

- 화면에는 **OFF로 표시 + 비활성 + "로그인 필요" 안내**를 보이지만, **저장 시 이 키들을 기록하지 않아 기존 값을 보존**한다.
- **런타임 동작은 저장된 값(운영자가 설정한 값)대로 유지**된다. 제한되는 것은 편집 권한뿐이다.
- 이 게이트는 **화면 로직에만** 존재한다. 설정 모델은 전 필드를 항상 직렬화한다.

### 2.4 QR 전송 정규화 규칙

```
정규화(로드·저장 시):
  if EnableQrDelivery && !SendPhoto && !SendTimelapse:
      EnableQrDelivery = false          # 하위 토글 값은 그대로 보존

재활성(화면에서 사용자가 off → on 으로 바꾼 순간):
  SendPhoto = true;  SendTimelapse = true
```

재활성 규칙은 **화면 로직**에만 있다(설정 모델의 정규화에는 없다). 설정 로드 중에는 억제해야 한다.

### 2.5 배포 게이트 키 취급

| 규칙 | 내용 |
|------|------|
| 기본 출처 | **빌드 시 바이너리에 주입**한다(Windows는 어셈블리 메타데이터, 다른 플랫폼은 빌드 설정/리소스) |
| 오버라이드 | 설정 파일에 값이 있으면 그 값이 **우선**한다 |
| **저장 금지** | 설정을 저장할 때 이 키를 **다시 쓰지 않는다**(평문 유출 방지) |
| 표시 금지 | 진단 화면에는 **"설정됨/미설정"만** 표시한다. 값 자체를 절대 노출하지 않는다 |
| 로그 금지 | 로그에 남기지 않는다 |
| 플랫폼별 키 | 플랫폼마다 **다른 키를 발급**받는 것을 권장한다(유출 시 해당 키만 폐기 가능). 서버는 CSV로 다수 키를 지원한다 |
| ⚠️ 브라우저 | 웹 클라이언트에 넣으면 **완전히 공개된다**. [05 §9 B4](./05-cross-platform-client-guide.md)의 결정이 선행돼야 한다 |

### 2.6 저장 신뢰성 규격

| 요구 | 내용 |
|------|------|
| **성공/실패 반환** | 저장 함수는 성공 여부를 **반환**해야 한다. 예외를 삼켜 로그만 남기고 성공처럼 보이게 하면 안 된다 |
| 화면 처리 | 실패 시 오류 안내를 표시한다(성공 안내와 시각적으로 구분). "저장 위치에 쓸 수 없습니다." |
| 로드 실패 | 파일 부재·손상 시 **크래시 없이 기본값**으로 진행하고 경고 로그를 남긴다. 이후 clamp를 적용한다 |
| 부수적 저장 | 창 위치 저장처럼 부수적인 저장은 실패해도 무해하므로 반환값을 무시할 수 있다 |
| 파서 내구성 | 손상된 줄·알 수 없는 키는 **무시**하고 계속 파싱한다(예외 없이) |

**Windows 구현의 경로 폴백(참고)**: 실행 경로 → `%ProgramData%\MCPhoto` → `%LocalAppData%\MCPhoto` 순으로 **실제 I/O 프로브**(디렉터리 생성 + 임시 파일 쓰기·삭제)를 해서 쓰기 가능한 첫 경로를 고르고, 첫 성공 경로를 이후 기본 경로로 승격한다. **다른 플랫폼에서는 이 폴백이 불필요**하다(앱 샌드박스가 쓰기 가능한 위치를 보장). 이식해야 하는 것은 폴백이 아니라 **"쓰기 실패를 사용자에게 알린다"** 는 성질이다.

### 2.7 자동 컷 수 규격 (it17)

`CutCount`는 **설정 의도**이고, 실제 촬영 컷 수는 **다른 값**이다. 두 도메인을 섞지 않는 것이 이 규격의 핵심이다.

| 도메인 | 값 범위 | 저장 대상 |
|--------|---------|-----------|
| 설정 의도(`CutCount`) | `{0}` ∪ `{6, 8, 10}` | ✅ 설정 파일에 왕복 |
| 실제 컷 수 | 임의 양의 정수(6, 7, 8, 10, …) | ❌ 저장하지 않음(세션 런타임 값) |

- 해석은 **프레임(슬롯 수)이 확정된 직후 1회만** 수행한다: 자동이면 `max(6, 슬롯 수 + 2)`, 고정이면 `max(설정값, 슬롯 수)`.
- sentinel `0`은 파일 누락·손상으로는 만들어질 수 없다(정수 파싱 실패는 fallback=현재값을 돌려줘야 하므로 6이 된다). 즉 `0`은 **명시적 의도**만을 뜻한다.
- 실제 컷 수는 설정 검증(clamp·허용 집합)을 **거치지 않는다.** 따라서 허용 집합에 없는 7컷이 정상 동작해야 하고, 컷 수에 의존하는 UI(썸네일 배치 등)는 열 수를 하드코딩하지 않아야 한다.
- 슬롯 수 상한을 자동 결과에 적용하지 않는다 — 적용하면 "컷 수 ≥ 슬롯 수" 불변이 깨져 빈 슬롯이 생긴다.

## 3. 로컬 프레임 저장소

### 3.1 저장 대상

| 무엇 | 서버에 올라가나 |
|------|-----------------|
| 공용 기본 프레임(서버에서 내려받은 것) | 서버에 원본 존재 — 로컬은 **캐시** |
| 번들 자산 프레임 | ✕ (설치물) |
| **일반 사용자·고급 유저 커스텀 프레임** | **✕ — 로컬 전용** |
| power가 새로 만든 공용 프레임 | ○ (`POST /frames`) + 로컬 캐시 |

> 정책: 서버 `frameTemplates` 컬렉션에는 **공용 기본 프레임만** 저장된다. 개인 커스텀 프레임은 **기기 로컬 전용**이다. 따라서 기기를 바꾸면 개인 프레임은 따라가지 않는다(현재 의도된 동작, 동기화는 비범위).

### 3.2 파일 레이아웃과 공용/개인 구분

프레임 하나 = **이미지 파일 1개 + 슬롯 파일 1개**(같은 base name, 확장자만 다름).

> ⚠️ **2026-08-07 개정 — 아래 접두 규약은 폐지됐다.** 소유 판정이 파일명이 아니라 `.slots`에 **서명된 `#owner`**
> 로 옮겨갔고(설계 [`wpf-frame-ownership-binding-design`](../design/wpf-frame-ownership-binding-design.md)),
> 개인 프레임은 `users/{SHA256(이메일) 앞16hex}/` 하위에 저장한다. 새 규격은 §3.2.1이다.
> 아래 서술은 **웹 클라이언트가 아직 쓰는 v1 규약**이므로 이력으로 남긴다(→ [`web-client/12` C15](../web-client/12-web-vs-windows-differences.md)).

```
{프레임 저장 루트}/
  베이직 4컷.png            ← 공용 (접두 없음)
  베이직 4컷.slots
  devmcjo_내프레임.png      ← 개인 ({계정}_ 접두)
  devmcjo_내프레임.slots
```

| 규칙 | 내용 |
|------|------|
| 공용 프레임 | base name에 **`_`가 없다**. 게스트를 포함해 누구에게나 노출 |
| 개인 프레임 | base name이 **`{계정id}_{프레임이름}`**. **본인 로그인 시에만** 노출 |
| 공용 판별식 | `!baseName.contains('_')` |
| 개인 판별식 | `baseName.startsWith(계정id + "_")` |
| 표시 이름 | 개인은 접두를 제거한 나머지, 공용은 base name 그대로 |
| 이미지 포맷 | **항상 PNG** |
| 슬롯 파일 없음 | 로컬 프레임으로 **인정하지 않고 건너뛴다** |
| 이름 정규화 | **하지 않는다.** 원문 그대로 저장하고, 파일시스템 금지문자(`\ / : * ? " < > |`)가 있으면 **저장을 거부**한다(치환 금지) |
| 빈 이름 | 저장 거부 |

> ⚠️ **프레임 이름에 `_`를 허용하면 안 되는 이유**: `_`가 공용/개인 구분자다. 공용 스코프에 `_`가 든 이름을 저장하면 그 프레임은 공용 목록에서 사라진다. 서버도 프레임 이름의 `_`를 **400으로 거부**한다([31 §8](./31-backend-api-reference.md)). 이름 자체에 `_`가 든 경우의 모호성은 수용된 트레이드오프다.
>
> **플랫폼 대체**: 파일명 접두 대신 디렉터리 분리(`public/` + `users/{계정}/`)나 DB 테이블로 구현해도 된다. 유지해야 하는 것은 **"공용 = 전원 노출, 개인 = 본인만 노출, 이름 충돌 판정은 스코프 안에서"** 라는 의미다. 단 서버가 강제하는 **프레임 이름의 `_` 금지**는 그대로 지켜야 한다.

### 3.2.1 새 규격 (v2 · 2026-08-07)

```
{프레임 저장 루트}/
  베이직 4컷.png                 ← 공용(번들·DB default 캐시). 루트
  베이직 4컷.slots
  users/
    3f9a2c1b8d4e7a05/            ← SHA256(정규화 이메일) 앞 16hex
      내 프레임.png
      내 프레임.slots            ← #owner=a@google.com (base64+서명 안)
```

| 규칙 | 내용 |
|------|------|
| 소유 판정 | **서명된 `#owner`가 유일한 권위**다. 파일명·폴더명은 저장 위치일 뿐이라 옮기거나 바꿔도 판정이 달라지지 않는다 |
| 공용 | `#owner=default` — 게스트 포함 전원 노출 |
| 개인 | `#owner={이메일}` — 로그인 이메일과 일치할 때만 노출(대소문자 무시) |
| 폴더 | 개인은 `users/{이메일 해시}/`. **이메일을 평문으로 두지 않는다**(폴더명·파일 내용 어디에도 남지 않음) |
| 이름 충돌 | 계정별 폴더가 다르므로 **다른 계정과 같은 이름을 써도 충돌하지 않는다**. 같은 계정 안에서는 "본인에게 보이는 이름"과 중복 금지 |
| 이름의 `_` | 로컬 제약은 사라졌지만 **서버가 여전히 거부**한다(웹·모바일이 v1 접두 규약을 쓰는 동안 유지) |
| 검증 실패 | 서명 불일치·손상·구 포맷은 **조용히 목록에서 제외**한다(삭제하지 않는다) |

### 3.3 `.slots` 파일 포맷 (계약)

UTF-8 텍스트, 줄 단위. 라인 종결자는 `\n`.

```
#imagesize=1200,1600
#dbid=8f2c1a90-3d5e-4b17-9c22-0ab7de441f03
0,80,140,480,640
1,640,140,480,640
2,80,840,480,640
3,640,840,480,640
```

| 줄 종류 | 형식 | 의미 |
|---------|------|------|
| 이미지 크기 메타 | `#imagesize={width},{height}` | 프레임 원본 픽셀 크기. **슬롯 좌표계의 기준** |
| 서버 문서 id 메타 | `#dbid={frameId}` | **있으면** 서버 문서와 연결된 프레임(삭제 시 서버 매칭에 사용) |
| 기타 `#` 시작 줄 | — | **주석으로 무시** |
| 슬롯 줄 | `{index},{x},{y},{width},{height}` | 5개 정수, 콤마 구분. 프레임 픽셀 좌표 |
| 빈 줄 | — | 무시 |
| 형식 위반 줄 | — | **무시하고 계속**(예외 금지) |

**파싱 규칙**
- 메타 키 비교는 **대소문자 무시**.
- 슬롯 줄은 필드가 정확히 5개이고 전부 정수 파싱에 성공할 때만 채택한다.
- `#imagesize`가 없으면 크기는 0으로 남는다(방어적 기본값).

**`#dbid` 유무의 의미 — 이게 핵심 규약이다**

| 저장 상황 | `#dbid` | 결과 프레임 id | 편집·삭제 판정 |
|-----------|:-------:|----------------|----------------|
| 서버 공용 프레임 캐시 | **기록** | 서버 문서 id 그대로 | "서버 공용 기본" → power만 |
| power가 신규 생성해 서버 등록 | **기록** | 서버 문서 id | 동상 |
| 개인 스코프 저장 | 없음 | **`local:{파일 base name}`** | "본인 로컬 생성분" |
| 사본(fork) 저장 | **없음** | `local:{파일 base name}` | 동상 — **서버 문서와 연결이 끊긴다**(의도) |

프레임 id 접두 규약(출처 판정)은 [13 §6.1](./13-client-behavior-spec.md)에 정리돼 있다: `local:` = 본인 로컬, `bundle:` = 번들, `fallback` 또는 빈 id = 코드 생성, 그 외(접두 없는 실 id) = 서버 공용.

### 3.4 삭제 규칙

```
deleteLocal(frame):
  1. 이미지 파일 경로 확인. 없으면 실패(false) 반환
  2. .slots 파일 삭제 (실패 무시)
  3. 이미지 파일 삭제 (실패 무시)
  4. 성공 판정 = "이미지 파일이 실제로 사라졌는가"
```

- **파일 잠금 주의**: 목록 썸네일이 파일을 잡고 있으면 삭제가 실패한다. 이미지 로딩 시 **파일 핸들을 즉시 놓는 방식**(전체 로드 후 닫기, 캐시 우회)을 써야 한다. Windows 구현에서 이 문제가 실제 결함이었고, 로더를 "즉시 로드 + 캐시 무시 + 불변화" 3종 규약으로 고쳐 해결했다.
- 성공 여부를 **정직하게 반환**하고 실패 시 사용자에게 알린다([13 §6.6](./13-client-behavior-spec.md)).

### 3.5 알려진 미해결 사항 (새 클라이언트가 개선해도 좋은 지점)

| 항목 | 현상 |
|------|------|
| 이름 변경 저장 시 옛 파일 잔존 | 로컬 프레임 이름을 바꿔 저장하면 새 파일명으로만 쓰기 때문에 옛 `{계정}_{옛이름}.png`/`.slots`가 남는다 |
| power의 공용 로컬 사본 재편집 불가 | 공용 스코프 사본은 소유자 정보 없이 로드돼 "본인 로컬 소유" 판정에서 탈락한다 |
| 공용 로컬 프레임 삭제가 소유자로 제한되지 않음 | 삭제 판정이 소유자를 보지 않는다(§3.3의 소유자 메타 부재가 원인) |

상세와 결정 대기 상태는 [90 §1](./90-roadmap-and-future-work.md).

## 4. 세션 작업 공간 (촬영 임시 산출물)

```
{앱 데이터 디렉터리}/sessions/{세션별 고유 id}/
    session.mp4        ← 세션 녹화본 (업로드하지 않음)
    timelapse.mp4      ← 타임랩스
    final.{jpg|png}    ← 최종 합성 이미지
```

| 항목 | 규격 |
|------|------|
| 생성 시점 | 촬영 화면 진입 후 **카메라 Ready 이후** |
| 정리(정상) | 촬영 세션 종료·리셋 시 **해당 세션 폴더** 삭제 |
| 정리(잔재) | **앱 시작 시 `sessions` 루트의 잔여 하위 항목을 일괄 삭제**(비정상 종료 대비) |
| **정리 비대상** | 로컬 결과물 보관 폴더(§5)와 로그 폴더는 **절대 지우지 않는다** |
| 개별 삭제 실패 | 무시하고 최대한 정리한다(사용 중 파일 등) |

> 이 "시작 시 잔재 정리"는 규격이다. 없으면 강제 종료가 반복될 때 임시 동영상이 무한히 쌓인다. 모바일 플랫폼에서 캐시 디렉터리를 쓰면 OS가 일부 회수하지만 **보장되지 않으므로 직접 정리**해야 한다.

## 5. 로컬 결과물 보관 (영구)

| 항목 | 규격 |
|------|------|
| 활성 조건 | 설정 `SaveLocalCopy` on |
| 위치 | 설정 `LocalSavePath`. 빈 값이면 **플랫폼 기본 결과물 위치**(Windows: `{실행경로}\result\`) |
| 세션 폴더명 | **`mcphoto_YYMMDD_HHMM`** (예: `mcphoto_260730_1445`) |
| 충돌 처리 | 같은 폴더가 있으면 `-2`, `-3` … 접미 |
| 파일 | `final.{jpg\|png}` + `timelapse.mp4`(있을 때만) |
| 만료 | **없다 — 영구 보관.** 서버 TTL·Lifecycle과 무관 |
| 실패 처리 | 쓰기 불가 시 **예외가 아니라 null 반환** + 오류 로그. 촬영 흐름을 중단하지 않는다 |
| 실행 시점 | **업로드 시도 이전**([13 §4.7](./13-client-behavior-spec.md)) |

> **모바일 플랫폼 대응**: "폴더에 복사"가 자연스럽지 않다. 사진 라이브러리(iOS Photos / Android MediaStore)에 저장하거나 앱 전용 디렉터리에 보관 후 공유 시트를 제공하는 것이 관용적이다. **유지해야 하는 성질은 "업로드 실패와 무관하게 결과물이 기기에 남는다"** 이며, 저장 위치·권한 UX는 플랫폼 관례를 따르면 된다. 권한 거부 시에도 크래시 없이 안내해야 한다.
>
> 로컬 결과물의 보관·정리 정책은 현재 **무기한 영구 보관**이며 장기 개선 항목이다([90 §2.1](./90-roadmap-and-future-work.md)). 모바일에서 무제한 누적은 저장공간 문제가 되므로 새 클라이언트는 정리 정책을 함께 설계하는 편이 낫다.

## 6. 브랜딩 (앱 표시명)

| 항목 | 규격 |
|------|------|
| 값 | `AppName`(앱 이름) · `Subtitle`(홈 화면 소제목) |
| 기본값(폴백) | `AppName = "MCPhoto"` · `Subtitle = "self custom photobooth"` |
| 폴백 독립성 | 두 값은 **독립적으로** 폴백한다(한 값만 비어도 그 값만 기본값) |
| 적용 지점 | 창/앱 제목 · 홈 화면 타이틀 · 홈 화면 소제목 |
| 로딩 시점 | **첫 화면이 만들어지기 전에** 주입한다(초기 렌더에 반영되도록) |
| 변경 반영 | 읽기 전용. 변경은 앱 재시작 필요 |
| 인코딩 | **UTF-8 명시**(한글 이름 대응) |
| 실패 | 어떤 실패에도 크래시 금지 → 기본값 사용 |

**Windows 구현(참고)**: `branding.ini`(섹션 `[Branding]`, 키 `AppName`/`Subtitle`)를 실행 경로 → `%ProgramData%\MCPhoto` 순으로 찾아 첫 파일을 사용한다. 샘플 파일을 동봉해 고객이 리네임해서 쓴다.

**플랫폼 대응**: 스토어 배포 앱은 사이드카 파일을 두기 어렵다. **원격 구성(서버 제공 브랜딩) 또는 빌드 변형(flavor/scheme)** 으로 대체하는 것을 권장한다. 원격 구성으로 갈 경우 서버 엔드포인트가 없으므로([31 §10](./31-backend-api-reference.md)) 추가 설계가 필요하다.

## 7. 버전·빌드 정보 표기

| 항목 | 규격 |
|------|------|
| 값 | `Version`(예 `1.1.6`) · `BuildDate`(빌드 시각) |
| 표시 문자열 | `v{Version}` (예 `v1.1.6`) |
| **`BuildDate`는 하단 표기에서 제외** | 업데이트 지연 시 오래된 앱으로 보일 위험. 값은 보관하되 하단 캡션에는 쓰지 않는다 — **진단·문의 화면에서만** 노출한다 |
| 표시 위치 | 화면 하단(흐린 캡션). **로그인 여부와 무관하게 상시** 노출, 클릭 비간섭 |
| 폴백 | 정보 부재·손상 시 `Version = "0.0.0"`, `BuildDate` 빈 문자열. 크래시 금지 |

**it18 개정**: 종전 규격에 있던 **`Site`(배포 채널) 표기를 폐기**했다 — 개발·알파 서버를 운영하지 않으면 값이 고정돼 정보량이 0이다. 새 클라이언트도 채널 표기를 만들 필요가 없다(운영 환경이 여러 개가 되면 그때 도입).

**Windows 구현(참고)**: 버전은 **어셈블리 버전 리소스**(`Directory.Build.props`의 `<Version>` → `AssemblyVersion`/`FileVersion` 파생)에서, 빌드 시각은 **exe의 `LastWriteTime`** 에서 읽는다(`AssemblyBuildInfoService`). 외부 파일(종전 `bldinfo.ini`)은 폐기됐다 — 리소스 버전과 표기 버전의 이중 관리를 없애기 위해서다. exe 경로는 `Environment.ProcessPath`를 쓴다(`Assembly.Location`은 단일 파일 퍼블리시에서 빈 문자열).

**플랫폼 대응**: 스토어 배포 앱은 번들 버전(`CFBundleShortVersionString` / `versionName`)을 그대로 쓰는 것이 정석이며, 이는 it18의 방향(빌드 산출물 자신이 버전의 유일한 출처)과 일치한다. 빌드 시각은 스토어 앱에서 파일 타임스탬프로 얻기 어려우므로 빌드 시 상수로 주입하는 방식이 현실적이다.

> 현재 로드맵에 **"설정 안에 [버전 확인] 버튼 + 모달, 그 안에 개발자 문의(`devmcjo@gmail.com`) 안내"** 로 재배치하는 아이디어가 등재돼 있다([90 §6](./90-roadmap-and-future-work.md)). 새 클라이언트는 처음부터 그 형태로 만드는 것을 고려할 만하다 — 모바일에서는 화면 하단 상시 캡션이 공간을 낭비한다.

## 11. 라이선스 고지 요약 메타데이터 (`licenses/notice-manifest.json`, it24)

읽기 전용 배포 자산이며 앱이 **소비만** 한다(생성·수정하지 않는다). 이 리포에서 앱이 읽는 JSON 파일의 첫 사례다 — 그 전까지 JSON은 HTTP 계층 전용이었다.

- **위치**: 실행 파일 옆 `licenses\notice-manifest.json`. 사용자 데이터가 아니라 **배포물에 동봉되는 정적 문서**이므로 `%ProgramData%`가 아니다.
- **왜 파일인가**: 법적 고지의 단일 소스는 배포물에 동봉된 파일이어야 한다. 요약을 exe 안 상수로 옮기면 고지 폴더를 교체한 배포물에서 화면과 파일이 서로 다른 말을 한다. 반대로 txt 산문을 파싱하면 고지 문구를 다듬을 때마다 화면이 깨진다.
- **왜 `.json`인가**: 확장자가 `.txt`가 아니라서 고지 문서 열거(`licenses/**/*.txt`)에 걸리지 않는다 → 기계용 파일이 사용자에게 보이는 문서 목록에 섞이지 않는다. INI를 쓰지 않은 이유는 컴포넌트가 배열이고 값이 문장이라 섹션·키 구조로 어색하고, 리포의 `IniFile`은 설정 파일 전용 자산(주석·개행 손실 이력)이기 때문이다.
- **인코딩**: UTF-8 no BOM · CRLF (고지 txt와 같은 규약).

### 11.1 스키마

| 필드 | 형 | 필수 | 의미 |
|------|-----|:---:|------|
| `schemaVersion` | int | ✅ | 현재 `1`. **다르면 해석하지 않고 강등**한다(앱보다 새로운 파일을 억지로 읽으면 잘못된 고지를 표시한다) |
| `updatedOn` | string | — | 고지 기준일 `yyyy-MM-dd`. 화면 푸터에 `{값} 기준`으로 표기. **색인 txt의 "이 고지의 기준일"과 같아야 한다**(테스트가 고정) |
| `components[]` | array | ✅ | 구성 요소 목록. **배열 순서 = 표시 순서**(코드가 재정렬하지 않는다). `kind:"self"` 항목이 첫 번째여야 한다 |

`components[]` 항목:

| 필드 | 필수 | 의미 |
|------|:---:|------|
| `kind` | ✅ | `self`(앱 본체) 또는 `redistributed`(동봉된 제3자). 그 외 값은 오타로 보고 **강등**한다(잘못된 섹션에 조용히 들어가는 것보다 낫다) |
| `name` | ✅ | 사용자가 아는 이름 |
| `version` | — | 바이너리 특정용. **`kind:"self"`는 반드시 `null`** — 앱 버전은 어셈블리 버전 리소스가 단일 소스이고, 여기 적으면 릴리스마다 어긋난다 |
| `licenseName` | ✅ | 사람이 읽는 라이선스 이름. **영문 유지**(식별자이므로 번역하면 지목 대상이 달라진다) |
| `spdxId` | ✅ | SPDX 표준 짧은 식별자(`MIT`·`GPL-3.0-or-later`). 화면 배지에 강조 표시 |
| `copyright` | — | 저작권 표시. GPLv3 §4가 **유지(retain)**를 요구하므로 원문 형태를 보존한다 |
| `purpose` | — | 왜 이 구성 요소가 여기 있는지 |
| `distribution` | — | 배포 형태. GPLv3 §5(a) 수정 사실 표시를 이 한 줄이 겸한다 |
| `sourceOffer` | — | 대응 소스 제공 사실(GPLv3 §6). 값이 있으면 첫 화면에 행이 생긴다 |
| `fullTextFile` | ✅ | 라이선스 전문 **파일명**. [라이선스 전문 보기]의 대상 |
| `noticeFile` | — | 상세 고지 **파일명**. 있으면 [소스 코드 제공 안내] 버튼이 생긴다 |

> `id` 필드를 두지 **않는다.** 표시에 쓰이지 않고 코드가 분기하지 않는다 — 분기하면 매니페스트가 데이터가 아니라 코드가 된다.

### 11.2 파싱·검증 규칙

| 규칙 | 내용 |
|------|------|
| 파서 옵션 | camelCase + 대소문자 무시(리포 선례) + **주석 허용** + **후행 콤마 허용**. 뒤 두 개는 이 파일이 사람이 손으로 편집하는 자산이기 때문이다(설명 주석을 달아 둘 수 있어야 유지보수가 산다) |
| 빈 문자열 정규화 | 공백만 있는 값은 **`null`로 정규화**한다. 화면의 행 표시 여부가 `null` 하나로 결정된다 |
| 파일 참조 제한 | `fullTextFile`·`noticeFile`은 **파일명만**. 경로 구분자·`..`·드라이브 문자를 거부하고, 결합 결과가 고지 폴더 하위인지 **재확인**한다. 위반은 참조 무효(=부재)로 처리하고 Warning 로그를 남긴다 — 허용하면 고지 화면이 임의 파일 리더가 된다 |
| 크기 상한 | 고지 본문과 같은 2 MB |
| 실패는 예외가 아니다 | 부재·손상·스키마 불일치·필수 필드 누락·항목 0개는 모두 **강등 사유 문자열**로 돌려준다. 예외가 새면 설정 화면이 통째로 닫힌다 |

### 11.3 강등 등급 (화면이 무엇을 보여주는가)

| 상황 | 화면 |
|------|------|
| 정상 | 요약 카드 + [전문 보기]. `그 외 동봉 고지 문서` 섹션은 항목 0건이라 렌더링되지 않는다 |
| 선언된 파일 부재·참조 무효 | 카드 유지 + 카드 안 경고 1줄. 버튼은 **활성 유지**(누르면 사유 표시) |
| 선언되지 않은 `.txt` 존재 | `그 외 동봉 고지 문서`에 파일명 그대로 나열 |
| 매니페스트 부재 | 경고 배너("찾을 수 없어…") + 폴더의 고지 문서 목록으로 축퇴. **전문 도달 경로 유지** |
| 매니페스트 손상 | 경고 배너("읽을 수 없어…") + 같은 폴백. 부재와 **다른 문구**다(조치가 다르다) |
| 폴더·`.txt` 자체가 없음 | 강등이 아니라 배포 누락 — 폴더 부재/파일 0건을 구분해 오류로 알린다 |

> 문구·화면 규격 상세는 [11 §19](./11-exe-app-features.md), 법적 근거는 [ffmpeg 라이선스·배포 설계](../design/wpf-ffmpeg-licensing-and-distribution-design.md), 재설계 근거는 [it24 라이선스 고지 재설계](../design/wpf-it24-license-notice-redesign-design.md).

### 11.4 이식 시

플랫폼이 바뀌어도 **매니페스트 + 전문 txt 분리**는 유지한다(모바일 플랫폼의 오픈소스 고지 관례와 동형이다: 메타데이터로 목록을 그리고, 항목을 누르면 전문을 보여준다). 고지 폴더의 위치만 플랫폼별 앱 번들·리소스 경로로 대응하면 된다.
