진실원 우선순위(`docs/design/README §4`)는 **관측 가능한 현행 동작**을 보호하기 위한 규칙이다.
아래 두 경우에는 "소스가 사실"을 기계적으로 적용하지 않는다.

1. **호출자 0 / 렌더된 적 없는 코드** — 보호할 현행 동작이 없다. 이때는 플랫폼 중립 규격
   (`docs/analysis` + Windows 소스)이 이긴다.
   예: Step 16에서 `domain/accounts/sessionUser.ts`의 `authMethodLabel`이 `"Google 계정"`을 돌려주고
   있었으나 호출자 0 + `Account`가 더미였다 → Windows `AuthMethodExtensions.ToLabel`·`analysis/13 §14`의
   **"Google SSO"** 로 소스를 고쳤다.
2. **아직 구현하지 않은 요구사항** — "소스에 없으니 문서가 틀렸다"가 아니다. 미구현일 뿐이다.
   예: 02 §5.1의 계정 팝오버(로그아웃 포함)가 미구현이라 앱에 로그아웃 경로가 아예 없었다 → 지웠어야
   할 요구사항이 아니라 Step 16에서 닫아야 할 구멍이었다.

반대로 **소스가 이긴 사례**: 슬롯 배율 10~300(Step 15, 커밋 `0a93b59`) — 구현·동작·커밋 의도가 모두
있었고 문서만 낡았다. 문서 6곳을 소스에 맞췄다.

**Why:** Step 15에서 배율 규격이 두 번 되돌려질 뻔했고, Step 16에서 같은 규칙을 반대 방향으로
적용해야 하는 사례가 나왔다. 규칙만 외우면 둘 중 하나를 반드시 틀린다.

**How to apply:** 소스와 문서가 어긋나면 먼저 **"그 코드가 실제로 실행된 적이 있는가"** 를 확인한다
(`grep`로 호출자 수 · 화면이 더미인지). 있으면 소스가 사실, 없으면 규격이 사실. **어느 쪽이든 판정
근거를 설계 문서에 코드 주석처럼 남긴다** — 남기지 않으면 다음 세션이 되돌린다.
