사용자가 "이 기능 제거"를 요구하면 먼저 **코드에 실재하는지 확인**하고, 설계 문서만 있는 경우
파일을 지우지 말고 **폐기 표시 + 근거·이력 보존 + 참조 전수 정리**로 처리한다.

**Why:** 리포 관례다(선례: `docs/web-client/05 §4.6` 프레임 zip 폐기, `docs/billing/04 §5` 로그아웃
purge 폐기). 폐기된 규격도 **왜 그렇게 하려 했는지**의 운영·정책 지식을 담고 있어 훗날 같은 논의가
반복될 때 근거가 된다. 더 중요한 이유는 **참조 정리**다 — 문서 하나만 폐기 표시하고 참조를 남기면
다른 문서들이 계속 거짓을 말한다.

**How to apply:**
- 형식: 제목에 `~~취소선~~ → ❌ **YYYY-MM-DD 폐기**` + `> 🚫` 블록에 **폐기 사유(명분이 무엇이었고 왜
  소멸했는가)** + 함께 폐기되는 것 / 살아남는 것 / **남는 리스크** 목록 + 원문은 `<details>`로 접어 보존.
- 반드시 **참조 전수 grep**을 먼저 한다(파일:줄 단위 조치표). 식별자·요구 표현·관련 용어를 모두 넣고,
  ⚠️ **동명이의 오치환**을 경계한다(예: "세션"이 촬영 세션·JWT 홀더·업로드 sessionId·로그인 세션
  레지스트리 4가지를 가리킨다. `maxSessions`는 로컬 사진 보관 개수이기도 하다).
- **불변식·게이트·미결정·Step 번호는 재사용·재배열하지 않는다** — 여러 문서가 교차 참조하므로 번호를
  당기면 다른 문서의 뜻이 조용히 바뀐다. `~~B11~~ ❌ 폐기`처럼 번호를 남긴 채 표시한다.
- 폐기가 **다른 설계의 전제였는지**를 반드시 분석한다. 전제가 사라진 설계는 ① 이미 다른 이유로 죽었나
  ② 대안이 있나 ③ 함께 폐기인가 중 하나로 판정한다. 판정하지 않으면 근거 없이 떠 있는 설계가 남는다.
- 코드가 없는 폐기라면 PR에 `src/`·`web/` 변경이 **0줄**이어야 하고, 그것을 `git diff --stat`으로
  검증 항목에 넣는다.
- 사례: `docs/design/wpf-it23-session-testmode-license-design.md` A부(단일 세션 강제 폐기, 12문서 43건).
